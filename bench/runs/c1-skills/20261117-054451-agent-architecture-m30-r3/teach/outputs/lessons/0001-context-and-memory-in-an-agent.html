Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in saved notes, or in a manual that is searched on demand.

Objective O3: context window, what is kept between steps and sessions, retrieval and notes as memory About 30 minutes Builds on your work on the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small model budget. Those are three separate design choices: what the model sees right now, what is saved for next time, and how the right manual page is found. This lesson gives you a way to make each choice and defend it at your design review.

Your program runs the tool, not the model. The model only writes a request for the tool, the program carries it out, and the result goes back to the model, which then decides what to do next. Today's question is about that last part: when the result "goes back to the model", where exactly does it go, and how long does it stay there?

The model sees only what is in its context 6 min

Here is one model call from the makerspace assistant, written the way you would build it in Python. Nothing else is available to the model during this call.

request = {
    "system": "You help students at the Westfield makerspace. Be brief.",
    "tools":  [calendar_tool, booking_tool],        # their descriptions
    "messages": [
        {"role": "user", "content": "Is the laser cutter free on Friday?"}
    ],
}
reply = call_model(request)

Trace it. The model receives the system prompt, the two tool descriptions and one student message. Ask it "what did the student ask me yesterday?" and it cannot say: yesterday is not in request. Ask it "what does the laser cutter manual say about acrylic?" and it can only guess from training, because the manual is not in request either. Whatever you want the model to use must be written into this request. Whatever is not there does not exist for it.

That bundle has a name: the context, the set of tokens the model reads when it generates a reply. The context window is the limit on how many tokens it can hold at once, and it covers everything: the system prompt, every message, tool results, your tool definitions and the reply the model writes ([Claude API docs: context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)). The docs call it the model's "working memory", as distinct from the training data it learned patterns from.

Why this works

A language model is a function from text in to text out. It has no database of past conversations and no connection to your files. Its only input is the request, so the request is the only place where information can reach it.

Check yourself

A student tells the assistant, in a chat on Monday, "I'm left-handed, so please give me left-side instructions." On Tuesday a new request is sent with only a system prompt and the new question. What will the model do about handedness?

Show the answer

The third option. The context is the only channel into the model, and Tuesday's context has no handedness in it.

Between steps: the history is resent 6 min

Now follow one request through the agent loop and count what the model reads at each call. The student asks: "What blade speed should I use for 3 mm acrylic on the laser cutter?" Assume the system prompt and tool descriptions together take about 800 tokens.

CallWhat is in the requestInput tokensModel writes
1system and tools (800) + question (20)820a tool request: search_manual("acrylic") (40)
2all of call 1 (820) + that tool request (40) + the manual page that came back (1,500)2,360the final answer (80)

Look at call 2. The model did not "remember" call 1. Your program built a new request that starts with a copy of everything from call 1, then appends the model's tool request and the tool's result. The model reads all 2,360 tokens again, including the 820 it already read. Over the whole request the model read 820 + 2,360 = 3,180 input tokens, even though the student only typed 20 and the page was only 1,500.

In code, the whole mechanism is a list that grows:

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system, tools, messages)   # reads ALL of messages
    messages.append(reply)                        # keep the model's turn
    if reply.is_final:
        break
    result = run_tool(reply.tool_request)         # your program runs it
    messages.append(result)                       # keep the result too

That list has a name: it is the conversation history (the messages above), and it is the only thing the loop carries from one step to the next. Each step resends it in full, and it only grows unless your code trims it ([Claude API docs: context windows](https://platform.claude.com/docs/en/build-with-claude/context-windows)).

Why this works

The model does not keep state between calls, so the only way step 2 can build on step 1 is for step 1 to be pasted into step 2's request. This is also why long agent runs cost more per step as they go: every step pays again for everything before it. Giving the model more text also is not free in quality, because recall of earlier content gets worse as the window fills, which Anthropic calls context rot.

Providers offer prompt caching, which lowers the price of an unchanged beginning of the request. The tokens still occupy the window, though: caching changes what you pay, not what the model reads (same docs page). Check current pricing before you put numbers in your budget.

Between sessions: notes 7 min

A student, Priya, finishes the laser cutter training on Monday and the assistant confirms it. On Thursday she opens a brand-new chat and asks, "Book the laser cutter Saturday." The Monday history is gone: a new session starts with an empty messages list. Without anything saved, the assistant must ask her again whether she has been trained.

The fix is to write the fact somewhere your program owns, then put it back into the next session's request. Here is a small version using a file per student:

import json, pathlib

def load_notes(student_id):
    path = pathlib.Path(f"notes/{student_id}.json")
    return json.loads(path.read_text()) if path.exists() else {}

def save_note(student_id, key, value):       # exposed to the model as a tool
    notes = load_notes(student_id)
    notes[key] = value
    pathlib.Path(f"notes/{student_id}.json").write_text(json.dumps(notes))

# Monday, end of session:
save_note("priya", "laser_cutter_trained", "2026-11-16")

# Thursday, new session starts with an empty history, but:
system = BASE_PROMPT + "\nNotes about this student: " + json.dumps(load_notes("priya"))

Trace Thursday. The history is empty, but the system prompt now contains {"laser_cutter_trained": "2026-11-16"}. The model reads that in its context, so it can go straight to booking. Nothing was "remembered" by the model: your program saved a fact to disk on Monday and pasted it into the context on Thursday.

That is notes as memory, also called structured note-taking: the agent writes information to storage outside the context window and reads it back later (Anthropic: effective context engineering). Claude's memory tool works this way: Claude asks to create, read, update or delete files, and your application carries those operations out against storage you control (memory tool docs). That is the same loop you already know, with "save a note" as one more tool.

Why this works

Context lasts only as long as the history list does, and a new session starts a new list. A file or database row outlives the session, and putting its contents into the next request is the only route back to the model. Notes are short, so reloading them is cheap compared with replaying a whole old conversation.

A common mix-up

"Assistants with a huge context window do not need memory." This is tempting because a big window sounds like a big memory. But the window is emptied at the end of each session, so it does nothing for next week. And inside one session, more tokens is not better by default: the Claude docs say accuracy and recall degrade as token count grows (context rot), so what you choose to include matters as much as how much fits.

Check yourself

Which of these is the best candidate to save as a note for the makerspace assistant?

Show the answer

The third option: a small, durable, per-student fact. Bulky re-fetchable content and fast-changing facts are poor notes.

Long manuals: retrieval 7 min

The laser cutter manual has 80 pages, roughly 100,000 tokens. Pasting it all into every request would make every call expensive, and the model would have to find one number in a mass of text. Instead, store the manual as pages and let the model ask for the ones it needs. Here is a very small search, to trace:

pages = {
  12: "Cutting acrylic: use 60% speed, 80% power for 3 mm sheets.",
  31: "Cleaning the lens: power off, use lens tissue only.",
  47: "Acrylic safety: never leave the cutter unattended while cutting.",
}

def search_manual(query, top=2):
    words = query.lower().split()
    scored = [(sum(w in text.lower() for w in words), n)
              for n, text in pages.items()]
    best = sorted(scored, reverse=True)[:top]
    return [pages[n] for score, n in best if score > 0]

search_manual("acrylic speed 3 mm")

Trace the call. The query splits into four words: "acrylic", "speed", "3" and "mm". Page 12 contains all four, so it scores 4. Page 47 contains "acrylic", so it scores 1. Page 31 matches nothing and is dropped. The function returns pages 12 and 47, about 40 tokens in this toy, or roughly 3,000 tokens for two real pages, instead of 100,000 for the manual. Those pages land in the history as the tool result, and the model answers from page 12.

This is retrieval: finding the few pieces of a large store that matter for this question and placing only those in the context. When the model decides when to search, by calling a tool at run time, Anthropic calls it just-in-time retrieval: the agent keeps lightweight handles like file paths or queries and loads data when needed (Anthropic: effective context engineering). It trades some speed, since each search is an extra step in the loop, for a much smaller context.

Why this works

The window is limited and every token in it costs money and a little attention. A question needs a handful of facts, not the entire manual, so selecting those facts first keeps the request short, cheap and easier for the model to read. The quality of the answer now depends on the search: if page 12 is not returned, the model cannot use it.

Real systems rank pages better than counting shared words, for example by comparing meaning rather than spelling. How search ranks is a topic for a later lesson; here you only need the idea that a search step sits between the big store and the context.

Worked example and practice 4 min

Worked example

Priya (trained on the laser cutter last week) writes: "Book the laser cutter Saturday morning, and remind me what speed to use for acrylic." For each piece of information, decide where it lives: context for this session, a note saved between sessions, or retrieval from a store.

  1. The assistant's instructions and tool descriptions. Needed in every call, small, same each time: always in the context (the system prompt).
  2. Priya's laser cutter training. A short fact about one student that must survive between visits: a note, loaded into the system prompt at session start.
  3. The acrylic speed. One fact inside a long document: retrieval. Search the manual, and only the matching page enters the context.
  4. Saturday's free slots. Changes constantly, so do not save it: call the calendar tool, and the result stays in the history for the rest of this session.

Each answer follows the same test: how long must it live, how big is it, and how often does it change?

Sort these four things: (a) the booking tool's description, (b) the fact that this student's CNC training was approved on 3 Nov, (c) the plywood feed-rate table in the 120-page CNC manual, (d) the "booking confirmed" result that comes back. Start with (a): it is needed on every call and is small, so it goes in the context. Do the other three, and give a reason for each.

Show a solution

(a) Context, in the system prompt or tool list, every call. (b) A note: short, about one student, and must survive between sessions; load it at the start. (c) Retrieval: one table inside a long manual, so search it and put only that page in the context. (d) Context, as a tool result in the history: it matters for the rest of this session, but it is not a note unless a later session needs it, and the booking system already holds the truth.

Summary 2 min

  • The model reads only its context: system prompt, tool descriptions, messages and tool results. It has nothing else to go on.
  • Between steps, the program resends the whole history each call, so requests grow and cost more per step.
  • Between sessions, nothing survives unless your program saves it as a note and loads it into the next request.
  • For large stores like manuals, retrieval puts only the few relevant pages in the context, and the search decides whether the right page arrives.
