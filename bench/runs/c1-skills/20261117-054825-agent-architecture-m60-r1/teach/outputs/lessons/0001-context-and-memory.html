Lesson 1 · 60 minutes

Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in a saved note, or in a manual that is searched on demand, and say why.

Objective O3: context window, what is kept between steps and sessions, retrieval and notes as memory About 60 minutes
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small budget. Those are three separate memory problems with three different tools. At your design review you will need to say which tool you chose for each and what it costs.

Warm-up 4 min

Two questions from your earlier sessions. Answer in your head or on paper first, then open the answer.

Recall

The agent loop: a student asks, "Is the laser cutter free on Friday?" Name the steps from the question to the final answer, in order. Which part of the system actually runs the calendar lookup: the model or your program?

Check your answer

The model is given the question and the tool list. It asks for an action (a calendar lookup with a date and a machine). The program carries it out and sends the result back. The model reads the result and either asks for another action or writes the final answer. If you said "the model runs it", look again: the model only writes the request, and your program runs the tool. That detail matters today, because every one of those hand-backs is another model call, and each call has to be given everything the model needs to know.

Recall

In one sentence: what does a language model do, mechanically, when it writes an answer?

Check your answer

It takes text in and writes text out one token at a time, using patterns learned in training. It has no access to anything you did not put in front of it, apart from those learned patterns. Hold on to that: today is about what you put in front of it.

The context window: what the model sees 11 min

Imagine you call the model for the first time from Python. Your program builds this and sends it:

system:  "You are the makerspace assistant. Be brief. Never book a
          machine the student is not trained on."
tools:   [check_calendar(machine, date), book_slot(machine, date, hour)]
user:    "Is the laser cutter free on Friday?"

The model replies with a request to call check_calendar("laser cutter", "Friday"). Your program runs it and gets back ["10:00", "14:00"]. Now you call the model again. What do you send? Not just the two times. The model does not remember the first call, so you send the system text, the tool list, the question, the model's own tool request, and the result:

system:  (same as before)
tools:   (same as before)
user:    "Is the laser cutter free on Friday?"
assistant: [tool request: check_calendar("laser cutter", "Friday")]
tool result: ["10:00", "14:00"]

Only with all of that can the model write "Yes, 10:00 and 14:00 are open." Count what it needed: instructions, tool descriptions, the question, its own earlier request, the result. Everything it used was text you sent in that one call.

That bundle has a name. The context window is all the text a model can reference when it writes a response, including the response itself, and the docs describe it as the model's "working memory", distinct from the data it was trained on (Claude docs: Context windows). Everything in the request counts toward it: the system prompt, every message, tool results, and your tool definitions. The window has a maximum size, measured in tokens (the small pieces of text a model reads and writes); recent Claude models list 1M tokens, but check the current table for the model you choose.

Why this works

The model itself keeps nothing from one call to the next: each call starts blank. The only way it can "know" the question or the calendar result is if your program puts that text into the window of that call. So when an agent seems to remember, your program is doing the remembering by re-sending text.

Check yourself

Between steps: the context only grows 11 min

Follow the booking request through its steps, and count tokens. The numbers are made up to keep the arithmetic easy; real counts come back in each API response, and a token counting API can estimate before you send.

Student: "Book the laser cutter Friday at 14:00."

StepWhat your program sendsInput size
1System text and tools (800), question (20)820
2Step 1 stuff (820), the model's calendar request (40), the result (60)920
3Step 2 stuff (920), the model's booking request (40), the confirmation (30)990
4Step 3 stuff (990), the model's final answer (30), then the student's next question (20)1,040

Each step re-sends everything before it and adds a little. Total input across the four calls: 820 + 920 + 990 + 1,040 = 3,770 tokens, although the conversation holds only about 1,040 tokens of "new" content. Now imagine step 2 returned a 6,000-token manual page instead of 60 tokens. Every later step carries it too: three more calls, each 6,000 heavier. The cost is not what a single message weighs; it is what it weighs times the number of calls that follow.

This is what is kept between steps: inside one session, the history of messages, requests and tool results accumulates, and each new call is given all of it. The docs state it directly: each turn's input is all previous history plus the new message, and previous turns are preserved completely (Claude docs: Context windows).

Why this works

Because the model is blank at every call (section 1), the only way to keep a conversation coherent is to resend it. That makes the context grow with every step, so cost grows with it, and you pay for a big tool result on every later call, not just once. Size therefore matters twice: against the window's limit, and against your budget.

Prompt caching can make repeated prefixes cheaper to pay for, but the docs note that cached tokens still occupy the window: caching changes what you pay, not whether they count. You do not need it yet; just know that it exists when you look at costs.

There is a second cost besides money. Anthropic's engineering team describes context rot: as the number of tokens in the window grows, the model's ability to accurately recall information from it decreases (Effective context engineering for AI agents). A bigger window is not a reason to fill it. The aim they give is the smallest set of high-signal tokens that gets the job done.

Check yourself

An agent makes five model calls to finish a task. A tool result of 2,000 tokens arrives after call 2 and stays in the history. About how many extra input tokens does that one result cost in total?

Show the answer

6,000. The result is resent with every call after it arrives. Make results short, or clear them once they are no longer needed.

When it fills up: compaction 9 min

Suppose a student spends an hour in a long chat about a 3D-printer problem. The history has reached 180,000 tokens and the window is 200,000. Many of those tokens are tool results the assistant no longer needs: an old calendar check, three pages of the manual that did not help. What survives if you do nothing? Nothing needs to be dropped yet, but the next big result will overflow the window, and the docs say that if the input alone exceeds the limit the API returns a 400 error ("prompt is too long").

So at 180,000 tokens, one more model call is made with a special instruction: "Summarize this conversation, keeping the student's goal, what has been tried, the decisions made and what is still unresolved." The model writes a 2,000-token summary:

Student is printing a PLA bracket; nozzle clogged twice.
Tried: cold pull (done), temperature raised to 215 (done).
Still unresolved: layer 3 under-extrusion. Not yet trained on printer B.

Your program now starts the next call with the system prompt, the tools and this summary, instead of the 180,000-token history. The context is back to a few thousand tokens, and the conversation can go on.

This is compaction: summarizing a conversation that is close to the limit and continuing with the summary in place of the full history. Anthropic describes it as keeping key decisions and unresolved problems while dropping redundant tool output (Effective context engineering); the API also offers server-side compaction as the main strategy for long-running agents (Claude docs).

Why this works

Most of a long history is detail that has already done its job. The decision "the nozzle was cleaned" matters later; the 3,000-token log that led to it does not. A summary keeps the decision and drops the log, so you spend a little once to save tokens on every later call. The risk is the same as with any summary: something that mattered later can be left out, and it is gone.

Check yourself

After a compaction, the assistant forgets that the student said they are allergic to resin fumes, which affects which printer to book. What is the most likely cause?

Show the answer

The third. Safety-critical facts should not depend on a summary. That is one reason for the next section: write them down somewhere that is not summarized away.

Between sessions: notes 11 min

On Monday a student, Dana, completes the laser cutter training. The session ends. On Thursday Dana opens a new chat and says, "Book the laser cutter for Friday." Trace what the assistant knows at the start of that new session. The system prompt, the tools, and the new question. That is all. Monday's chat, including the training status, was only ever text in a window, and the window is gone. The assistant has no idea Dana is trained, so it either refuses or asks again.

Now add one tool and one rule. The tool is save_note(student, text) and its partner read_notes(student), backed by a database table. The rule, in the system prompt, is "At the start of a session call read_notes; when you learn something durable, call save_note."

Monday:  model calls save_note("dana", "Laser cutter training done 2026-11-09.")
         program writes a row to the notes table
Thursday: new session, empty window.
         model calls read_notes("dana")  -> "Laser cutter training done 2026-11-09."
         model now knows, books Friday.

The training status lives in a database row, not in the model. The row was written by a tool call and read by another, and only the two lines of text came back into the Thursday window.

This is notes as memory: the agent writes information to storage outside the context window and loads it back in a later step or session. Anthropic calls it structured note-taking, or agentic memory, and notes that the saved text persists across context resets (Effective context engineering). The Claude API's memory tool is one built-in way to do it, in which the model reads and writes files that your application stores (Claude docs: Memory tool).

Why this works

The window is rebuilt from scratch every call, so anything that must outlive a session has to live somewhere that is not the window. Tools are the agent's only way to touch the outside world, so storage is reached the same way as the calendar: the model asks, your program reads or writes, the result comes back as text.

What to save is a design decision, and for you it connects to cost: a note is read into the window at every session start, so ten useful lines beat a whole transcript. A good rule is to save facts that would change a later decision (training status, equipment bans, preferences) and not the chat that revealed them.
Check yourself

Which of these should the assistant save as a note for a later session?

Show the answer

The third. Save short, durable facts that change decisions. Do not save what a tool can look up fresh, and do not save whole conversations.

Long manuals: retrieval 12 min

The makerspace has 40 machine manuals, about 2,000 pages in total, perhaps 1.5 million tokens. A student asks, "What speed should I set for 3 mm acrylic on the laser cutter?" You cannot put 1.5M tokens in the window, and as section 2 showed, you would not want to pay for it on every step even if you could.

So prepare the manuals once, ahead of time: cut each into pages or sections, and store them in a searchable index. Then add a tool, search_manual(machine, query), that returns the best few pieces. Trace the question:

1. Model asks: search_manual("laser cutter", "3 mm acrylic speed")
2. Program searches the index, returns the top 2 pieces (about 600 tokens):
     "Laser cutter, p.31: Materials table. Acrylic 3 mm: 12 mm/s, power 60%..."
     "Laser cutter, p.12: Always remove protective film before cutting..."
3. Model reads the 600 tokens and answers: "12 mm/s at 60% power; remove the film first (manual p.31, p.12)."

Out of 1.5 million tokens, the window got 600, and they were the right ones. The answer can cite the page, so a student can check it.

This is retrieval: the agent fetches only the relevant pieces of a large store into the context window when they are needed, usually by calling a search tool. Anthropic describes agents keeping lightweight references and loading data into context at runtime using tools, rather than pre-loading everything (Effective context engineering). Retrieval-augmented generation, or RAG, is the common name for the pattern of retrieving first and generating from what came back (Anthropic: Contextual Retrieval).

Why this works

The model needs only a few paragraphs to answer one question, but the manuals are far bigger than the window and cost money on every call. A search step turns "all the manuals" into "the 600 tokens that matter", so the window stays small, cost stays low and the answer stays grounded in text that was just put in front of the model.

Retrieval can fail quietly. If a chunk says "increase the speed" without naming the machine or material, the search may not find it. Anthropic's Contextual Retrieval adds a short explanation of where the chunk sits to each chunk before indexing, and reports fewer failed retrievals. The same article notes that a knowledge base under about 200,000 tokens may simply fit in the prompt with no retrieval at all. Both are worth reading later; neither is needed to design your first version.
Check yourself

Your search tool returns the top 5 pieces, each about 1,000 tokens. The model needs one of them. Over a six-step conversation, which change would cut cost most with the least risk to answers?

The second. It uses the lessons of sections 2 and 5 together: retrieved text stays in the history and is resent, so return less of it.

Common mix-ups 3 min

"The model remembers me"

Tempting because chat apps feel continuous. But the model is blank on every call; what looks like memory is your program re-sending history (inside a session) or reading notes (between sessions). If the program does not send it, the model does not have it.

"A bigger window means I can skip memory design"

Tempting because 1M tokens sounds like everything. But a bigger window still empties at the end of the session, still costs more per call the fuller it is, and, per context rot, recall gets worse as it fills. The Claude docs say more context is not automatically better.

"Retrieval and notes are the same thing"

They look alike, since both are a tool that reads stored text into the window. They answer different questions: notes hold what the agent learned about this student and wrote itself; retrieval searches a store of existing documents you prepared. One is written during use, the other beforehand.

Worked example and practice 13 min

Worked example

The assistant must handle: (a) the safety rule "never book an untrained student", (b) which machines Dana is trained on, (c) the laser cutter's material settings, (d) Friday's open slots. Decide where each lives.

  1. The safety rule. It applies to every call and never changes during a session, so it goes in the system prompt, which is part of the window on every call. It is short, so resending it is cheap.
  2. Dana's training status. It must survive between sessions, and it is short and specific to one student. That makes it a note, saved by save_note and read at session start.
  3. The material settings. They are large, written in advance and rarely needed in full. That makes them retrieval: indexed manual pages fetched by search_manual.
  4. Friday's open slots. They change constantly, so any saved copy goes stale. They are neither a note nor a manual; they are fetched fresh by check_calendar at the moment they are needed.
  5. Cost check. Only the rule and the notes enter every call. Manual pieces and calendar results enter only when asked for, and a long chat can be compacted. That keeps the per-call input small.
Your turn

Place these three pieces of information, using the same reasoning: (a) "Students may book at most 4 hours per week"; (b) Dana prefers morning slots; (c) the 3D printer's filament-loading steps. For each, say: system prompt, note, retrieval or fresh tool call, and give one reason. Step 1 is done for you: (a) is a rule that applies to every call and is short, so it goes in the system prompt. Do (b) and (c) yourself.

Show a solution

(b) A note. It is about this student, short, and learned during use; the assistant writes it once with save_note and reads it at the start of later sessions. (c) Retrieval. It is part of a long manual prepared in advance and only needed when someone asks; fetch it with search_manual rather than keeping it in every window. A reasonable argument for (a) as a fresh tool call also exists if the limit changes often, but a stable rule belongs in the prompt.

Challenge

Your sponsor says: "Just paste all the manuals into the prompt, and the assistant will be simple." Write two sentences for your design review that answer this using what you know about the window, the cost per step and context rot.

Show a model answer

Pasting 1.5M tokens fills or overflows the window, and because the history is resent on every step, we would pay for all of it at every model call; recall also drops as the window fills, so the answers could get worse. Retrieval gives the model about 600 relevant tokens per question, which is cheaper and easier to cite.

Summary 3 min

  • The context window is everything the model can use in one call; the model is blank at every call, so your program resends what it needs.
  • Within a session the context only grows, so every large tool result is paid for again at every later step; and recall worsens as it fills.
  • Compaction replaces a long history with a summary, and can lose details.
  • Between sessions, nothing is kept unless a tool writes it to storage; notes are short, durable facts that change decisions.
  • Retrieval searches a large prepared store and puts only the few relevant pieces in the window.

Say it in your own words: without looking, explain to a teammate where each of these lives in the assistant: the booking rules, a student's training status, and the laser cutter manual, and what each choice does to cost.
