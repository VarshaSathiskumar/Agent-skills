Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context window, in saved notes, or in a manual that is searched on demand, and defend that choice with a token count.

Your program runs the tool, not the model. The model only writes text that says which tool it wants and with what arguments. The program takes the result and sends it back to the model as new input, and the loop repeats until the model gives a final answer or a limit stops it.

Check your answer

It takes text in and writes text out one token at a time, using patterns learned in training. Nothing in that description includes looking things up or remembering your last conversation. That gap is exactly what context and memory fill.

The context window: everything the model can see 10 min

Start with one request to the makerspace assistant. A student types: "Is the laser cutter free on Friday?" Before the model writes a single word, your program has to assemble what it will read. Here is the whole package for step 1, with made-up but realistic sizes:

PieceWhat it isTokens
Instructions"You are the makerspace assistant. Be brief. Never book without confirming the student's training."500
Tool descriptionscheck_calendar, book_slot, read_manual_page, each with its parameters explained700
The student's message"Is the laser cutter free on Friday?"50
Total the model reads1,250

Now ask: what does the model know about this request? Exactly those 1,250 tokens and nothing else. It does not know Friday's date unless the instructions say so. It does not know who the student is, what happened yesterday, or what the laser cutter manual says. If a fact is not in those tokens, then for the purposes of this step the fact does not exist. Then the model writes its reply, say 60 tokens asking to call check_calendar, and those 60 tokens count too.

That package has a name. The context window is all the text the model can reference when generating a response, including the response itself; it works like the model's working memory, and it is different from the training data the model learned from (Claude API docs, Context windows). The same page is explicit about what counts: the system prompt, every message including tool results, and your tool definitions, plus the output.

Why this works

A model has no connection to the outside world while it writes: its only input is the text handed to it. So whatever you want it to use has to be put into that text. This is why "what does the assistant keep in context?" is a design question you control, not something the model decides.

How big can the window be? It depends on the model. The docs list 1M tokens for the current Claude models and 200k for some older ones, and note that more context is not automatically better. We come back to that in section 2.

The third option. The model's knowledge at any step is the window's contents; a fact that is not in the request cannot be used.

A common mix-up

"The model remembers what I told it." It is tempting because chat apps feel continuous. But the continuity is built by the app, which resends the earlier messages. You will see exactly how in the next section, and it matters for your budget.

Between steps: the history is sent again, every time 12 min

Continue the same request. The model asked to call check_calendar. Your program runs it and gets back a short result of 300 tokens: Friday's laser cutter slots with their status. Now the program must call the model again. Here is a few lines of Python, with a made-up call_model:

messages = [{"role": "user", "content": "Is the laser cutter free on Friday?"}]

# step 1
reply = call_model(instructions, tools, messages)       # reads 1,250 tokens
messages.append(reply)                                   # the tool request, 60 tokens

# the program runs the tool
result = check_calendar("laser cutter", "Friday")
messages.append({"role": "user", "content": result})     # 300 tokens

# step 2
reply = call_model(instructions, tools, messages)       # reads ???

Trace step 2. The model is a fresh call with no memory of step 1, so the program must hand it everything again: instructions 500, tools 700, the question 50, its own earlier tool request 60, and the new result 300. That is 1,610 tokens. Step 1 read 1,250 and step 2 reads 1,610, even though the new information was only 300 tokens, because the old 1,250 and the 60 came along too.

Now say the model needs the laser cutter manual page for the safety rule about Friday's thick-material jobs, so it calls read_manual_page and the page returns 4,000 tokens. Step 3 reads 1,610 + 70 (the new request) + 4,000 = 5,680 tokens. Then the model writes a 150-token answer. Add up what you sent across the three steps:

StepWhat was newTokens read
1Question1,250
2Calendar result (300) and tool request (60)1,610
3Manual page (4,000) and tool request (70)5,680
All steps8,540

The new content across the whole request was about 4,430 tokens. You paid to read 8,540. The difference is the old history being read again. Tokens read are what you pay for and what fills the window, which is why the lesson began with cost.

This pattern has a name. The model is stateless: each call stands alone, and the program keeps the conversation history (the messages list) and sends the whole thing every time. The Claude docs describe it this way: each turn's input is all previous history plus the current message, and the output becomes part of the input for the next turn (Context windows).

Why this works

Because a model call has no memory of its own, the only way the model can "continue" is if the earlier steps are in the text it reads. Your program is the memory between steps; the list messages is where it lives. The price of that design is that every step re-reads everything before it, so a long loop costs far more than the sum of its new facts.

A common mix-up

"A bigger window means I can stop worrying about what goes in." Two problems. First, you pay per token read, and the history is read every step. Second, accuracy gets worse as context grows: the Claude docs call this context rot, and Anthropic's engineering team describes models as having a limited "attention budget" that every added token uses up (Effective context engineering for AI agents). The aim is the smallest set of tokens that still does the job.

More than 10 times, when steps add content. Step 10 re-reads the content from steps 1 to 9 as well, so the tokens read per step grow, and the total grows faster than the step count. The size of tool results drives it most, which leads straight to the next section.

Keeping the window small: clearing old tool results 10 min

Take a longer session. A student asks three questions in a row, and each needs its own manual page of 4,000 tokens: laser cutter, 3D printer, vinyl cutter. Fixed part plus question is 1,250 tokens. For simplicity, ignore the small tool-request messages.

Without any trimming, trace the tokens read when the model composes each answer:

  • Answer 1: 1,250 + 4,000 = 5,250.
  • Answer 2: the first page is still there, so 5,250 + 4,000 = 9,250.
  • Answer 3: 9,250 + 4,000 = 13,250.
  • Total read: 5,250 + 9,250 + 13,250 = 27,750.

But look at what the model needs at answer 3: the vinyl cutter page. The laser cutter page was used to answer question 1, and the answer is already written into the history. It is dead weight. So change one rule in the program: after the model answers, replace each old tool result with a short stub such as [manual page cleared; call read_manual_page again if needed], say 20 tokens, and keep only the newest result in full.

def clear_old_results(messages, keep_last=1):
    results = [m for m in messages if m["kind"] == "tool_result"]
    for m in results[:-keep_last]:
        m["content"] = "[manual page cleared; call read_manual_page again if needed]"

Retrace. Answer 1: 5,250. Answer 2: 1,250 + 20 (stub) + 4,000 = 5,270. Answer 3: 1,250 + 20 + 20 + 4,000 = 5,290. Total: 15,810, against 27,750. That is 43 percent less, from three lines of code, and the third answer is as well informed as before.

This technique is called context editing (here, clearing old tool results): removing content from the history that the model no longer needs, so later steps read less. Anthropic describes clearing old tool results as one of the lightest, safest ways to trim context, and the Claude API offers it as a built-in strategy (Context editing; Effective context engineering).

Why this works

The window is rebuilt from your program's history on every call, so you are free to edit that history between calls. Tool results are usually the biggest items and are often needed for only one step, while the model's own written answer already holds what mattered. Clearing is safe when the data can be fetched again, which is why the stub tells the model how.

There is a heavier cousin called compaction: when the conversation nears the limit, the system summarizes it and continues from the summary. It is for long conversations, where clearing is not enough, and it loses detail, so use it later rather than first (Compaction docs). It is a topic for a later lesson.
Check yourself

The assistant fetched the booking calendar (800 tokens) at the start of a session. Ten minutes later the student asks to move the booking, and the calendar may have changed. If you cleared that old calendar result, what should the program let the assistant do?

Between sessions: notes saved outside the window 13 min

Monday. A student, Dana, chats with the assistant and completes the laser cutter safety training. The assistant's loop runs, and the conversation history grows to a few thousand tokens. The student closes the tab. Thursday. Dana returns and says, "Book me the laser cutter for Friday." The program starts a new request: instructions, tools, and the new message. The messages list from Monday is gone, because it only existed in the program's memory for that session. The assistant, correctly following its own instructions ("never book without confirming training"), asks Dana to prove training status again. The student is annoyed.

Fix it with one new tool and one habit. The tool writes to a file or database that is not the context window:

import json, pathlib

def save_note(student_id, key, value):
    path = pathlib.Path(f"notes/{student_id}.json")
    data = json.loads(path.read_text()) if path.exists() else {}
    data[key] = value
    path.write_text(json.dumps(data))

def load_notes(student_id):
    path = pathlib.Path(f"notes/{student_id}.json")
    return path.read_text() if path.exists() else "{}"

Monday, at the end of training, the model calls save_note("dana", "laser_cutter_trained", "2026-11-09"). The file now holds one line, about 15 tokens. Thursday, the habit: before the first model call, the program runs load_notes("dana") and puts the result into the context, say after the instructions. Trace it. Thursday's step 1 reads instructions 500 + tools 700 + notes 15 + the new message 20 = 1,235 tokens. The model sees "laser_cutter_trained: 2026-11-09" and goes straight to check_calendar. Dana's training status survived the gap, and it cost 15 tokens.

This is memory across sessions, sometimes called agent memory: information the agent saves outside the context window, in a file or database, and loads back in a later session. Anthropic calls the pattern structured note-taking: the agent regularly writes notes persisted outside the context window and pulls them back later; a to-do list or a NOTES.md file are examples (Effective context engineering). Claude's API also has a ready-made memory tool that works on a directory of files you control, with your application running every file operation (Memory tool docs).

Why this works

A session ends when the program drops its history, and the model keeps nothing. Anything that must outlive the session therefore has to live in storage your program owns, and it only influences the model once it is read back into the window. Notes are small because you decide what to write down, instead of keeping the whole transcript.

A common mix-up

"The assistant learned that Dana is trained." Learning would mean the model's weights changed; saving a note changes none. The model is exactly as it was, and it appears to know Dana only because a line of text is placed in front of it. This also tells you what can go wrong: a note can be stale. If the training expires and nobody updates the file, the assistant will keep trusting it, which is the confident outdated answer you have already noticed in chatbots. Give notes a date, as save_note did, and keep facts that change fast, like bookings, in the calendar tool where they are always read fresh.

Finding the right page: retrieval 12 min

The laser cutter manual is 120 pages. At about 800 tokens a page that is roughly 96,000 tokens, and the assistant has several manuals. Putting everything into the window every step would cost a lot per request (section 2) and bury the answer (context rot). The student only asks: "What speed should I use to cut 3 mm acrylic?"

Do it by hand with four tiny manual chunks, each a paragraph a program has already cut from the manual:

ChunkText (shortened)
ALens cleaning: wipe the lens with isopropyl alcohol weekly.
BCutting 3 mm acrylic: set speed to 20 mm/s and power to 60 percent.
CEngraving wood: set speed to 300 mm/s and power to 30 percent.
DCutting 6 mm acrylic: set speed to 10 mm/s and power to 80 percent.
 
def score(question, chunk):
    q = set(question.lower().split())
    c = set(chunk.lower().split())
    return len(q & c)          # how many words they share

def retrieve(question, chunks, k=2):
    ranked = sorted(chunks, key=lambda c: score(question, c), reverse=True)
    return ranked[:k]

Trace it for "what speed should i use to cut 3 mm acrylic". The program splits on spaces, so "acrylic:" with its colon does not match "acrylic", and "cut" does not match "cutting". Shared words: A has none (score 0). B shares "3", "mm", "speed" and "to": 4. C shares "speed" and "to": 2. D shares "mm", "speed" and "to": 3, because its "6" does not match the question's "3". Ranking: B (4), D (3), C (2), A (0). With k=2 the program puts B and D into the window: about 40 tokens instead of 96,000. The model reads B, sees 20 mm/s and 60 percent, and answers; D is a close neighbour that did no harm here. Notice that even this toy was helped by the filler word "to": a sign of how crude word counting is.

That whole move is retrieval: searching a large store for the few pieces most relevant to the current question and placing only those in the context window. Using it to ground a model's answer is often called retrieval-augmented generation (RAG). Real systems score by meaning (embeddings) or a mix of methods rather than shared words, but the shape is the same: score, rank, take the top few (Anthropic, Contextual Retrieval). Anthropic also describes a second style, where the agent keeps light references like file paths and loads data itself at runtime with tools, and notes that the two are often combined (Effective context engineering).

Why this works

The window is a small, costly space, and the manual is large and mostly irrelevant to any one question. Retrieval spends a cheap search outside the window to choose what deserves space inside it. The model still does the reading and writing; the search decides what it gets to read.

A weakness to know about: when a manual is cut into chunks, a chunk can lose its context. A chunk saying "set speed to 20 mm/s" no longer says which machine or material. Anthropic's Contextual Retrieval prepends a short explanation to each chunk before indexing, and reports it cut failed retrievals from 5.7% to 2.9% in its tests when combined with keyword search (source). Treat the figures as one vendor's test, not a promise for your manuals.

Worked example and practice 8 min

Worked example

Decide where each of these five things lives in the makerspace assistant: (1) "Never book without confirming training", (2) Dana's laser cutter training date, (3) the safety rules in the 3D printer manual, (4) Friday's open slots on the laser cutter, (5) the result of the calendar lookup from five steps ago.

  1. Ask of each: is it needed on every step, needed across visits, large and mostly irrelevant, or short-lived? Item 1 is needed on every step and small, so it goes in the instructions, which are part of the window every time (section 1).
  2. Item 2 must survive the session and is tiny, so it is a note, saved outside the window and loaded at the start (section 4).
  3. Item 3 is a few pages from a manual of 100, relevant only to some questions, so it is retrieved when a question needs it (section 5).
  4. Item 4 changes constantly and a copy goes stale, so it is fetched with the calendar tool at the moment it is needed, not stored.
  5. Item 5 is an old tool result that has already served its purpose, so it is a candidate for clearing, with the tool available to refetch (section 3).

Cost check: instructions are paid on every step. Notes cost a few tokens per session. Retrieval costs about two chunks per question, never the whole manual. So the only parts that grow without limit are tool results, and that is where clearing earns its place.

Summary 4 min

  • The context window is everything the model can see for a call: instructions, tool descriptions, history, tool results and its own output. If a fact is not in it, the model cannot use it.
  • Between steps, the program keeps the history and resends all of it every call. Cost and window use grow faster than the amount of new information, and long contexts also degrade accuracy.
  • Clearing old, re-fetchable tool results is the lightest way to keep the window small.
  • Between sessions nothing survives unless you save it: notes in storage outside the window, loaded into the next one. A note is small, dated, and can go stale.
  • For long manuals, retrieval searches outside the window and places only the top few chunks inside it.
