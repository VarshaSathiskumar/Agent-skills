Context and memory in an agent

Why this matters for you

Warm-up 3 min

Before new material, recall what you already know about the loop. Answer in your head, or write it down, and then open the answer.

Recall

A student asks, “Is the laser cutter free on Friday?” Write the steps the agent loop takes, in order, until the student gets an answer. Who runs the calendar lookup: the model or your program?

Check your answer

The model is called with the question and the tool list. It replies with a request to use the calendar tool. Your program runs the lookup, because the model only writes text. The result goes back to the model in a new call, and the model writes the final answer.

Notice the phrase “a new call”. Each step is a separate model call. Today's question is what each of those calls contains, and what survives after the last one.

What the model sees: the context window 6 min

Start with one model call from the makerspace assistant, written out in full. This is everything the model receives for the first step of the Friday question, with rough token counts:

[system prompt]   "You are the makerspace assistant. Answer from the
                   manuals. Book equipment only for trained students."   500 tokens
[tool list]       check_calendar(machine, date), book(machine, slot),
                  search_manual(machine, question)                       600 tokens
[student message] "Is the laser cutter free on Friday?"                   30 tokens
                                                                  total  1,130 tokens

That block is all the model has. It does not know the student's name, what was asked yesterday, or what is in the manual, unless one of those is in the block. If a fact is not in the text the model receives for this call, then for this call it does not exist.

The text has a ceiling. Suppose a model accepts 200,000 tokens in one call, and one laser-cutter manual is 300,000 tokens. The whole manual cannot be placed in the block, however you arrange it. Even a manual that fits would take space and money on every call, as the next section shows.

What you just traced has a name. The context is the set of tokens given to the model when it generates a reply, and the context window is the maximum number of tokens it can take in one call, input and output together (Claude API docs: context windows; Anthropic: effective context engineering). Everything the assistant “knows” at one step is whatever you chose to put there.

Why this works

The model has no hidden store of facts about your conversation. Its reply is computed from the tokens it is handed, so the only way to change what it knows right now is to change those tokens. That is why context is the thing you design, and why it is limited: the window is a fixed size, and every token in it also adds cost.

Check yourself

A student told the assistant yesterday, “I'm allergic to the resin in the 3D printer lab.” Today the student asks for a printer slot, and the call contains only the system prompt, the tools and today's message. What will the model do about the allergy?

Show the answer

The third option. The model computes its reply from this call's tokens only, and the allergy is not among them.

What is kept between steps 6 min

Now follow the whole Friday question through three model calls, and count what is sent each time. Your program, not the model, keeps a list called messages and sends the whole list on every call.

messages = [system, tools, "Is the laser cutter free on Friday?"]   # 1,130 tokens

# Call 1: send 1,130 tokens.
#   Model replies: tool request check_calendar("laser", "Fri")  -> +60 tokens
messages.append(model_reply)

# The program runs the lookup and appends the result.
messages.append(calendar_result)                                 # +400 tokens

# Call 2: send 1,130 + 60 + 400 = 1,590 tokens.
#   Model replies: tool request search_manual("laser", "booking rules") -> +50
messages.append(model_reply)
messages.append(manual_page)                                     # +2,000 tokens

# Call 3: send 1,590 + 50 + 2,000 = 3,640 tokens.
#   Model replies: final answer (150 tokens)

Add up what was sent: 1,130 + 1,590 + 3,640 = 6,360 input tokens, for a conversation whose longest call was 3,640. The first 1,130 tokens were sent three times. The manual page, added late, was sent once, but if the loop ran a fourth step it would be sent again, and again after that.

Nothing was kept inside the model between calls. What carried the earlier steps forward was the list your program re-sent.

That list has a name. The conversation history (here, the list of messages, tool requests and tool results so far) is the only thing kept between steps, and it is kept by your code, which re-sends it in full with each call. Because it only grows, the context grows with every step, and so does the input you pay for (Anthropic: effective context engineering).

Why this works

Each call is independent: the model starts fresh and reads whatever text arrives. To make step 3 “remember” step 1, step 1 has to be in step 3's input. This is why long tool outputs are expensive in an agent: a 2,000-token manual page is paid for on every later step, not once.

Anthropic's article describes the consequence of growth as “context rot”: as the context gets longer, the model's recall of details in it tends to get worse, so a bigger window is not a reason to fill it. When a history nears the limit, one remedy is compaction, replacing old steps with a summary. You do not need it for short requests like these.
A common mix-up

“The model keeps its place between steps, so only the new result needs sending.” It is tempting because a chat feels like a continuing conversation. But the trace above shows the model re-reads everything each time. If your program sent only the calendar result on call 2, the model would not know the question was about Friday.

Check yourself

Suppose call 3 above, which sent 3,640 tokens, had ended in a booking request of 50 tokens instead of a final answer. The booking tool returns a 100-token confirmation, and the loop makes a call 4. How many tokens does call 4 send?

Show the answer

3,790. Call 3 sent 3,640. The model's new request (50) and the tool result (100) are appended, and the whole list goes again.

What is kept between sessions: notes 7 min

Riley finishes laser-cutter training on Monday. On Thursday Riley opens a new chat and asks to book the laser cutter. A new session starts with an empty history, so the model sees a system prompt, tools and one message, and has no idea about Monday.

The fix is a small file the program writes and reads. Here is the whole idea in a few lines of Python:

import json, pathlib

def load_notes(student_id):
    path = pathlib.Path(f"notes/{student_id}.json")
    return json.loads(path.read_text()) if path.exists() else {}

def save_note(student_id, key, value):
    notes = load_notes(student_id)
    notes[key] = value
    pathlib.Path(f"notes/{student_id}.json").write_text(json.dumps(notes))

Trace two sessions:

  1. Monday. A staff member confirms training. The program calls save_note("riley", "laser_trained", True). The file notes/riley.json now holds {"laser_trained": true}. Then the session ends and its history is thrown away.
  2. Thursday, start. A new history begins. Before the first call, the program runs load_notes("riley") and adds one line to the system prompt: “Student notes: laser_trained = true.” That is about 10 tokens.
  3. Thursday, the request. The model sees the note in its context, and can book. If instead the file said false, the model would see that and refuse.

The history from Monday is gone. The one fact that mattered survived, as ten tokens.

What the file did has a name. Notes (also called persistent or agentic memory) are information the agent or its program writes to storage outside the context window, and reads back into the context in later sessions or later steps (Anthropic: structured note-taking). Memory between sessions is not a model feature here: it is a file, written and loaded by your code.

Why this works

Because the model only reads what is in its context, any fact that must outlive a session has to be stored somewhere that is not the context, and then copied in when needed. Storing a short fact rather than the whole old chat keeps the new context small, so the cost stays low.

A common mix-up

“Just keep the old chat and re-send it next session.” It is tempting because it needs no new code. But a month of chats per student would fill the window and be paid for on every call, and most of it is irrelevant. The note holds the fact that matters, and nothing else.

Check yourself

Which of these should the assistant write to the student's notes file so it is available next week?

Show the answer

The training status. It is lasting, small and not available from another tool. Availability can be looked up again, and the transcript is too large.

Finding the right page: retrieval 7 min

The laser cutter manual is far larger than you want in every call. A student asks, “What focus height should I use for 3 mm acrylic?” Here is a toy version of the manual, split into three chunks (pieces of a few paragraphs each), and a search that scores each chunk by how many question words it shares:

chunks = {
  "c1": "Cleaning the lens: use isopropyl alcohol and a lint-free cloth.",
  "c2": "Focus height: for 3 mm acrylic set the focus height to 6 mm.",
  "c3": "Booking rules: trained students may book up to 2 hours per day.",
}

def search(question, k=1):
    q = set(question.lower().replace("?", "").split())
    scored = [(len(q & set(text.lower().replace(":", "").replace(".", "").split())), id)
              for id, text in chunks.items()]
    return [id for score, id in sorted(scored, reverse=True)[:k]]

Trace the question “what focus height should i use for 3 mm acrylic?”:

  1. The question words are what, focus, height, should, i, use, for, 3, mm, acrylic.
  2. c1 shares none. c3 shares none. c2 shares focus, height, for, 3, mm and acrylic: a score of 6.
  3. search returns ["c2"]. The program appends only that chunk, about 30 tokens here, to the context as a tool result.
  4. The model answers “6 mm” from text that is now in front of it.

The model never saw the cleaning or booking chunks. Only the page that mattered was paid for.

This has a name. Retrieval is searching a store of documents for the few pieces relevant to the current question and putting only those into the context (Anthropic: contextual retrieval). In your assistant it is a tool, search_manual, that the model calls like any other. Anthropic notes that a knowledge base under about 200,000 tokens can simply be put in the prompt, and that retrieval is for what does not fit.

Why this works

The context is small and billed per token, while the manuals are large and rarely needed in full. Searching first turns a 300,000-token problem into a 30-token one, and the model still reads real manual text instead of guessing from training. The risk moves to the search: if it returns the wrong chunk, the model answers from the wrong page.

Real systems score chunks with better methods than shared words, such as embeddings and BM25 keyword ranking. Anthropic's post reports that adding context to each chunk before indexing reduced failed retrievals. A later lesson can cover how to score; here the point is where retrieval sits.
Check yourself

A student asks, “Can I book the laser cutter for 3 hours?” The toy search above scores only shared words, and the stored chunk reads “trained students may book up to 2 hours per day.” Which statement about this case is true?

Show the answer

The first option. The question shares “book” and “hours” with the booking chunk, and nothing with the others, so it ranks first and is the only one returned.

Worked example and practice 8 min

You now have three places where information can live. This task puts them together, the way you will in your design review.

Worked example

Decide where each item lives: (a) the system prompt text “book only for trained students”; (b) Sam's status “trained on the band saw”; (c) the band saw manual, 150,000 tokens.

  1. Ask: is it needed on every call, and is it small? Item (a) is, at about 15 tokens. It goes in the context from the start. Cost: 15 tokens per call.
  2. Ask: does it outlive the session, and is it a lasting fact? Item (b) is. It goes in notes, and the program loads the one line into the context at the start of each session. Cost: about 10 tokens per call.
  3. Ask: is it large, and needed only for some questions? Item (c) is. It goes into a searchable store and a tool brings in the one relevant page, about 2,000 tokens, on the calls that need it. Putting all 150,000 tokens in the context would cost 150,000 tokens on every call, and the history would re-send them on every later step.
  4. Check the cost. A 3-call request with the manual in context sends about 450,000 manual tokens in total. With retrieval it sends 2,000 once on call 2 and again on call 3: 4,000.

Show a solution

Stretch

A sponsor asks: “Why not just give the assistant a bigger window and put everything in it?” Give two reasons from this lesson.

Show a solution

First, cost: every token in the context is re-sent and paid for at each step, so a large fixed block multiplies across steps. Second, quality: Anthropic's article reports that recall of details declines as the context grows (context rot), so more is not automatically better. A third reason also applies: a window is still finite, and a growing history will reach it eventually.

Summary 2 min

  • The model sees only the context of the current call: system prompt, tools, and history. The context window is its size limit.
  • Between steps, your program re-sends the whole history, so context and cost grow at every step.
  • Between sessions, nothing survives unless you save it: notes are a store outside the context, loaded back in as short facts.
  • For large documents, retrieval brings in only the chunk that matches the question.
