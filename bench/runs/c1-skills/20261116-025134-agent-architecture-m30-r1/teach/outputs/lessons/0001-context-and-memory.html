Context and memory in an agent

By the end of this lesson you can say, for any piece of information in the makerspace assistant, whether it belongs in the context, in saved notes, or in a searchable manual, and why.

The context window 6 min

Here is a request to the makerspace assistant, with invented token counts to keep the arithmetic easy. A token is a small chunk of text, roughly three-quarters of a word. Suppose our toy model can read at most 2,000 tokens in one call. Your program builds the call like this:

system_prompt   = 300   # "You are the makerspace assistant. Rules: ..."
tool_definitions = 400  # names, descriptions, arguments of 3 tools
student_question = 20   # "What speed do I use to cut 3 mm acrylic?"
manual_pages    = 1500  # pasted laser cutter manual, pages 12-18
total           = 300 + 400 + 20 + 1500 = 2220   # limit is 2000

The total is 2,220. It does not fit. The model cannot read the call at all, or the provider rejects it. To make it fit you must drop 220 tokens: perhaps paste four pages of the manual instead of seven.

Notice what the model needed: all four parts in one place, because the model can only use what is in that single call. It has no other view of your system prompt, your tools, or the manual.

That single space has a name. The context window is all the text the model can look at when it writes its next output, including the system prompt, tool definitions, the conversation so far and the output it is writing; its size is measured in tokens (Claude API docs: context windows). Real windows are much bigger than our toy: the same page lists up to 1 million tokens for recent models. Bigger is not free, as sections 2 and 5 show.

Why this works

A model has no connection to your files, database or earlier calls. Each call is only text in and text out, so anything it should use has to be written into that text. The window is the size limit on that text.

A student asks about a 3D printer, and you want the model to know the printer's safety rules. The rules live in a file on your server. How does the model get them?

The third option. The model sees only the text your program sends; the file is invisible until your program pastes it in.

What is kept between steps 6 min

Now run the loop for one request, with the same invented numbers. The student asks: "Can I use the laser cutter Friday, and what speed for 3 mm acrylic?" The program keeps a Python list called messages and sends all of it every time.

messages = [question]                  # system + tools + question = 720 tokens
reply = call_model(messages)           # CALL 1: model reads 720 tokens
                                       #   outputs: tool request check_calendar (30)
messages += [reply, calendar_result]   # + 30 + 200  -> 950 tokens
reply = call_model(messages)           # CALL 2: model reads 950 tokens
                                       #   outputs: tool request search_manual (30)
messages += [reply, manual_page]       # + 30 + 1500 -> 2,480 tokens
reply = call_model(messages)           # CALL 3: model reads 2,480 tokens
                                       #   outputs: the final answer

Trace the calls. Call 2 does not start from only the calendar result: it reads the system prompt, the tools, the question, its own earlier request and the result. Call 3 reads all of that plus the manual page. The model does not remember call 1; it re-reads it, because your program included it.

Now add up what the model read: 720 + 950 + 2,480 = 4,150 tokens, although the longest single call was 2,480. Providers charge for the input tokens of every call, so a long loop pays for the early messages many times.

What was kept between steps is a plain list in your program's memory. The model kept nothing. This has a name: the conversation history (or message history) is the list of earlier messages and tool results that your program re-sends on each call, so that each step can build on the last. This is how an agent seems to remember within a single task (Anthropic: effective context engineering describes the context as the tokens passed to the model on each call, and the agent loop as curating them over time).

Why this works

Each model call is independent, so continuity has to come from the program. The list is the continuity. That is also why you control it: whatever is not in the list on the next call does not exist for the model.

A common mix-up

"The model remembers what happened in the earlier steps." It is tempting because the chat feels continuous. But in the trace above, if your program forgot to append the calendar result, call 2 would behave as if the calendar was never checked, and might call the tool again.

Check yourself

A request takes 4 model calls. The system prompt and tool definitions together are 700 tokens, and nothing is ever removed. Which statement about cost is true?

Show the answer

The third option: 4 calls × 700 = 2,800 tokens for the fixed part alone. That is why short system prompts and tool descriptions matter for your budget.

Nothing is kept between sessions: notes 6 min

On Monday, Riley asks the assistant for the laser cutter and the assistant checks the training status: passed the safety course on 2 October. The program ends. On Wednesday, Riley opens a new chat. Here is what the program does:

# Wednesday, new session
messages = [question]          # a fresh list: system + tools + "Book the laser cutter"
# Monday's messages list was a variable; it vanished when the program exited.
# The model is asked: "Is this student trained?"  It has no way to know.

The assistant would ask for the training status again, or worse, guess. The history from section 2 lived in a Python variable, so it died with the session.

The fix is to write something down outside the program, then read it back. A small version:

import json

def save_note(student, key, value):          # a tool the model can call
    notes = json.load(open("notes.json"))
    notes.setdefault(student, {})[key] = value
    json.dump(notes, open("notes.json", "w"))

def start_session(student):
    notes = json.load(open("notes.json"))
    return "Known about this student: " + str(notes.get(student, {}))

# Monday:  model calls save_note("riley", "laser_training", "passed 2 Oct")
# Wednesday: start_session("riley") returns
#   "Known about this student: {'laser_training': 'passed 2 Oct'}"
# and that line goes into the new context at the start.

Trace Wednesday: the program loads notes.json, finds Riley's entry, and puts one short line into the fresh context. The model now answers without asking again. Only that line came back; the whole Monday conversation did not.

The name for this: notes as memory (Anthropic calls it structured note-taking, or agentic memory) is when the agent writes information to storage outside the context window and loads it back into the context later (Anthropic: effective context engineering). The storage can be a file, a database row, or anything your program can read.

Why this works

The context is rebuilt from scratch every session, so anything that must survive has to live somewhere that survives: a file or a database. The model decides what is worth writing; the program does the saving and the loading. Because only a few lines are loaded, the context stays small and cheap.

What to save is a design decision. A training status is worth a note. The whole chat transcript usually is not: it is long, and loading it again costs tokens on every call.

Finding the right page: retrieval 7 min

Back to the manual problem from section 1. The real laser cutter manual is 200 pages, far past any toy window and expensive even in a large one. You only need the page about acrylic. A tiny version, with four chunks (pieces of the manual) and a score that counts shared words:

chunks = {
  "p12": "acrylic cutting speed 3 mm use 20 percent power 80",
  "p31": "wood engraving focus distance and bed height",
  "p47": "exhaust fan must run when cutting any plastic",
  "p58": "cleaning the lens weekly with isopropyl alcohol",
}
query = "speed for cutting 3 mm acrylic".split()

def score(text):  return len(set(query) & set(text.split()))
# p12 shares: speed, cutting, 3, mm, acrylic  -> 5
# p31 shares: (none)                           -> 0
# p47 shares: cutting                          -> 1
# p58 shares: (none)                           -> 0
best = sorted(chunks, key=lambda k: score(chunks[k]), reverse=True)[:2]
# best = ["p12", "p47"]  -> only these ~2 chunks go into the context

Trace it: the question is turned into a query, every chunk gets a score, the top two are put in the context, and the model answers from them. The context holds two short chunks instead of 200 pages, and the model never saw the other pages.

This is retrieval: searching a large store of text for the few pieces relevant to the current question and adding only those to the context. When the model then answers from them, the pattern is often called retrieval-augmented generation, or RAG (Anthropic: Introducing Contextual Retrieval). Real systems use better scoring than word counts, but the shape is the same: chunk, score, take the top few.

Why this works

Most of a manual is irrelevant to any one question. Searching first means the model reads only what matters, which keeps the window free for the conversation and keeps the cost per request low. The same Anthropic post notes a shortcut: if the knowledge base is under about 200,000 tokens, you can just put all of it in the prompt.

A common mix-up

"A chunk is always understandable on its own." Look at p12: it never says "laser cutter". If your manual covers several machines, a chunk saying "use 20 percent power" could belong to any of them, and a search could return the wrong machine's page. Anthropic's fix, contextual retrieval, is to prepend a short note about where the chunk came from before indexing it (same post). For you, a first step is to put the machine name in every chunk.

Check yourself

With the scoring above, a student asks "how do I clean the lens?" What happens, and what does it tell you?

Show the answer

Only "lens" matches (and "the" if it appeared). "clean" does not match "cleaning". The right page still ranks first here, but narrowly, which shows why exact word matching is a weak search.

Keeping the context lean 4 min

Return to the trace in section 2. After call 3 the model wrote its answer, but suppose the student now asks a follow-up: "And what about 5 mm?" The context already holds 2,480 tokens, and 1,500 of them are the manual page about 3 mm. Your program has a choice:

before = 720 + 30 + 200 + 30 + 1500 + answer(150) = 2,630 tokens
# Option: replace the 1,500-token page with a stub once the answer is written
stub   = "[manual page p12 was here; search again if needed]"   # ~15 tokens
after  = 2,630 - 1500 + 15 = 1,145 tokens
# Next call (follow-up question 20 tokens) reads 1,165 instead of 2,650.

Trace it: the big tool result has done its job, so the program swaps it for a one-line stub. The next call is about 1,500 tokens cheaper, and if the model needs the page again, it can retrieve it again.

This is a form of compaction: shrinking the context as it fills, either by clearing old tool results or by summarizing the conversation so far and starting a new window from the summary. Anthropic calls clearing old tool results one of the safest, lightest-touch forms of it (Anthropic: effective context engineering).

Why this works

Cost is paid on every call, and quality suffers when the window fills: Anthropic describes "context rot", where the model's ability to recall information from the context drops as the number of tokens rises. Removing content that is no longer needed helps both, and retrieval makes removal safe because the content can be fetched again.

Worked example and practice 6 min

Worked example

Decide where each piece of information for the makerspace assistant lives: context only, saved note, or retrieval from the manuals. Take: "Riley's safety-course date".

  1. Ask: is it needed after this session ends? Yes, Riley will return next week. So it cannot live in the context alone.
  2. Ask: is it a small fact about one student, or a large shared document? A small fact about one student, so a saved note, not retrieval.
  3. Ask what loads it back. At session start the program reads Riley's note and adds one line to the new context.

Answer: saved note. Compare "the laser cutter's speed for acrylic": needed by every student, long, and shared, so it is retrieved from the manual. And "what check_calendar just returned": needed only for this request, so it stays in the context and may be cleared later.

Summary 2 min

  • The model sees only the context window: the text your program sends on this call.
  • Between steps, your program keeps the message list and re-sends it every call, so cost and length grow.
  • Between sessions, nothing survives unless saved: notes in a file or database, loaded back at the start.
  • For long documents, retrieval finds a few relevant chunks and adds only those; compaction clears what is no longer needed.
