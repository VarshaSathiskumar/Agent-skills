Context and memory in an agent: what the model sees, and what survives

By the end of this lesson you can look at one request to the makerspace assistant and say, for every piece of information, whether it sits in the model's context, gets saved between sessions, or gets fetched from a manual on demand.

Objective O3: context and memory in an agent About 60 minutes Builds on your notes on the agent loop (learning record 0002)
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small model budget. Those are three separate design decisions: what stays in context, what gets saved, and how it finds the right page. This lesson gives you the vocabulary and a method to make and defend each one at your design review.

Warm-up 3 min

You already know the agent loop: the model asks for an action, the action runs, the result comes back, and this repeats. Two quick recall questions before we look inside that loop. Answer in your head or on paper first.

Recall 1

In the loop, what actually runs a tool such as "check the booking calendar": the model or your program?

Check your answer

Your program. The model only writes a request that names the tool and its inputs; your code runs it and sends the result back. That detail matters today, because it means your program, not the model, is in charge of what the model gets to see next.

Recall 2

When a tool result comes back, how many separate model calls has the request used so far if the model has asked for two tools and then given its final answer?

Check your answer

Three. Every trip around the loop is a separate call to the model. Hold on to that number: in section 2 you will see why it makes long requests expensive.

1. The context window 8 min

A student types: "What's the maximum acrylic thickness for the laser cutter?" Your assistant has to make one model call. What do you actually send? Here is the request as a Python dict, the way you will soon write it:

request = {
    "system": "You are the makerspace assistant. Be brief. "
              "Only answer from the manuals. Book equipment with the tools.",
    "tools": [search_manual_definition, check_calendar_definition, book_slot_definition],
    "messages": [
        {"role": "user", "content": "What's the maximum acrylic thickness for the laser cutter?"}
    ],
}

Now count what the model can use to write its answer. Step by step:

  1. The system prompt: about 100 tokens, say.
  2. The three tool definitions (names, descriptions, input formats): about 1,400 tokens, since each description is a paragraph.
  3. The student's question: about 15 tokens.
  4. The answer the model is about to write: it also takes up room, as it is written.

Everything in that list is all the model has. It has no access to the manuals unless you put text from them in the request, and no access to yesterday's conversation unless you put it in. (The numbers are round figures for illustration; real counts depend on the model's tokenizer.)

That whole collection has a name: the context window is all the text a model can refer to when it writes a response, including the response itself. The Claude documentation compares it to a "working memory" and notes it is different from the large body of text the model was trained on (Claude docs: Context windows). It counts the system prompt, every message including tool results, and your tool definitions, and it has a fixed maximum size measured in tokens. The docs list up to 1 million tokens for recent models, but check the current table for whichever model your team picks.

Why this works

A model can only condition on the tokens it is handed in this call. It stores nothing between calls, so whatever it needs, whether a manual page, a rule or a tool, has to be in the request. That is why you, as the designer, control the model's knowledge in the moment: you choose what goes into the window.

Check yourself

A student asks about the band saw. Your assistant's request contains the system prompt, the tools and the question. The band saw manual is stored on your server but is not in the request. What can the model say about the manual's content?

Show the answer

The third option. The window is the model's whole world for the call; a file on your server is outside it until a tool fetches the text and the result is added.

Extra practice: estimate a window

Your assistant has a system prompt of 300 tokens and four tools described in 400 tokens each. A student's question is 40 tokens, and the model's planned reply is 150 tokens. Add up what the window must hold for this one call, then say which part you could shrink most easily to save money, and how.

Show the answer

300 + 4 × 400 + 40 + 150 = 2,090 tokens. The tool definitions are the biggest block at 1,600, and they are resent on every call. Shorter, sharper tool descriptions (or loading only the tools a request needs) saves tokens on every call. Anthropic's context guide makes the same point: tools should be token-efficient and easy to choose between (Anthropic: Effective context engineering for AI agents).

2. What is kept between steps 9 min

Now run the full request for the laser-cutter question and watch the context at each model call. The assistant has a tool search_manual(query). The numbers are made up but realistic in shape.

  1. Call 1. Input: system prompt and tools (1,500 tokens) plus the question (50) = 1,550. The model replies with a request to run search_manual (60 tokens of output).
  2. Your program runs the search. It returns a manual page of about 900 tokens.
  3. Call 2. The model is a fresh call. It remembers nothing of call 1, so your program sends everything again, plus the new items: 1,550 + the model's 60-token request + the 900-token result = 2,510 tokens in. The model replies with a second tool request, this time check_calendar (70 tokens).
  4. The calendar returns 400 tokens.
  5. Call 3. Input: 2,510 + 70 + 400 = 2,980. The model writes the final answer (80 tokens).

Add up the input of all three calls: 1,550 + 2,510 + 2,980 = 7,040 input tokens, though the conversation itself only ever held about 3,060 tokens. The early items were sent, and paid for, again on every call after them. Here is the loop in code; the key line is the one that appends to messages:

messages = [{"role": "user", "content": question}]
while True:
    reply = call_model(system, tools, messages)       # sends ALL of messages
    messages.append({"role": "assistant", "content": reply.content})
    if reply.stop_reason != "tool_use":
        break                                          # final answer
    result = run_tool(reply)                           # your code runs it
    messages.append({"role": "user", "content": result})  # kept for next call

The list messages is the only thing carrying information from one step to the next. This is the conversation history your program keeps: every model call is independent, and the only reason call 3 "knows" what call 1 asked is that your program sent it again. The Claude docs describe the same pattern: each turn's input holds all previous history plus the new message, and each response becomes part of the next input (Claude docs: Context windows).

Why this works

The model does not change between calls, so it has no way to remember. Memory inside a single request is an illusion your program creates by resending the transcript. This also means cost grows faster than the conversation itself: the longer the history, the more input tokens every further call pays for.

A common mix-up

"The model remembers what it did in the earlier steps." It is tempting because the final answer clearly uses earlier results. But that is your messages list at work: delete the appended search result and call 3 would have no idea what the manual said.

Check yourself

Another request runs four model calls. The first call has 2,000 input tokens, and each tool result you append adds 1,000 tokens (ignore the model's own short outputs). What is the total input across all four calls?

Show the answer

14,000. The calls see 2,000, 3,000, 4,000 and 5,000 tokens of input, because each includes everything before it. The second option is the trap: it treats each result as paid for once.

Extra practice: trace the history

Take the code in section 2. A request runs two tool calls and then a final answer. Write down, in order, what messages contains just before call 3 (use short labels like "user: question"), and say which single line of code would break the assistant's "memory" if you deleted it.

Show the answer

Before call 3: (1) user: question; (2) assistant: first tool request; (3) user: first tool result; (4) assistant: second tool request; (5) user: second tool result. Deleting the line that appends the tool result to messages means the model never sees what the tool returned and cannot use it; deleting the assistant append means it forgets what it asked for. Either way, nothing is kept except what you append.

3. Context rot: more is not better 9 min

Suppose a student plans a project and your assistant works through twelve tool calls: it searches the laser cutter manual, the 3D printer manual and the vinyl cutter manual, checks three calendars, and so on. Each manual page is about 900 tokens and every page stays in messages. By call 13 the context holds roughly 11 manual pages, about 10,000 tokens of text that mostly has nothing to do with the student's current question: "So what was the max acrylic thickness again?"

Now picture the answer. The relevant sentence ("maximum acrylic thickness is 6 mm") is there, but it is one line among thousands. A plausible failure: the model confidently answers with a number from the 3D printer page, say a different "maximum" that sat nearer the end. Nothing crashed, no error was raised; the answer was just wrong, and the only difference from a short conversation is the clutter. (This is an illustrative scenario, not a measurement from your assistant. You will want to test your own, but the effect is documented.)

That effect is called context rot: as the number of tokens in the window grows, the model's accuracy and recall of what is in it degrade. The Claude docs put it plainly: "more context isn't automatically better," so curating what is in context matters as much as how much room there is (Claude docs: Context windows). Anthropic's engineering team explains it with an "attention budget": models draw on a limited budget when reading a large context, and every new token uses some of it (Anthropic: Effective context engineering for AI agents). Their goal for builders is the smallest set of high-signal tokens that gets the job done.

Why this works

The model weighs every token in the window against every other when it writes each new word, and that attention is finite. Adding ten irrelevant pages does not just waste money; it dilutes the weight the one relevant sentence gets. A big window sets the upper limit on what fits, not how much works well.

A common mix-up

"The window holds a million tokens, so I can put all the manuals in and skip the design work." It is tempting because it removes a hard problem. But you would pay for those tokens on every call (section 2) and the answers would get worse (this section). The window size is a ceiling, not a target.

Check yourself

Your assistant answers well for the first five messages, then starts mixing up the equipment rules after twenty messages of tool results. Nothing is over any size limit. Which explanation fits best?

Show the answer

The third option. Overflow is an explicit error, and training is frozen. Degraded recall in a long but legal context is exactly context rot.

4. Compaction: making room 9 min

You decide the assistant's context should never pass 3,000 tokens. At call 8 the history reaches 3,400 tokens: a system prompt, a long exchange about booking, three manual pages. A small function tidies it before the next call:

def compact(messages, limit=3000):
    if count_tokens(messages) <= limit:
        return messages                      # nothing to do yet
    old, recent = messages[:-2], messages[-2:]
    summary = call_model(
        "Summarize this conversation. Keep: the student's goal, "
        "decisions made, bookings made, and any numbers they need.",
        old)
    return [{"role": "user", "content": "Summary so far: " + summary}] + recent

Trace what happens at call 8:

  1. count_tokens returns 3,400, which is over 3,000, so the function does not return early.
  2. It splits off the last two messages as recent and everything before as old.
  3. It asks the model (a separate call) for a short summary of old, say 250 tokens: "Student wants to cut 5 mm acrylic on Saturday. Laser cutter max acrylic is 6 mm. Booked 2 pm Saturday."
  4. The new history is that summary plus the two recent messages: about 250 + 400 = 650 tokens. The three full manual pages are gone.

That is compaction: when a conversation nears the limit, summarize its contents and start the next window from the summary. Anthropic's engineering post defines it this way, and says the art lies in choosing what to keep and what to discard (Anthropic: Effective context engineering for AI agents). The Claude docs also describe server-side compaction as a managed option for long-running agents, in beta at the time of writing (Claude docs: Context windows).

Why this works

Most of what is in a long history was needed once and is dead weight now: the full text of a page that produced one number. A summary keeps the decisions and results and drops the bulk, trading a little detail for a lot of room and sharper attention. The risk is the same trade in reverse: whatever the summary leaves out is gone from this conversation for good.

Compaction costs one extra model call each time it runs, so it pays off when the tokens it removes would have been resent on many later calls.
Check yourself

Your compact prompt only says "Summarize this conversation." After compaction, the assistant forgets which Saturday slot the student already booked and offers to book it again. What is the most direct fix?

Show the answer

The third option. The failure came from a summary that dropped something important; the fix is to say what must survive. The first two options avoid the problem instead of fixing it.

Extra practice: write the summary prompt

Your assistant helps a student plan a three-machine project over a long chat. Write the instruction you would give the summarizer so that a later call can still book the right slots and respect the machine limits. List at least four things it must keep and two it can drop.

Show a sample answer

Keep: the student's project goal; which machines they need; bookings already made, with times; limits that affect the plan (for example, maximum material thickness); anything the student asked not to do. Drop: greetings, the full text of manual pages already used to extract a number, and failed searches. The test of a good prompt is whether a call that sees only the summary could carry on without asking the student to repeat anything.

5. Notes: memory between sessions 10 min

Dana, a student, spends Monday's session finishing laser cutter safety training. Your assistant confirms it. Dana closes the app. On Thursday Dana opens it and asks to book the laser cutter. This is a brand new session: messages starts as an empty list, because a list in a running program does not survive the program closing. The assistant has no idea Dana did the training, and asks again, or worse, refuses.

The fix is to write the fact down outside the context window and read it back at the start of the next session. A small version, with a JSON file:

import json

def save_note(student_id, key, value):
    notes = json.load(open("notes.json"))
    notes.setdefault(student_id, {})[key] = value
    json.dump(notes, open("notes.json", "w"))

def start_session(student_id):
    notes = json.load(open("notes.json")).get(student_id, {})
    system = BASE_SYSTEM_PROMPT + "\nWhat we know about this student: " + json.dumps(notes)
    return system, []          # fresh messages, but a system prompt with notes

Trace both days:

  1. Monday. Training is confirmed. The assistant (or your code) calls save_note("dana", "laser_training", "done 2026-11-09"). The file now holds {"dana": {"laser_training": "done 2026-11-09"}}.
  2. Monday's session ends; its messages list disappears.
  3. Thursday. start_session("dana") loads the file and puts a short line into the system prompt: "What we know about this student: {"laser_training": "done 2026-11-09"}".
  4. Dana asks to book. The model sees the note in its context, skips the training question and goes straight to the calendar tool.

This is notes as memory, which Anthropic calls structured note-taking or agentic memory: the agent regularly writes notes to storage outside the context window, and they are pulled back into the window later (Anthropic: Effective context engineering for AI agents). Between sessions, "memory" is just whatever you wrote to storage; Claude's docs point to a memory tool and a multisession pattern for agents that work across many sessions (Claude docs: Context windows).

Why this works

A running program's memory dies with it, and the model keeps nothing at all. Anything that must outlive a session has to be in a file or database, then loaded into the next context. Saving a few facts instead of the whole transcript keeps the next session cheap and uncluttered, which is the lesson of sections 2 and 3 applied across time.

A common mix-up

"Just save the whole conversation and reload it next time." It feels safest, but you would reload every old manual page and every chat message, paying for them on every call and inviting context rot. Save the durable facts (training status, preferences, open bookings), not the transcript.

Check yourself

Which item is the best candidate to save as a note for next time? Think about what stays true and is needed later.

Show the answer

The third option: small, durable and decision-relevant. Manual pages are better fetched fresh when needed (next section), and chit-chat has no future value.

Extra practice: a note that goes stale

Your code saves the note "laser_slot": "Sat 10 am" for a student. Two weeks later the assistant loads it into the system prompt and tells the student they have a booking on Saturday. The booking was cancelled by someone else last week. What went wrong, and how would you change what you save or how you use it?

Show the answer

A live fact (a booking) was saved as if it were a durable one, so it went stale. Save durable facts such as training status, and either skip bookings or store them only as a hint ("had a booking once"), then check the calendar tool for the real state before saying anything. The calendar, not the note, is the source of truth for slots.

6. Retrieval: finding the right page 10 min

Your makerspace has 40 manual pages of about 600 tokens each, so 24,000 tokens in total. Putting them all in the context would cost 24,000 input tokens on every call (and invite rot). Instead, you store the pages as small chunks and give the model a search tool. Here is a toy version with three chunks and a keyword score:

chunks = {
    "laser-p3":   "Laser cutter: maximum acrylic thickness is 6 mm. Never cut PVC.",
    "laser-p7":   "Laser cutter: clean the lens weekly with isopropyl alcohol.",
    "printer-p2": "3D printer: PLA bed temperature is 60 C.",
}

def words(text):
    return set(text.lower().replace(".", "").replace(":", "").split())

def search_manual(query, top_k=2):
    q = words(query)
    scored = [(len(q & words(text)), name) for name, text in chunks.items()]
    scored.sort(reverse=True)
    return [(name, chunks[name]) for score, name in scored[:top_k] if score > 0]

Trace search_manual("max acrylic thickness laser cutter"):

  1. The query words are {max, acrylic, thickness, laser, cutter}.
  2. laser-p3 shares laser, cutter, acrylic and thickness: score 4. (It does not share "max", because the page says "maximum". Keep that in mind.)
  3. laser-p7 shares laser and cutter: score 2. printer-p2 shares nothing: score 0.
  4. The sort puts 4, 2, 0 in that order; the function returns the top two with a score above zero: laser-p3 and laser-p7, about 40 tokens in this toy, about 1,200 for two real 600-token chunks.
  5. Those chunks become the tool result in messages. The model reads "maximum acrylic thickness is 6 mm" and answers.

This is retrieval: instead of loading everything in advance, the agent uses a tool to find and pull in only the pieces it needs, when it needs them. Anthropic describes this "just in time" approach as keeping lightweight references and using them to load data into context at runtime with tools, and names its trade-off: runtime exploration is slower than reading pre-computed data (Anthropic: Effective context engineering for AI agents). Retrieval quality is the real work: the toy search missed "max" versus "maximum", and a bad search puts the wrong text in context or none at all.

Why this works

The model needs one or two facts, not the whole library. Searching first turns a 24,000-token problem into a 1,200-token one, which cuts cost, keeps the window uncluttered and lets the manual grow without growing the context. The price is that the answer can only be as good as the search that found the page.

A common mix-up

"Retrieval and notes are the same thing." Both store text outside the window, which makes them look alike. But notes are facts the agent wrote about one student, kept to remember; retrieval searches a large reference like the manuals, which the agent never wrote, to look something up.

Better ways to search than shared words exist, such as search by meaning and adding context to each chunk. Anthropic's contextual retrieval post is a good start. They are for a later lesson; the idea in this section is the same.
Check yourself

Worked example and practice 12 min

Now combine the three sources of information. For each fact in a request, ask: is it needed right now (context), does it need to outlive the session (notes), or is it reference material to look up (retrieval)?

Worked example

Priya returns to the assistant and says: "Book the band saw for Saturday morning, and remind me how thick a board it can cut." Where does each piece of information live?

  1. Priya's band saw training status. It needs to survive between visits and is a short fact about one student: notes. It is loaded into the system prompt at session start, so the assistant knows before booking.
  2. The band saw's maximum cutting thickness. It is part of a long manual that the assistant did not write and Priya has not asked about before: retrieval. The assistant calls search_manual and receives one or two chunks.
  3. Saturday morning's free slots. It changes constantly, so saving it would go stale: a tool result, fetched live and held in the context for this session only.
  4. "Book Saturday 10 am" once confirmed. It is a decision made in this conversation, needed in the next few steps (context) and also useful next visit (a short note: "booked band saw Sat 10 am").
  5. The full manual page after the answer is given. Once Priya has the number it is dead weight. It is a candidate for being dropped by compaction if the conversation runs long, and is never saved as a note.
Your turn

Sam, a returning student, writes: "Is the resin printer free tomorrow? Also, how do I clean the build plate? And last time you told me I needed to redo training." Sort each of the following into context, notes or retrieval, with one line of reason each. The first is done for you: Sam's resin printer training status: notes, because it must survive between visits.

  1. The cleaning instructions for the resin printer's build plate.
  2. Tomorrow's free slots on the resin printer.
  3. That Sam has now rebooked the training.
Show a solution
  1. Retrieval: reference material from a long manual, searched when asked and not saved per student.
  2. Context, via a calendar tool: it is live data that goes stale, so fetch it fresh and hold it only for this session.
  3. Both: it matters now (context, so the assistant can say "you're booked") and for the next visit (notes, so the status carries over).

If your answer to 3 was only one of the two, that is the usual slip: a fact can be needed now and later, so it can live in two places for two different reasons.

Challenge a design

A teammate proposes: "Skip notes and retrieval, put all 40 manual pages and each student's full chat history in the system prompt every time." Write two sentences answering them, using the numbers and ideas from sections 2, 3 and 6.

Show a sample answer

Every call would resend roughly 24,000 manual tokens plus the history, so a five-call request costs well over 120,000 input tokens before any answer, which breaks a small budget. It would also bury the relevant line in clutter, which causes context rot, so answers would get worse as well as dearer.

Summary 3 min

  • The context window is everything the model sees in a call: system prompt, tools, messages, tool results and its own reply. Nothing outside it exists for the model.
  • Between steps, only the history your program resends carries information. It grows each step, and so does the input you pay for on every later call.
  • Context rot means a crowded window gets less accurate, so keep the smallest set of useful tokens. Compaction summarizes old history to make room, and what you tell it to keep decides what survives.
  • Between sessions, nothing survives unless you save it: notes hold short, durable facts and return to the next context. Retrieval looks up pieces of a long reference on demand, and is only as good as its search.

Say it in your own words: without looking back, explain to a teammate why the assistant "remembers" the first question at step 3 of a request, but does not remember Dana's training on Thursday unless you built something.
