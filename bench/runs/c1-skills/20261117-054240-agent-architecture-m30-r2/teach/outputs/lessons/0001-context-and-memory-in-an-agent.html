Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the context, in saved notes, or in a manual that is searched on demand, and say why.

Objective O3: context window, what is kept between steps and sessions, retrieval and notes as memory About 30 minutes
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits, all on a small model budget. Those are three different memory problems with three different answers, and your design review will ask you to defend each one.

Warm-up 2 min

Check your answer

The question goes to the model; the model asks for check_calendar with the machine and date; your program runs it; the result goes back to the model; the model writes the answer and the loop stops. Your program runs the tool, never the model. Today's question is what the model can see at each of those model calls, and what survives after the loop ends.

The context window 6 min

Imagine one model call inside your assistant. A student has just typed "How do I change the blade on the bandsaw?" Before the model writes a single word, your program assembles one block of text and sends it. Here is that block, with rough token counts (a token is a small chunk of text, a few characters long):

1. System prompt: "You are the makerspace assistant. Be brief..."   300 tokens
2. Tool definitions: check_calendar, search_manuals, book_slot      600 tokens
3. Conversation so far: the student's question                       20 tokens
                                                              -------------
   Sent to the model:                                               920 tokens
4. The model writes back: "Let me look that up" + a tool request     40 tokens
                                                              -------------
   Used in this call:                                               960 tokens

Notice three things. The model sees only what is in this block: it has no other view of your system. The tool definitions take up space even though nobody asked about them. And the model's own reply is counted too.

That block is the context window: everything the model can see when it produces a response, including the response itself. Anthropic's docs call it the model's "working memory" and note that the system prompt, every message, tool results and tool definitions all count toward it (Claude docs: Context windows). It has a maximum size, and more is not automatically better: as the token count grows, accuracy and recall degrade, which the docs call context rot.

Why this works

A model has no connection to your database, your calendar or earlier chats. Its only input is the text you hand it on this call, so whatever is not in that text effectively does not exist for it. That is why "what do we put in the context?" is a design decision, and why Anthropic's engineers treat context as a finite resource to curate rather than a bucket to fill (Effective context engineering for AI agents).

Check yourself

Your team adds a 15-line list of safety rules to the assistant's code, but never puts it into the text sent to the model. A student asks about wearing gloves at the drill press. What can the model use?

Show the answer

Only its general training knowledge. The rules never entered the context window, so the model cannot see them.

What is kept between steps 6 min

Now run the full loop for "Is the bandsaw free Friday, and what blade do I need for aluminium?" Each step below is one model call. The numbers are made up but realistic: the manual page your tool returns is the big one.

Call 1  sent: system 300 + tools 600 + question 30                    =   930
        model writes: tool request check_calendar(...)  (+40)
Call 2  sent: everything from call 1 + request 40 + calendar result 150 = 1,160
        model writes: tool request search_manuals(...)  (+40)
Call 3  sent: everything from call 2 + request 40 + manual page 3,000  = 4,200
        model writes: final answer (+120)

Tokens sent in total:  930 + 1,160 + 4,200 = 6,290

Look at call 3. The model has to reason from the calendar result and the manual page together, so both are sent again. Call 3 alone costs more than calls 1 and 2 combined, and the 3,000-token manual page is resent on every later call for as long as the loop runs. If the loop ran ten more steps, that page would be paid for ten more times.

Between steps, then, the model keeps nothing by itself. Your program keeps a growing list of messages and sends the whole list each time. That list is the conversation history, and in the Claude API, previous turns are preserved completely and each response becomes part of the input for the next call (Claude docs: Context windows).

Why this works

Each call to the model is independent, so the only way it can "remember" call 1 during call 3 is if call 1's content is inside call 3's input. Memory between steps is your program re-sending text. That is also why cost climbs with the length of the loop: you pay for the history again on every call.

Anthropic's docs describe trimming this growth with context editing, which clears old tool results, and compaction, which summarizes earlier turns. Those are later tools; first see why the growth happens.
A common mix-up

"The model remembers the conversation, the way I remember a chat." It is tempting because chat apps feel continuous. But the model remembers nothing; the program re-sends the transcript. If your program forgets to include the calendar result in call 3, the model has no idea the calendar was ever checked.

Check yourself

An assistant run uses a 1,000-token starting context. Step 1 adds 500 tokens (tool result), step 2 adds 500 more, step 3 adds 500 more, and the model is called after each addition. How many tokens are sent across the model calls after steps 1, 2 and 3 (not counting the first call)?

Show the answer

After step 1 the context is 1,500; after step 2, 2,000; after step 3, 2,500. Each is sent in full, so 1,500 + 2,000 + 2,500 = 6,000.

What is kept between sessions: nothing 4 min

On Monday, Dana completes her laser cutter training, and the assistant says "Great, you're certified." On Thursday she opens the assistant again and asks "Can I book the laser cutter?" The program starts a new session with a fresh list of messages:

Monday session   messages = [Dana: "I finished training", ..., assistant: "You're certified"]
                 session ends -> list is discarded

Thursday session messages = [Dana: "Can I book the laser cutter?"]
                 context = system prompt + tools + that one message
                 -> the model has no record of Monday

The assistant might ask Dana to prove her training again, or, worse, guess. Nothing in the model or the context carried over, because the Monday list lived only in your program's memory for that session and was thrown away when the session ended.

So the default between sessions is that nothing persists: a new session starts with an empty context, containing only what your program puts there. Anything the assistant should know next time has to be saved outside the context window and put back in. Anthropic's memory-tool docs describe exactly this: Claude stores and reads information in a file directory that your application controls (Claude docs: Memory tool).

Why this works

The context window is rebuilt from scratch on every call. A session is just a list your program chose to keep, so ending the session ends the list. Persistence is therefore your design job: something outside the model, such as a file or a database row, must hold the information.

Check yourself

A student sets a preference on Tuesday: "always show me times in the evening." On Wednesday, in a new session, the assistant lists morning slots. What is the most likely cause?

Show the answer

The preference was never saved. A new session starts with an empty context, so only stored data brought back in can carry it over.

Notes as memory 6 min

Fix Dana's problem. Give the assistant a small record per student, stored in your database or a file, and two steps in your program: read it at the start of each session, update it at the end. Here is Dana's record and Thursday's session:

# students/dana.json (stored on disk, not in the context)
{"training": ["laser_cutter"], "prefers": "evenings", "last_visit": "Mon"}

# Thursday, start of session
notes = json.load(open("students/dana.json"))
system_prompt += "Student notes: " + json.dumps(notes)      # about 40 tokens

# Dana: "Can I book the laser cutter?"
# Model sees the notes, so it checks the calendar for evenings.
# Dana: "I also passed the 3D printer safety quiz."
# The model calls save_note(...) -> your program updates the file.

Dana's Monday information now costs about 40 tokens on Thursday, instead of a replayed transcript of thousands. The notes were written by the assistant (or your program) when something worth keeping happened, and loaded back when needed.

This is notes as memory: the agent writes what matters to storage outside the context window and reads it back in later. Anthropic describes it as "structured note-taking, or agentic memory", with examples like a to-do list or a NOTES.md file (Effective context engineering).

Why this works

A short, distilled note carries the conclusion without the conversation that produced it, so it is cheap to put back in the context. Because the note lives outside the context window, it survives session endings. You decide what is worth writing, which keeps the budget under control.

A common mix-up

"Just save the whole transcript and reload it next time." It feels safest, but it re-sends every old tool result on every call, which costs money and invites context rot. Save the facts, not the chatter.

Check yourself

Which of these is the best candidate to save as a note for the makerspace assistant?

Show the answer

The training fact. It is short, it is specific to this student, and nothing else in the system holds it.

Retrieval as memory 6 min

Notes work for small facts about a student. The manuals are different: say 40 manuals, each 60 pages, roughly 2 million tokens in all. A student asks "What is the maximum material thickness for the laser cutter?" Compare two ways to answer:

Option A: put all manuals in the context   -> 2,000,000 tokens per call: too big for most windows,
                                               and a huge bill on every call
Option B: search first, then read one page:
   1. Model calls search_manuals("laser cutter max thickness")
   2. Program searches an index, returns the 3 best-matching pages  (about 1,500 tokens)
   3. Model reads them and answers: "Up to 10 mm acrylic, p. 14."

Option B pays for 1,500 tokens instead of two million, and the model sees only pages likely to hold the answer. The manuals sit outside the context in a store, and the model pulls in just what the question needs.

That is retrieval: searching a larger store at the moment of need and putting only the best matches into the context. Anthropic calls the agent version "just in time" context: the agent keeps lightweight references, such as file paths or stored queries, and loads data with tools when it needs it (Effective context engineering). Your search_manuals tool from the agent loop is exactly this.

Why this works

The context window is small and costly relative to a library, and a long context loses recall. Retrieval turns "everything the assistant could know" into "the few pages this question needs". The trade-off, noted in the same article, is that searching at run time is slower than having data ready, and a bad search returns the wrong pages.

Check yourself

The assistant gets slow answers because every call loads all 40 manuals, and it sometimes misses details buried in the middle. Which single change addresses both problems?

Show the answer

Retrieval. It shrinks the context to the relevant pages, which lowers cost and reduces the chance of missing details.

Worked example and practice 6 min

Worked example

Sort these four pieces of information for the assistant into context (always sent), notes (saved, loaded at session start) or retrieval (searched on demand): (1) "You are the makerspace assistant. Never book without a training record." (2) Which machines Dana is trained on. (3) The 60-page bandsaw manual. (4) What Dana just asked.

  1. The rules (1): needed on every call and small, so they sit in the system prompt in the context.
  2. Dana's training (2): a short fact about one person that must outlive the session, so it goes in notes, and a copy is placed into the context at session start.
  3. The bandsaw manual (3): large and needed only for some questions, so it is retrieved a few pages at a time.
  4. Dana's current question (4): it is the live conversation, which is in the context for this session. Whether anything about it becomes a note is decided afterwards.
Your turn

Sort these three the same way and give one reason each: (a) The booking policy "no more than 4 hours per student per week" (two sentences). (b) The student's request earlier in today's chat to book the 3D printer on Friday at 2 pm. (c) The 3D printer's 80-page maintenance guide. Start with (a): is it small, and is it needed on every call?

Show a solution

(a) Small and needed whenever a booking is made, so it belongs in the context (system prompt). (b) Part of today's live conversation, so it is in the context; once the booking succeeds, only the result, such as "booked Friday 2 pm", might become a note. (c) Large and rarely needed, so retrieval, loading only the relevant pages.

Summary 2 min

  • The context window is everything the model sees on one call; nothing outside it exists for the model.
  • Between steps, your program re-sends the growing history, so cost rises with every step.
  • Between sessions, nothing persists unless you save it outside the context.
  • Notes save small, distilled facts; retrieval fetches only the needed pages from a large store.

Say it in your own words: explain to a teammate why the assistant forgot Dana on Thursday, and name the two different fixes you would use for her training status and for the laser cutter manual.
