Context and memory in an agent

By the end of this lesson you can say, for any piece of information in the makerspace assistant, whether it lives in the context window, in saved notes, or in a manual that gets searched, and why.

Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits. Those are two different memory problems, and the context you choose to carry is also what you pay for on every request.

The result goes back to the model, which decides on its next action, and the loop repeats until the model answers or a limit is hit. Today's question: what exactly does the model see each time the result comes back?

The context window 3 min

Here is the assistant answering "Is the laser cutter free on Friday?", written as the Python list your program would build:

messages = [{"role": "user", "content": "Is the laser cutter free on Friday?"}]
# model call 1 sees: [user question]
messages.append({"role": "assistant", "content": "call check_calendar(laser, Fri)"})
messages.append({"role": "tool", "content": "Fri: 10-12 booked, rest free"})
# model call 2 sees: [user question, tool request, tool result]
messages.append({"role": "assistant", "content": "Free except 10-12."})

Trace it. At call 1 the model sees one message. At call 2 your program sends the whole list again, with the new entries added. The model keeps nothing itself between the calls; the only reason it "remembers" the question at step 2 is that your program sent it again. Every extra tool result makes the next call longer, and a long call costs more.

That list, everything sent to the model on one call, is the context: the set of tokens the model sees when it generates (Anthropic, context engineering). The context window is the maximum amount of it a model can take in at once, counted in tokens (Claude docs).

Why this works

The model is a function from text in to text out, so any fact it should use on a step has to be in that step's input. "Memory between steps" is just your program re-sending the history. Anthropic also notes that recall gets worse as the window fills, so more context is not automatically better, and it always costs more.

Notes: memory between sessions 2 min

A student, Ana, finishes the laser cutter training on Monday. Her session ends and the messages list is thrown away. On Thursday she starts a new session and asks to book the laser. With only a fresh list, the assistant has no idea she is trained. So before Monday's session ended, your program wrote a line to a file:

notes/ana.json  →  {"laser_cutter": "trained 2026-11-09", "3d_printer": "not trained"}

On Thursday the program reads that file and puts it at the start of the new list. The assistant now says "You're trained on the laser, here are the free slots." The file survived; the context did not.

Information written outside the context window, to be loaded back in later, is notes (agent memory). Anthropic describes it as the agent regularly writing notes persisted to memory outside the context window, such as a to-do list or a NOTES.md file (Anthropic).

Why this works

The context is rebuilt from scratch each session, so anything that must outlive a session has to live in storage your program controls. You decide what is worth saving, and you decide what to load back, which keeps the new context small.

Retrieval: finding the right page 3 min

The laser cutter manual is 200 pages, about 150,000 tokens. A student asks, "What power setting for 3 mm acrylic?" Pasting the whole manual into every call would cost a lot and bury the answer. Instead:

  1. The manual is split into pages ahead of time, each with an id such as laser-p42.
  2. The assistant calls a tool, search_manual("acrylic 3mm power"), which returns the top three matching pages' ids and short snippets.
  3. It calls read_page("laser-p42") and gets one page, about 700 tokens.
  4. It answers from that page. The context grew by about 1,000 tokens, not 150,000.

Pulling just the needed pieces into the context, at the moment they are needed, is retrieval. Here the agent keeps light references (page ids) and loads the data at runtime, which Anthropic calls just-in-time retrieval (Anthropic).

Why this works

The window is limited and every token in it is paid for on every later call, so you load only what the current question needs. The manual stays in cheap storage; the search tool is how the model reaches it.

A common mix-up

"A bigger window means I can skip retrieval." It is tempting because the manual might fit. But you pay for those tokens on every call, and recall gets worse as the window fills (Anthropic). Fitting is not the same as working well or being affordable.

Worked example and practice 1.5 min

Worked example

Ben says: "Book me the vinyl cutter tomorrow, and remind me how to load the roll." Where does each piece of information come from?

  1. Is Ben trained on the vinyl cutter? A lasting per-student fact, so notes, loaded at the start of the session.
  2. Is the cutter free tomorrow? A live fact from a tool call; it goes in the context for this request only.
  3. How to load the roll? A fact inside a long manual, so retrieval of one page.
Your turn

Cara asks, "Which tools did I book last month, and what is the max thickness the bandsaw can cut?" Sort the two parts into context, notes or retrieval. The first is done: past bookings are a lasting fact about Cara, so they are notes.

Show a solution

Bandsaw thickness is a detail inside a manual, so retrieval: search, read the one page, answer. Both results then sit in the context for the rest of this request.

Summary 0.5 min

  • The context is everything sent on one model call; your program re-sends it each step, so it grows and costs more.
  • Notes live outside the window and carry lasting facts across sessions.
  • Retrieval loads only the needed piece of a big source, when it is needed.

Say it in your own words: why does the assistant need all three, not just a very large window?
