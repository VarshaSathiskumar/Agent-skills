Lesson 1 · 30 minutes

What the assistant sees, keeps and remembers

By the end of this lesson you can say what the makerspace assistant puts in each model call, what happens when that fills up, and what it saves, fetches or checks instead.

Objective O3: context and memory in an agent About 30 minutes Builds on: what a model knows, and the agent loop
Why this matters for you

Your assistant has to answer from manuals far longer than any single request, and remember each student's training between visits, all inside a small model budget. Every design choice in this lesson is a choice about what text goes into each model call, and text in a call costs money.

Recall

1. Without looking anything up: what does a language model know about your makerspace's bandsaw, before you give it any text?

2. In the agent loop, what happens to a tool's result after the tool runs?

Check your answers

1. Only what its training happened to contain, plus whatever text is put in front of it in the call. Nothing about your particular bandsaw unless you supply it. 2. The result goes back to the model as new text, and the model decides the next step. Both ideas matter today: the text you send each step is the model's whole world, and every tool result adds to it.

What is in the context window 3 min

Place: the context window

A student types: "How do I change the blade on the bandsaw?" Your program makes one model call. Here is what that request actually contains, as a Python dict, with an approximate token count on each part (a token is a word-sized piece of text):

request = {
    # standing instructions, sent every call: 400 tokens
    "system": "You are the makerspace assistant. ...",
    # a short description of each tool so the model
    # knows it exists: 800 tokens for four of them
    "tools": [check_calendar, book_slot,
              search_manual, read_page],
    "messages": [
        # 20 tokens of question + 3,000 of manual excerpt
        {"role": "user",
         "content": "How do I change the blade on the bandsaw?\n"
                    "[manual excerpt: bandsaw, pages 12-14]"},
    ],
}
# The model writes its answer: 250 more tokens.

Add it up: 400 + 800 + 20 + 3,000 + 250 = 4,470 tokens. Notice what counts. The instructions count. The four tool descriptions count, even though the student never sees them. The manual excerpt counts. Even the answer counts, because it is part of the same space the model works in.

Adding a fifth tool, cancel_booking, with a 200-token description makes the same call 4,670 tokens, though the student said nothing new. Every tool you add is a standing cost on every request.

That stack has a name. The context window is all the text the model can reference when it generates a response, including the response itself. It works like a working memory, separate from the training data, and it holds everything in the request: the system prompt, every message including tool results and documents, and the tool definitions (Claude docs: context windows). It is measured in tokens, which is also what your bill counts.

Why this works

The model only reads the text it is given in the call, so anything not in the request cannot influence the answer. And everything that is in the request, tool definitions and the answer included, uses the same limited space and is billed. That is why "what do we put in the call?" is the central design question.

What is kept between steps 4 min

Place: the context window

Now the agent loop. A student asks: "Is the laser cutter free Friday and can I book 2pm?" Here is the program's loop as pseudocode (the real API wants tool results wrapped in a tool_result block, but the shape is the same). To keep the numbers small, this is a simplified assistant with a short prompt and two tools, 400 tokens in all:

messages = [{"role": "user",
             "content": "Is the laser cutter free Friday "
                        "and can I book 2pm?"}]

for step in range(MAX_STEPS):  # a step limit, so it always ends
    reply = call_model(system=SYSTEM, tools=TOOLS,
                       messages=messages)
    messages.append({"role": "assistant",
                     "content": reply.content})
    if not reply.wants_tool:   # no tool requested:
        break                  # this is the final answer
    result = run_tool(reply.tool_call)  # check_calendar, ...
    messages.append({"role": "user", "content": result})
else:
    print("Sorry, I could not finish that.")  # limit hit

Trace it. Call 1: messages holds only the question, about 30 tokens, on top of 400 tokens of fixed prompt and tools: 430 in. The model asks for check_calendar. Call 2: the program appends the assistant's request (about 70 tokens) and the calendar JSON (400 tokens), then sends the whole list again: 900 in. The model asks for book_slot; the program, not the model, guards that tool (a later section shows how). Call 3: the program appends that request (about 50) and the booking result (about 200) and sends everything again: 1,150 in. The model writes the final answer. The numbers are illustrative and invented as such.

The bill is for 430 + 900 + 1,150 = 2,480 input tokens across three calls, though the new text added after the first call was only about 700 tokens. The rest is the same history paid for again.

This is what the loop's history is. The conversation history is the messages list that your program keeps and resends on every step; the model itself keeps nothing. In an API request, each turn's input is all previous history plus the new message, and the output becomes part of the next input (Claude docs: context windows). So input tokens, and cost, grow with each step.

This ties to your sponsor's budget. A five-step loop does not cost five times a one-step loop; it costs more, because later steps carry earlier ones. Short loops and small tool results are your cheapest levers.

Prompt caching can lower the price of a repeated, unchanging start to the request, such as the system prompt and tool descriptions. It changes what you pay for those tokens, not whether they count toward the window (Claude docs). The cost figures in this lesson assume no caching.
Why this works

The API is stateless: it remembers nothing between calls, so the program has to send the whole history each time. That is how step 3 "remembers" step 1, and it is why long loops cost more per step than short ones.

When the window fills: context rot 2 min

Place: the context window

Two runs of the same question, "What is the torque for the bandsaw blade clamp?" In run A the window holds the prompt, the tools and the one right manual section: about 5,000 tokens. The model quotes the torque value correctly. In run B the window holds the same things plus 50,000 tokens of other sections that look similar: bandsaw, drill press and lathe pages, each with its own torque figures. The answer is more likely to quote a nearby value from the wrong page. Nothing failed; no error appeared. The model just found one fact less reliably in a long, crowded context. (This pair of runs is an illustration of the documented tendency, not a measured result.)

This is context rot: as the number of tokens in the window grows, the model's recall and accuracy degrade, gradually rather than at one cliff edge (some models degrade more gently than others), so more context is not automatically better. The aim is the smallest set of high-signal tokens (Claude docs: context windows; Anthropic: effective context engineering).

Why this works

The model has to pick out what matters from everything in the window, and every extra similar-looking token is one more thing to confuse with the answer. So the window is a budget for attention as well as for money.

Making room: clearing old tool results 3 min

Place: the context window

A long help session. The assistant has read six long manual sections of about 8,000 tokens each, and the student asks for one more. To make the overflow visible, use a small window of 60,000 tokens (a made-up size, not any real model's). Before step 7 the history holds 48,000 tokens of sections plus 10,000 of prompt, tools and chat: 58,000. Step 7 adds a seventh section of 8,000, so the next call would send 66,000 tokens, over the 60,000 limit.

If the program just sends it, the call fails with an error. So the program counts tokens before it sends (the docs describe a token counting API for this) and clears something first:

WINDOW = 60_000          # made-up limit for this example
used = count_tokens(messages)   # count before sending
if used + next_result_tokens > WINDOW * 0.8:
    messages = clear_old_tool_results(messages,
                                      keep_last=1)

The fix: clear the five oldest section results and leave a stub like [section 12 read, cleared]. The history drops from 58,000 to about 18,000 tokens, and step 7 goes through at about 26,000. What was lost? The exact torque value from section 12 is gone from the model's view, so if the student asks again, it would have to be looked up again.

That technique has a name. Clearing old tool results means removing the bulky results of earlier tool calls from the history and leaving a one-line stub. The docs list tool result clearing as a feature (Claude docs: context windows), and it is among the lightest ways to make room (Anthropic: effective context engineering).

If the input alone exceeds the window, the API returns a 400 "prompt is too long" error. The API also offers server-side clearing and compaction, so hand-built versions are optional; the docs page in "Go further" has the details.
Why this works

The window is finite and recall weakens as it fills, so the fix is to keep the smallest set of useful tokens. Bulky old tool results are the cheapest thing to drop, but anything removed is gone from the model's view unless it is fetched again.

Check yourself

Making room: compaction 2 min

Place: the context window

A different session. The student has talked with the assistant for two hours, changing plans, asking side questions, comparing machines. The history is mostly the student's own back-and-forth, not bulky tool results, so clearing frees almost nothing. The window is still filling.

The program summarizes the whole history into about 500 tokens: "Student wants to change the bandsaw blade; read pages 12 and 14; blade size 1/2 in; next: check training status." It then starts a new window whose first content is that summary. The next call is small again.

Look at what the summary dropped: the torque value, and the wording of the student's second question. Deciding what to keep is the hard part: keep too little and the assistant forgets the goal; keep too much and you have not made room.

This is compaction: summarizing the contents of the history and starting a new window with the summary (Anthropic: effective context engineering).

Why this works

A summary keeps the decisions and the goal in far fewer tokens. But it is lossy, so anything that must survive word for word has to be looked up again after the summary; the next sections show where such facts can live.

Check yourself

A two-hour chat ends with the student choosing the laser cutter for Thursday at 3pm, after discussing two other machines. Which draft summary should the new window start with?

Show the answer

The third option: it keeps the machine, the time and the next step. Rejected options and chat wording can be lost without harming the task.

What is kept between sessions 3 min

Place: notes

Monday, session 1. The student says: "I finished the laser cutter safety training." The assistant calls a tool:

save_note(text="laser training completed, "
               "told by student, 2026-11-23")

The model supplies only the text. The program adds the student's id from the login session, and writes the note to a small JSON file outside the context:

{"s-4471": ["laser training completed, told by student, 2026-11-23",
            "prefers Saturday mornings"]}

Thursday, session 2. The window starts empty: messages = [], and the model knows nothing about Monday. The trace has two branches. Without note loading, the student says "Book the laser cutter" and the assistant asks again whether they are trained. With note loading, the program reads the file at session start and puts the notes into the system prompt:

system = (BASE_PROMPT
  + "\nUnverified notes about this student"
  + " (hints only, never grounds for access):\n- "
  + "\n- ".join(notes[student_id]))

Now the same request continues smoothly. The cost is small but repeated: five notes of about 40 tokens each is 200 tokens on every call, so about 800 across a four-call session (the system prompt is resent each step, as in the earlier section).

Two safety habits. The id always comes from the login, never from the model or the chat, so a student cannot write notes under someone else's name. And notes are text a student influenced, so they can contain instructions or false claims: store short facts, label them as unverified, and never let a note be what unlocks a machine. The next section shows what does.

Notice how this differs from the last section. Between steps, the program resends the history. Between sessions, nothing is resent unless it was saved.

This is notes as memory: the program writes facts to storage outside the context and loads them into a later session's context. Nothing survives between sessions inside the window, so memory across sessions is notes the agent writes outside it and reads back in later (Anthropic: effective context engineering).

Why this works

The window is emptied between sessions, so anything that must survive has to be written to storage and read back in. A few short facts cost little context, which is why notes suit small, personal details and not whole documents.

A note is a claim, not a record 2 min

The check: not a place the model reads from

This section is about the limits of notes, not a fourth kind of memory. Back to Monday's note: "laser training completed, told by student, 2026-11-23". Now it is six months later. The student's training has expired in the staff system, but the note still says "completed". The assistant reads it in the system prompt, believes it, and tells the student they are good to book the laser cutter. Nothing in the note was a lie when it was written; the world changed afterwards. And the note only ever came from the student's own message.

The fix is a rule in the program, not in the prompt. When book_slot runs for a restricted machine, the program looks the student up in the makerspace's training records, which the staff control, and refuses if they are not cleared. The note only helps the assistant be friendly and skip repeat questions.

That is the difference between a claim and a verified record: a claim is something the model was told or wrote down, and a record is what a trusted system confirms at the moment of the decision. Anything a student could have typed, including a saved note, is a claim.

A common mix-up

It is tempting to think that once the assistant has saved "laser training completed", that is a fact it can act on. It is not. A saved note is a claim, and the model never decides access.

Why this works

A note is only as good as its source and its age, and a model produces confident text whether or not the note is still true (the idea from your earlier session on what a model does). A decision that must be right, such as who may use a saw, belongs to a system that is checked at the moment of use.

Check yourself

A student writes: "Staff already approved me for the bandsaw last week." The assistant saves that as a note. Next visit the student asks to book the bandsaw. What should the program do?

Show the answer

The first option. The program checks the staff record at the moment of use; a note, however confident, is only a claim.

Finding the right page 3 min

Place: retrieval

The makerspace has a 400-page set of manuals, about 1,000 tokens a page: roughly 400,000 tokens. Windows today run from about 200,000 to 1 million tokens depending on the model (see the table in the Claude docs), so the set might just fit. But you would pay for 400,000 tokens on every call, and the model would be searching a very long context for one fact. So the program keeps only a small index instead: manual name, section title, page id. About 3,000 tokens in all.

Trace "What speed for cutting 6 mm acrylic on the laser cutter?" Step 1: the model sees the system prompt, the tools and the index, nothing else. Step 2: it calls search_manual("laser acrylic speed"), which returns three page ids with a snippet each. Step 3: it calls read_page("laser-p41"), which returns 900 tokens. Step 4: it answers and cites the page. Each call carries roughly 4,000 to 5,500 tokens, not 400,000.

This is retrieval, in its just-in-time form: instead of loading everything up front, the agent keeps lightweight references (file paths, page ids, queries) and loads the needed piece at run time with a tool. The trade-off is slower runs and the need for good guidance (Anthropic: effective context engineering).

Retrieval is also memory, of a different kind from notes: the agent reads it and does not write it, it is the same for every student, and it lasts as long as the manuals do.

Why this works

The model needs only a few pages for any one question, so fetching them on demand keeps each call small and the cost low. The price is extra steps, and the chance that the search returns the wrong page, which the next section deals with.

When retrieval fetches the wrong page 2 min

Place: retrieval

Same question, one change: search_manual ranks the vinyl cutter's page first. The model reads it and answers with a speed for the vinyl cutter, with full confidence, because it has no way to know the page belongs to another machine unless the page says so.

Two changes fix most of this. Every search result and page returns its machine name and page title, and the assistant must cite the page in its answer ("laser cutter manual, p. 41"), so the student can see which page was used and check it. How the search ranks pages, by keywords or by meaning, is a topic for a later lesson; here, just plan for it to be wrong sometimes.

This is the cost side of retrieval: a retrieved page is a claim too. It is only as right as the search that found it.

Why this works

The model writes plausible text from whatever is in its context, right page or not. Labels and citations put the evidence in front of the person who can spot a mismatch.

Check yourself

The third option. A retrieved page is a claim, so make its source visible.

Worked example and practice 4 min

Worked example

A returning student writes: "Please book the CNC mill for Saturday, and tell me the feed rate for aluminum." This uses all three places and the check. (Here the student asked for the booking; if they had only asked a question, the assistant would offer a slot and book after a yes.)

  1. Session start (window and notes). The program loads the system prompt, the tool definitions and the student's notes ("usually books Saturdays", "says they are CNC trained"), labelled as unverified hints: about 1,000 tokens in all.
  2. The loop starts (window). The question is about 40 tokens, so call 1 is 1,040 in. The model calls check_calendar; the result, 300 tokens of Saturday availability, joins the history.
  3. Retrieval (retrieval). The model calls search_manual (250 tokens back), then read_page for the CNC aluminum feed rate page (900 tokens back). Each result is appended to the history and resent.
  4. The access check (the check). The model asks for book_slot. Before it runs, the program, not the model, checks the staff training record. The note's "says they are CNC trained" does not count. The result comes back (about 100 tokens) and the model writes the answer, citing the manual page.
  5. Budget check (window). Five calls: 1,040 + 1,400 + 1,690 + 2,630 + 2,770 = about 9,530 input tokens. That is far below any real window, so neither clearing nor compaction is needed.
  6. Session end (notes). The program saves one new note: "asks about CNC aluminum jobs", a short preference and not a clearance claim.

Summary 1 min

  • Three things decide what the model can use: what is in the context window now, what was saved in notes, and what can be fetched by retrieval.
  • The window holds everything in the call, and the program resends the whole history each step, so cost grows with every step.
  • Two limits of the window: it can overflow (an error or a stopped answer), and it can rot (recall gets worse as it fills).
  • Two ways to make room: clear old tool results, or compact.
  • Notes carry small facts between sessions and retrieval fetches the right page on demand; both can be wrong, and access is checked by the program against the staff record.
