# Plan: What the assistant sees, keeps and remembers

- Objective: O3, Explain context and memory in an agent: the context window, what is kept between steps and between sessions, and retrieval and notes as memory.
- Minutes: 30; total budget: 4500 words
- Win: By the end of this lesson you can explain, for the makerspace assistant, what is in the model's context at each step, what happens when it fills up, and which facts go into saved notes, which are fetched from the manuals on demand, and which are checked against a real record.
- Builds on: learning record 0001 (the model knows only its training plus the text it is given), learning record 0002 (the agent loop: each step is a model call, results go back). No earlier lessons exist yet. Quiz 0001 is not graded, so the warm-up must not lean on it; recall the loop and the "only what it is given" idea.
- Primary source: Effective context engineering for AI agents (Anthropic Engineering) - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents

## Key facts
K1. The context window is all the text the model can reference when generating a response, including the response itself; it is a working memory, separate from training data. Everything in the request counts: system prompt, every message (including tool results and documents) and the tool definitions. It is measured in tokens. - https://platform.claude.com/docs/en/build-with-claude/context-windows - taught in: S1
K2. The model does not remember between calls: in an API request, each turn's input is all previous history plus the new message, and the output becomes part of the next input. So every loop step resends the history, and input tokens (and cost) grow with each step. - https://platform.claude.com/docs/en/build-with-claude/context-windows - taught in: S2
K3. More context is not automatically better: as tokens grow, recall and accuracy degrade (context rot). It is a gradient, not a cliff. The aim is the smallest set of high-signal tokens. - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents and https://platform.claude.com/docs/en/build-with-claude/context-windows - taught in: S3
K4. Failure case: if the input alone exceeds the window, the API returns a 400 "prompt is too long" error; on newer models, if input plus max_tokens passes the window, generation stops with stop_reason "model_context_window_exceeded". The program should count tokens before sending (token counting API). - https://platform.claude.com/docs/en/build-with-claude/context-windows - taught in: S3
K5. Ways to handle a full window: compaction (summarize the contents and start a new window with the summary; the hard part is choosing what to keep) and clearing old tool results (one of the lightest forms). - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents and https://platform.claude.com/docs/en/build-with-claude/context-windows - taught in: S3
K6. Between sessions nothing survives in the context: memory across sessions is notes the agent writes outside the window and reads back into context later (structured note-taking, agentic memory). - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents - taught in: S4
K7. Retrieval: instead of loading everything up front, an agent can keep lightweight references (file paths, page ids, queries) and load the needed piece at run time with a tool (just-in-time retrieval). Trade-off: slower, and needs good guidance; a hybrid of some up-front data plus exploring is often best. - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents - taught in: S5
K8. Failure case for notes and retrieval: a note can be stale or wrong and retrieved text can be the wrong page; the model then answers confidently from it. For access and permission decisions the program must check the real record. (Reasoned from K6 and K7 and learning record 0001; no URL.) - taught in: S4 and S5

## Sections

### S1 What is in the context window
- Concept and term: the context window, the text the model can see for one call, counted in tokens (token defined only as "the unit the window and the bill are counted in, roughly a word piece"). Two terms allowed because one cannot be said without the other.
- Example to trace: one call from the makerspace assistant for "How do I change the blade on the bandsaw?". Lay out the request as a labelled stack with token counts: system prompt 400, three tool definitions 600, student question 20, a manual excerpt of 3,000, and the model's answer 250 (about 4,270 total). Show a small Python dict with `system`, `tools`, `messages`, and a figure (inline SVG bar) of the window as a stack filling a box. Ask the learner what the model knows about the bandsaw that is not in this stack (nothing but training), linking to record 0001.
- Why this works: the model only reads the text it is given in the call, so anything not in the request cannot influence the answer, and everything in the request, including tool definitions and the answer, uses the same limited space and is billed.
- Check: a new case. A teammate says "the model already knows our booking calendar because we set it up last week." Right answer: it knows it only if the calendar text is in this call's context. Wrong options: "it learned it from setup" (training is not changed by setup), "it knows it only for tool results" (tool results are context too, but only once returned), "the window holds only the question" (it holds all of the stack).
- Key facts: K1
- Where the length comes from: the traced stack with its numbers and the figure, plus a second mini-trace that adds a tool definition and shows the total rising.

### S2 What is kept between steps
- Concept and term: conversation history (the `messages` list) that the program keeps and resends each step; the model itself keeps nothing.
- Example to trace: the request "Is the laser cutter free Friday and can I book 2pm?" as a small Python loop with a `messages` list (about 12 lines). Step 1: messages has the question (about 30 tokens in), the model asks for `check_calendar`. Step 2: program appends the assistant's request and the tool result (calendar JSON, 400 tokens), resends all, model asks for `book_slot`. Step 3: appends again, resends, final answer. Table of tokens in per call: 430, 900, 1,150 (the numbers are illustrative and invented as such). Point out the sum, 2,480 input tokens billed over three calls, though the new text added was only about 700.
- Why this works: the API does not store state between calls, so the program must send the whole history each time; that is how step 3 "remembers" step 1, and why long loops cost more per step than short ones.
- Check: new case. A loop for a manual question takes 5 steps and each adds a 2,000-token tool result; roughly how does input grow? Right answer: step n sends all earlier results, so input grows each step and total cost grows faster than steps (about 2,000, 4,000, ... 10,000 per call; 30,000 across calls, ignoring fixed prompt). Wrong options: "stays at 2,000 per call" (forgets resend), "only the last result is sent" (not by default), "grows once at the end".
- Key facts: K2
- Where the length comes from: the full code trace and the token table, and the cost angle tied to the small model budget in MISSION.md.

### S3 When the window fills: clearing old tool results (revised by the teacher: S3 and S3b replace the single S3, so each fix has its own example)
- Concept and term: clearing old tool results, removing the bulky results of earlier tool calls from the history and leaving a one-line stub. The section opens with the problem (overflow and context rot, K3 and K4) shown in the example; compaction is NOT mentioned here.
- Example to trace: a long help session where the assistant has read six manual pages of 8,000 tokens each. Use a small made-up window of 60,000 tokens (label it as made up) so overflow is visible: step 7 would send 66,000, so the program counts tokens first (token counting API) and sees it. Trace the real failures: input over the limit returns a 400 "prompt is too long" error; on newer models a too-large input plus max output stops with stop_reason `model_context_window_exceeded`. Note that even under the limit, recall gets worse (context rot). Then the fix: clear the five oldest page results, leaving a stub like "[page 12 read, cleared]"; the window drops to about 14,000 and step 7 goes through. Show what is lost: the exact torque value on page 12 is gone, so the model must re-fetch it.
- Why this works: the window is finite and recall weakens as it fills, so the fix is to keep the smallest set of useful tokens; bulky old tool results are the cheapest thing to drop, and anything removed is gone from the model's view unless fetched again.
- Check: new case. The assistant's context is at 90 percent after a booking conversation; the team wants to keep the student's chosen machine and time and drop 6 verbose calendar dumps. Right answer: clear the old calendar results but keep the decision in the history. Wrong options: "wait for the error and retry" (the error means the call failed, and rot has been hurting already), "send a bigger max_tokens" (that takes more of the window), "drop the first message" (it may hold the goal).
- Key facts: K3, K4, K5 (clearing)
- Budget: 400 words.

### S3b When clearing is not enough: compaction
- Concept and term: compaction, summarizing the whole history and starting a new window with the summary (K5).
- Example to trace: a two-hour session where the history is mostly the student's own back-and-forth, not bulky tool results, so clearing frees almost nothing. The history is summarized into about 500 tokens: "Student wants to change the bandsaw blade; read pages 12 and 14; blade size 1/2 in; next: check training status." The new window starts with the summary. Show what the summary dropped (the exact torque value) and that choosing what to keep is the hard part.
- Why this works: a summary keeps the decisions and goal in far fewer tokens, but it is lossy, so what must survive exactly belongs in notes or a fetchable page.
- Check: new case. Which line must a compaction summary of a booking chat keep: the chosen machine and time, the tone of the greeting, the wording of the calendar JSON, or the tool's name? Right answer is the machine and time; vary position.
- Key facts: K5 (compaction)
- Budget: 300 words (taken from S3's original 700; S3 + S3b = 700 total).

### S4 What is kept between sessions
- Concept and term: notes as memory (structured note-taking): the program writes facts to storage outside the context and loads them into the next session's context.
- Example to trace: Session 1 on Monday: the student says "I finished the laser cutter safety training." The assistant calls `save_note(student_id, "laser training completed, told by student, 2026-11-23")`. Session 2 on Thursday starts with empty messages, the model knows nothing. Show the program loading the note file (a tiny JSON dict) into the system prompt at the start: "Notes: ...". Then trace the failure: with no note loading, the assistant asks again; with the note loaded, it continues. Include the note's size cost: 5 notes at 40 tokens is 200 tokens per session.
- Safety: the note says "told by student", so it is a claim. The lesson states plainly: the model's saved note is not a verified record. Before the booking tool books a restricted machine, the program (not the model) checks the makerspace's training-records system (a source the staff controls). The note only helps the assistant be friendly and skip repeat questions. Who verifies: the program code against the staff record; the model never decides access.
- Why this works: the window is emptied between sessions, so anything that must survive has to be written to storage and read back in; it is a small set of facts, so it costs little context.
- Check: new case. Which of these goes in a saved note: (a) the student's preferred machine for Friday sessions, (b) the full text of the 3D printer manual, (c) "student is cleared for the CNC mill" taken from chat, (d) the last 40 tool results. Right answer: (a) as a preference; (b) belongs in retrieval, (c) must be checked in the staff record and not trusted from chat, (d) is noise. Position the right answer not first; keep option lengths equal.
- Key facts: K6, K8
- Where the length comes from: the two-session trace with the loaded notes, a second mini-trace of a stale note (student's training expires and the note still says completed), and the safety paragraph.

### S5 Finding the right page
- Concept and term: retrieval (just-in-time): the model calls a tool to fetch only the needed page from a long manual, instead of loading the manual into context.
- Example to trace: a 400-page set of manuals (about 600,000 tokens, too big for most windows and costly even if it fits). The program keeps a small index: manual name, section title, page id (about 3,000 tokens in all). Trace "What speed for cutting 6 mm acrylic on the laser cutter?": step 1 the model sees the index only; step 2 it calls `search_manual("laser acrylic speed")`, which returns three page ids with a snippet each; step 3 it calls `read_page("laser-p41")`, which returns 900 tokens; step 4 answers with a citation. Total context about 5,000 tokens rather than 600,000. Then the failure: the search returns the wrong page (a different machine's page), and the model answers confidently with the wrong speed; the fix is to put the page title and machine in the result and require citation so the student can check. State the trade-off: more steps and slower than preloading; a hybrid (keep the top 10 most asked pages up front) can help.
- Why this works: the model only needs a few pages per question, so fetching them on demand keeps the context small and the cost low, at the price of extra steps and the chance of fetching the wrong page.
- Check: new case. Which design for the booking calendar: preload the whole semester into context, or a `check_calendar(machine, date)` tool? Right answer: the tool, because only one day matters per question and the calendar changes, so a preload would be stale and large. Wrong options each name a plausible reason (simpler, faster) and why they fail (stale, big).
- Key facts: K7, K8
- Where the length comes from: the four-step trace with numbers, the wrong-page failure trace, and a second practice case on hybrid choice.

## Worked example
- Decision: how should the makerspace assistant handle "I want to use the CNC mill on Saturday; what feed rate for aluminum?" across a returning student's visit, using all five concepts (the window's contents, history resent, space management, notes and retrieval).
- Steps (shown fully): (1) Decide what is loaded at session start: system prompt, tool definitions, the student's notes (preferences, "told us CNC trained") about 1,000 tokens. (2) The loop starts, history grows as the calendar tool returns Saturday availability. (3) The model retrieves the CNC manual page for aluminum feed rate with `search_manual` then `read_page` (900 tokens). (4) Before booking, the program checks the staff training record; the note's claim does not count. (5) Budget check: the total tokens of the three calls, and compaction not needed at this size. (6) At the end, save a new note: "prefers Saturday mornings." Show a table of tokens per step.
- Faded task: a similar case for the 3D printer: "Book the resin printer Tuesday and tell me how to clean the build plate." Steps 1 and 2 are given partly filled; the learner fills in: what goes in the start-of-session context, what is retrieved (and how), which check the program makes before booking (staff record, since the resin printer is restricted), what is saved as a note (a preference only), and what to clear if the session runs long.
