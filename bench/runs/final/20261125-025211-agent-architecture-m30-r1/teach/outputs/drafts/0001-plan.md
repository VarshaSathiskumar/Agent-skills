# Plan: What the makerspace assistant sees, forgets and remembers

- Objective: O3, Explain context and memory in an agent: the context window, what is kept between steps and between sessions, and retrieval and notes as memory.
- Minutes: 30; total budget: 4500 words
- Win: By the end of this lesson you can decide, for each piece of information in the makerspace assistant (manual pages, tool results, a student's training status), whether it lives in the context window, in saved notes, or in a retrieval store, and defend the choice by its effect on accuracy and cost.
- Builds on: learning record 0001 (a model reads text in and writes text out); learning record 0002 (the agent loop: model asks, program runs the tool, result goes back, repeat). No earlier lessons or cheat sheets exist yet. Quiz 0001 is ungraded, so the warm-up must not repeat its items.
- Primary source: Effective context engineering for AI agents (Anthropic Engineering) - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents

## Key facts
K1. The context window is all the text the model can reference when generating a response, including the response itself. It is the model's "working memory", distinct from its training data. Everything in the request counts: system prompt, every message, tool results, documents and tool definitions. - https://platform.claude.com/docs/en/build-with-claude/context-windows - taught in: S1
K2. Failure case: if the input alone exceeds the window, the API returns a 400 `invalid_request_error` ("prompt is too long"). The program must catch it and shrink the input. The window size varies by model (up to 1M tokens on some, 200k on others), so Riley should check the model's table. - https://platform.claude.com/docs/en/build-with-claude/context-windows - taught in: S1
K3. More context is not automatically better: as token count grows, accuracy and recall degrade ("context rot"). The model has a limited attention budget, and each token draws it down. The aim is the smallest set of high-signal tokens. - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents and https://platform.claude.com/docs/en/build-with-claude/context-windows - taught in: S1
K4. Between steps, the context accumulates: each turn's input is all previous history plus the new message, and the output becomes part of the next input. The model keeps nothing itself; the program resends the history on every call, so a longer history means more input tokens on every later step. - https://platform.claude.com/docs/en/build-with-claude/context-windows - taught in: S2
K5. Compaction summarizes a conversation nearing the limit and continues in a fresh window with the summary. Failure case: overly aggressive compaction can lose subtle but critical context. Lighter option: clear old tool results. - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents - taught in: S3 (clearing is named in one line only)
K6. Between sessions, nothing survives unless the application saves it. Structured notes: the agent writes notes outside the context window and reads them back later. In the memory tool the model only requests file operations and the application runs them against storage it controls, so memory lives entirely in the application. - https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool and https://anthropic.com/engineering/effective-context-engineering-for-ai-agents - taught in: S4
K7. Notes need care: the app must restrict paths to the memory directory (path traversal), cap file sizes, expire stale files, and keep sensitive data out. Notes are written by the model and can be wrong or stale, so they are not a verified record. - https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool - taught in: S4
K8. Retrieval, just-in-time: keep lightweight references (file paths, queries, page IDs) and load content at runtime with tools rather than preloading everything. Tradeoff: runtime exploration is slower than pre-computed data and needs good tool guidance to avoid wasted context; a hybrid is often best. - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents and https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool - taught in: S5

### S1 The context window
- Concept and term: context window (the text the model can see for one call, its response included). Second term only if needed: token.
- Example to trace: one call from the assistant. Count roughly: system prompt 400 tokens, 3 tool definitions 600, student question 30, a manual chapter pasted in at 60,000. Show the table adding up to about 61,000, and the answer's own tokens added. Then show a student asking about a 300-page combined manual set at 900,000 tokens against a 200k-window model: the call fails with a 400 "prompt is too long". Then the quieter case: a 190,000-token request that succeeds but misses the one safety line buried in the middle. Use illustrative numbers and say so.
- Why this works: the model can only use what is in the request, and its attention is spread over every token, so a full window both runs out and gets noisy.
- Check: new case. The assistant sends 120,000 tokens to a model with a 100,000-token window. Right answer: the request is rejected with a 400 error and the program must trim. Wrong options: the model silently ignores the oldest text (that is not what the API does for input over the limit); the model answers but with lower quality (that is context rot, which happens below the limit).
- Key facts: K1, K2, K3.
- Where the length comes from: the token table traced line by line, and the two failure cases (hard and soft) each given their own short trace.

### S2 What carries from step to step
- Concept and term: accumulating history (each step is a fresh call; the program resends everything).
- Example to trace: the "Is the laser cutter free Friday, and book me 2 pm" request. Step 1 call: system plus tools plus question, 1,030 tokens in. Model asks `check_calendar`. Step 2 call: all of step 1, plus the model's tool request, plus the calendar result of 1,500 tokens, about 2,600 in. Step 3 call: adds the `book_slot` request and confirmation, about 2,800 in. Show a Python list `messages` growing, with `messages.append(...)` lines, and the line count of input tokens per call. Add up total input tokens across the three calls (about 6,430) versus the final context size (2,800), to show why cost per request grows faster than the conversation.
- Why this works: the model keeps no state between calls, so the only "memory" inside a task is the list the program sends again, and every call is billed for all of it.
- Check: new case. A manual lookup tool returns an 8,000-token page at step 2 of a 6-step run. Roughly how many extra input tokens does that page cost across steps 2 to 6? Right answer: about 8,000 x 5 = 40,000 (it is resent on every later call). Wrong: 8,000 (counts it once); 48,000 (counts step 1, before the page existed).
- Key facts: K4.
- Where the length comes from: the traced growing list with a running token column and the cost arithmetic; a second check on which budget lever helps (shorter tool results).

### S3 When the window fills
- Concept and term: compaction (summarize old history, continue in a fresh window with the summary).
- Example to trace: a long booking chat reaches 150,000 of 200,000 tokens. Show the before: 40 messages. Show the summary the program asks the model to write (a 600-token list: student is certified on the laser cutter, wants Friday 2 pm, booked slot 41, still needs 3D printer info). New window: system prompt plus summary plus the last user message, about 1,100 tokens. Then the failure: the summary dropped "the student said they are left-handed and need the bench on the left"-style detail, or more relevantly the line "student has not completed the safety quiz", and the assistant later offers a booking it should not. Show how to reduce the risk: check what a summary must keep (bookings, constraints, open questions), and keep the safety-relevant facts in a checked record (see S4).
- Why this works: most old messages are no longer needed word for word, so a short summary keeps the thread at a fraction of the tokens, but a summary is lossy by design.
- Check: new case. After compaction the assistant forgets the student's chosen machine. Which fix is best? Right answer: change the summary instructions so machine, time and open questions are always kept, and re-test. Wrong: make the summary shorter (loses more); raise the window limit (does not fix what the summary left out).
- Key facts: K5, K3.
- Where the length comes from: the before/after message lists, the lost-detail failure trace, and a second check on what must survive.
- Closing line in this section: clearing old tool results is a lighter option, named only, taught in a later lesson.

### S4 Between sessions: notes as memory
- Concept and term: notes as memory (the agent writes files the application stores, and reads them back in a later session).
- Example to trace: Monday, a student chats about the laser cutter and says they prefer evening slots. Trace: session starts, model calls `view /memories`, the app returns a listing, it reads `/memories/students/s123.md`, which holds "prefers evenings; asked about 3D printer" (a note). During the chat the model calls `str_replace` to add "booked laser cutter Tue 6 pm". Session ends; the context is thrown away. Thursday, new session: the model views the file and offers evening slots without being told. Show the handler in about 12 lines of Python: map `/memories` to a per-student folder and reject paths that resolve outside it. Show the failing request `/memories/../../secrets.env` being refused.
- Safety and verification: the student's training status (who is certified on which machine) is NOT trusted from a note. A note says "certified on laser cutter" only as a hint. The booking tool checks the makerspace's official training records (the staff-maintained system) before it books, so the code, not the model's note, enforces the permission. The lesson must state this in the example and the check.
- Why this works: the model cannot keep anything after the call ends, but the application can, and file operations the model requests let the model decide what is worth saving while the application stays in control of storage and access.
- Check: new case. A note from a past session says "student has passed the milling machine training." Student asks to book the mill. What should the assistant do? Right answer: use the note to speed the chat, but have the booking tool verify against the official training record before booking. Wrong: book because the note says so (a note is model-written and may be stale or wrong); refuse since notes are never usable (they still help with preferences).
- Key facts: K6, K7.
- Where the length comes from: the two-session trace with the file contents at each step, the handler code with the traversal rejection traced, and the second check about what belongs in notes (preferences, progress) versus a verified record.

### S5 Finding the right page: retrieval
- Concept and term: just-in-time retrieval (keep a light index, fetch the needed page with a tool at the moment of need). Optional second term: retrieval store, glossed as "the manuals, outside the window".
- Example to trace: a student asks "What speed do I use to cut 3 mm acrylic on the laser cutter?" Do not preload: 12 manuals at about 80,000 tokens would cost every call and bury the answer (S1 and S2 results). Instead: the system prompt lists an index (manual name, section titles, page IDs, about 500 tokens). Step 1 the model calls `search_manual(machine="laser", query="acrylic 3 mm speed")`. Step 2 the tool returns the two best matching pages (1,200 tokens). Step 3 the model answers and cites the page. Show the token tally: about 2,300 in the third call against 80,000+ if preloaded. Then the failure: the query is vague ("settings") and returns the wrong page; the model answers from the wrong machine. Fix: a clear tool description and returning the page title and manual name so the model can tell it has the wrong page. Say that runtime lookup costs an extra step (slower) and that a hybrid (always preload the short safety rules, retrieve the long manual pages) is often best.
- Why this works: the window is scarce and noisy, so putting only the needed pages in it at the moment of need keeps answers sharp and cheap, and the index lets the model know where to look.
- Check: new case. The assistant needs the makerspace opening hours, 40 words, needed in nearly every chat. Preload or retrieve? Right answer: preload (small, always needed, an extra step each time would cost more than it saves). Wrong: retrieve because retrieval is always cheaper (adds a step and a call every time); retrieve because it is more accurate (40 words do not cause context rot).
- Key facts: K8, K3.
- Where the length comes from: the three-step trace with a token tally, the vague-query failure trace, and the second check on the hybrid split.

## Worked example
- Decision: for the makerspace assistant, where should each item live? Items: the system prompt and tool definitions; the 12 manuals; the student's training status; the student's preferred time of day; the current chat's tool results.
- Steps (worked in full by the lesson, using each section's concept): (1) estimate the window use of each item (S1); (2) note which items are resent on every step and what that costs (S2); (3) decide when a long chat needs compaction, and what its summary must keep (S3); (4) decide which facts to save as notes and which to verify from an official record (S4); (5) decide what is retrieved on demand versus preloaded (S5). End with a filled table: item, place, reason, and who verifies it. Training status: official record, checked by the booking tool's code. Preference: notes. Manuals: retrieval. Tool results: window, cleared or summarized later. Short rules: preload.
- Faded task: a second feature, "the assistant answers questions about equipment maintenance schedules and reminds a returning student that their booking was moved". Give the item list; step 1 is done for the learner, steps 2 to 5 are blanks to fill in, with a hint for each. Solution on demand. Check the solution has the booking change verified from the calendar system, not from a saved note.
