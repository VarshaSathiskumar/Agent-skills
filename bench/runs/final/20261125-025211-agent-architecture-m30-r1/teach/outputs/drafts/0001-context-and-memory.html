Lesson 1 · 30 minutes

What the makerspace assistant sees, forgets and remembers

By the end of this lesson you can decide, for each piece of information in the makerspace assistant (manual pages, tool results, a student's training status), whether it lives in the context window, in saved notes, or in a retrieval store, or is not memory at all but a fact the code checks against an official record, and defend the choice by its effect on accuracy, cost and safety.

Objective O3: context and memory in an agent About 30 minutes Builds on: a model reads text in and writes text out; the agent loop
Why this matters for you

Your assistant has to answer from long manuals, remember each student's training status between visits, and stay inside the sponsor's budget. All three come down to one question: what goes where? This lesson gives you three places information can live: the context window, saved notes, and a retrieval store. It also shows the one thing that must not live in any of them: a permission, which the code checks against the staff's official record.

1. The context window 5 min

Let us count one call from the assistant. A student asks how to change the blade on the band saw. The program sends the model the following. All numbers here are illustrative round figures, not measurements. (A token is roughly a short word or a piece of a longer one; a tool definition is the description of one tool the model may ask for.)

Part of the requestTokens (about)
System prompt (the assistant's instructions)400
3 tool definitions600
Student question30
Band saw manual chapter, pasted in6,000
Input totalabout 7,000
The model's answer, written as it goes500
Window used by the end of the callabout 7,500

Everything the model can look at while writing is in that table, and nothing else. Its own answer counts too, because each new token it writes is something it can read when writing the next one.

Failure 1: the request is too big. Another student's chat has dragged on all evening, with page after page pasted in, and the next request would be 230,000 tokens. Say the model's window is 200,000 tokens. The input alone is over the limit, so the API refuses the call with a 400 invalid_request_error, "prompt is too long" (context windows docs). Nothing is answered. Your program has to catch the error, or better, count tokens before each call, and shrink the input.

Failure 2: the request fits, but the answer is worse. Now a 190,000-token request (a long chat plus pasted pages), inside the window with little room left for the answer. The call succeeds. (If input plus answer reached the window, the reply would be cut off with the stop reason model_context_window_exceeded on newer models; context windows docs.) But the one line that matters, "never run the saw with the guard removed", is buried in the middle of 190,000 tokens, and the answer leaves it out. No error, no warning. The model simply did not use it.

What you just traced has a name. The context window is all the text the model can reference when generating a response, including the response itself; it is the model's working memory, distinct from its training data. Everything in the request counts: the system prompt, every message, tool results, documents and tool definitions (context windows docs). The window is measured in tokens, as in the table.

The two failures are the two limits a long conversation hits: the hard limit, where the request fails, and the soft limit, where answers get worse before it fails.

How big a window is depends on the model: some offer up to 1M tokens, others 200k, so check the model table (context windows docs).
Why this works

The model can only use what is in the request, so anything outside it does not exist for that call. And its attention is spread over every token in the window: each token draws down a limited attention budget, so a full window both runs out and gets noisy (Anthropic Engineering). The goal is the smallest set of high-signal tokens, not the largest set you can fit.

A common mix-up

"If the request fits in the window, more context can only help." It is tempting because more text feels like more safety. But as the token count grows, accuracy and recall degrade, an effect often called context rot (Anthropic Engineering). The 190,000-token request above fit and still lost the safety line.

2. What carries from step to step 5 min

A student writes: "Is the laser cutter free Friday, and book me 2 pm." Here is the loop, with the list your program keeps. Token counts are illustrative.

messages = [{"role": "user", "content": "Is the laser cutter free Friday, and book me 2 pm."}]
# CALL 1: system + tools + messages            -> about 1,030 tokens in
#   model replies: tool request check_calendar
messages.append(model_reply)                    # +70 tokens
messages.append(tool_result)                    # +1,500 tokens (the calendar)
# CALL 2: everything above, resent             -> about 2,600 tokens in
#   model replies: tool request book_slot
messages.append(model_reply)                    # +80
messages.append(tool_result)                    # +120 (confirmation)
# CALL 3: everything above, resent again       -> about 2,800 tokens in
#   model replies: "Booked, Friday 2 pm."

Trace it. At call 1 the model sees only the question, the system prompt and the tool definitions: 1,030 tokens. It asks for check_calendar. Your program runs it, appends the model's request and the 1,500-token result, and makes call 2. The model starts that call knowing nothing about call 1 except what is in the list, so the list carries all of call 1 and the new result. Call 3 does the same again with the booking.

Add the three input counts: 1,030 + 2,600 + 2,800 = 6,430 tokens, though the conversation ended at only 2,800. The first call's tokens were paid for three times. That is why cost per request grows faster than the conversation does. (Resent text can sometimes be cached at a different price, but cached text still fills the window, so the window limits above are unchanged: context windows docs.)

This has a name: accumulating history. Each step is a fresh call; the model keeps nothing itself, and the program resends all previous history plus the new message every time, with the model's output becoming part of the next input. A longer history therefore means more input tokens on every later step (context windows docs).

Why this works

The model keeps no state between calls, so the only memory inside a task is the list your program sends again. Every call is billed for the whole list, which is why one oversized tool result keeps costing you on every step after it arrives.

A common mix-up

"The model remembers what happened in the earlier steps, so I pay for each step's new text once." It feels that way because the answer in call 3 refers back to call 1. But the model only "remembers" because your code put call 1 back into the request. Delete the list and the memory is gone.

3. When the window fills 4 min

A long booking chat has run for 40 messages. The list has reached 150,000 of the 200,000 tokens the model allows, and every call now resends all of it. The program does this:

  1. Before: 40 messages, 150,000 tokens.
  2. Ask for a summary. The program sends the history to the model with the instruction "summarize this chat for continuing it". The model writes about 600 tokens: wants the laser cutter on Friday 2 pm; booked slot 41; still needs 3D printer info.
  3. Fresh window: system prompt (400) + summary (600) + the student's latest message (about 100) = about 1,100 tokens. Tool definitions ride along too, so about 1,700 in practice.

The chat continues from 1,700 tokens instead of 150,000. Cheaper, and with far less text to search through. The summary call itself sends the full 150,000 tokens once, so it pays for itself only if the chat goes on. The program counts tokens before each call and compacts at a threshold, say 75% of the window; without that check, the next call over the limit simply returns the 400 error from Section 1.

Now the failure. Forty messages earlier, the student said they had not yet completed the safety quiz. The summary left that line out. Ten messages later the assistant cheerfully offers a booking on the table saw, because nothing in the new window says it should not. Nobody sees an error; the fact just vanished.

How to reduce the risk: tell the summarizer exactly what to keep, namely bookings, constraints and open questions, and re-test it on a chat where you know the answer. And do not trust any summary with a safety rule: Section 4 shows where such facts should live instead.

This technique is compaction: summarize a conversation that is nearing the limit and continue in a fresh window with the summary. Its failure case is that overly aggressive compaction can lose subtle but critical context (Anthropic Engineering).

Why this works

Most old messages are no longer needed word for word, so a short summary keeps the thread at a fraction of the tokens. That also leaves less noise for the model's limited attention. But a summary is lossy by design: whatever the summarizer judges unimportant is gone for good.

4. Between sessions: notes as memory 5 min

Monday. A student chats about the laser cutter and mentions they prefer evening slots. Here is what the program and model do.

  1. The session starts. The model asks to view /memories. The program returns an empty listing: this is the student's first visit.
  2. During the chat the model asks to create /memories/profile.md with one line: prefers evening slots; asked about 3D printer.
  3. The program writes the file. The session ends, and the context is thrown away, all of it.

Thursday. A new session starts with an empty window. The model asks to view /memories, reads profile.md and offers evening slots without being told. The file, not the model, carried the memory.

The model never touches a disk. It only asks for file operations, and your program runs them against storage it controls. The student's id comes from the signed-in session in your program, never from model output, so one student can never read another's notes.

This is notes as memory: nothing survives between sessions unless the application saves it, so the agent writes structured notes outside the context window and reads them back later. In Anthropic's memory tool the model only requests file operations and the application runs them, so memory lives entirely in the application (memory tool docs, Anthropic Engineering).

Notes need care. The application must:

  • restrict every path to the student's own memory directory, refusing something like /memories/../../secrets.env;
  • cap file sizes and expire stale files, because a note is read back into the window and a huge file would bring back the cost and noise of Section 1;
  • keep sensitive data out (memory tool docs).
A common mix-up

"If a note says the student is certified, they are certified." Notes are written by the model, and a model can be wrong or out of date, so a note is not a verified record. Training status, who may use which machine, comes from the makerspace's official training records, the staff-maintained system. A note "certified on laser cutter" is a hint to speed up the chat, never a permission.

So the booking tool checks the official record before it books. The code, not the model's note, enforces the permission:

def book_slot(student_id, machine, slot):
    if machine not in training_records.certified(student_id):  # staff system
        return {"error": "not certified on " + machine}
    ...
Why this works

The model cannot keep anything after the call ends, but the application can. File operations let the model decide what is worth saving, while the application stays in control of storage and access.

5. Finding the right page: retrieval 5 min

A student asks: "What speed do I use to cut 3 mm acrylic on the laser cutter?" The twelve manuals total about 80,000 tokens. Option one is to paste them all into every call. By Section 1 and Section 2 you know the price: 80,000 tokens on every call, and the answer buried in noise.

Option two, step by step (illustrative numbers):

  1. The prompt holds an index, not the manuals. System prompt (400) plus index (manual name, section titles, page IDs: 500), with tool definitions (600) and the question (30), makes call 1 about 1,530 tokens.
  2. The model calls search_manual(machine="laser", query="acrylic 3 mm speed").
  3. The program runs the search and returns the two best pages, 1,200 tokens, each with manual name and page title.
  4. The model answers and cites the page. This call carries about 2,800 input tokens (1,530 + 70 for the request + 1,200 for the pages).

Two calls cost about 4,300 input tokens. Preloaded, one call would carry about 81,000, and in a longer chat that cost repeats on every later step (Section 2). Retrieval is justified by cost and accuracy here, not by the hard limit, because 80,000 tokens would still fit in the window.

The retrieved pages stay in the list and are resent on later calls, like any tool result (1,200 tokens x 5 more calls = 6,000 extra input tokens in a 6-call run), so return only the best pages.

How search_manual picks pages can be as simple as a keyword match over page titles and text; the model chooses its query from the index and the tool's description. Retrieval is memory too: the store remembers what the manuals say, written by staff, while notes remember what happened with this student, written by the assistant. Both live outside the window.

Now the failure. A different student asks about "settings" and the model searches query="settings". The search returns a page from the 3D printer manual, and the model answers from the wrong machine. The fix has two parts. Write a clear tool description that says what each argument is for, so the model always passes the machine. And return the manual name and page title with every result, so the model can tell it has the wrong page and search again.

Retrieval has a cost, too: runtime lookup adds a step, so it is slower than pre-computed data. The usual answer is a hybrid: always preload the short safety rules, and retrieve the long manual pages.

This is just-in-time retrieval: keep lightweight references (file paths, queries, page IDs) and load content at runtime with tools, rather than preloading everything. The manuals, kept outside the window and fetched on demand, are the retrieval store. The trade-off is that runtime exploration is slower and needs good tool guidance to avoid wasting context (Anthropic Engineering).

Why this works

The window is scarce and noisy, so putting only the needed pages in it at the moment of need keeps answers sharp and cheap. The index tells the model where to look, so it can fetch a page instead of guessing.

Worked example and practice 4 min

Worked example

Decide where each item of the makerspace assistant should live: system prompt and tool definitions; the 12 manuals; a student's training status; a student's preferred time of day; the current chat's tool results.

  1. Estimate the window use (S1). Prompt and tools: 1,000 (400 + 600). Manuals: 80,000. A status line: tiny. Tool results: 1,500 each.
  2. What is resent each step (S2)? Everything in the window. The 1,000 is small and constant. The 80,000 would hit every call. Tool results pile up.
  3. Long chats (S3). Compact near the limit, and the summary must keep bookings, constraints and open questions.
  4. Notes or official record (S4)? Preferences go in notes. Training status stays in the official record, checked by the booking tool's code.
  5. Preload or retrieve (S5)? Short safety rules and hours are preloaded. The manuals are retrieved.

Summary 1 min

Five ideas:

  • Context window: everything the model can see in one call, its own answer included, with a hard limit (the request fails) and a soft limit (answers get worse first).
  • Accumulating history: the model keeps nothing; your program resends the whole list on every step, so every token stays on the bill.
  • Compaction: summarize an old chat and continue fresh, but a summary is lossy.
  • Notes as memory: the application saves files between sessions; notes help, but permissions come from an official record checked by code.
  • Just-in-time retrieval: keep an index in the window and fetch the page at the moment of need; preload only what is small and always needed.

Say it in your own words: without looking, explain to a teammate why the assistant should not paste all twelve manuals into the prompt, using both the cost and the accuracy argument.
