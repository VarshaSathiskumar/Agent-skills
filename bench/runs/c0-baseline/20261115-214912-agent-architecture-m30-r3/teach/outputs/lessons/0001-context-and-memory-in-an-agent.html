Context and memory in an agent

By the end of this lesson you can say exactly what your makerspace assistant "knows" at each step and in each new session, and decide where each kind of information should live: in the context, in saved notes, or in a manual it looks things up in.

Why this matters for you

The context window 5 min

Start with a concrete case. A student types: "How do I change the focus lens on the laser cutter?" Before the model writes a single word, the program builds one big block of text to give it. It contains:

  • the system prompt: your instructions ("You are the makerspace assistant. Be brief. Never book without confirming.");
  • the tool definitions: the name, description and parameters of each tool;
  • the conversation so far: the student's messages, the assistant's replies, and every tool request and tool result.

All of that, plus the reply the model is about to write, is the context: the set of tokens the model sees when it generates text. The context window is the limit on how many tokens fit. Anthropic's documentation describes it as the model's "working memory" and says that everything in the request counts toward it: the system prompt, every message including tool results, your tool definitions, and the model's own output (Claude docs: Context windows). A token is a small piece of text, roughly a word or part of one; models read and write in tokens, and you pay per token.

The most important fact in this lesson comes next, and it is easy to get wrong: the model keeps nothing between calls. Each call is independent. The only thing the model "remembers" is whatever the program puts into the context for that call. If a fact is not in the context, then for that call it does not exist, unless it was learned in training.

"Working memory" is an analogy: like yours, it is small and holds only what you are thinking about right now. Unlike yours, it is wiped after every call and rebuilt by your program.

A bigger window is not a better memory

Windows are large now: the current Claude models list windows of up to 1 million tokens (Claude docs). It is tempting to think that this settles the memory problem: paste everything in. The docs say otherwise: "more context isn't automatically better. As token count grows, accuracy and recall degrade, a phenomenon known as context rot."

Anthropic's engineering team explains it with an attention budget: the model spends some of its limited attention on every token it reads, so each extra token leaves less for the others. Their goal is "the smallest possible set of high-signal tokens" that gets the job done (Effective context engineering for AI agents). Choosing what goes in is called context engineering, and it is the main design job in this lesson.

A common mix-up (M7)

"If the window is big enough, put everything in and the model will use it all." It is tempting because a bigger window sounds like a bigger brain. But the window only limits what fits. Recall gets worse as the window fills, and you pay for every token on every call (next section). If your assistant gets 40 manuals pasted into each request, it pays more and finds the right page less reliably than if it got one page.

What is kept between steps 6 min

Inside one request, the agent loop makes several model calls. What carries over from one call to the next? Only what the program appends to the context. Trace "Is the laser cutter free tomorrow at 3 pm, and do I need training?" with these token counts (invented round numbers, to make the arithmetic easy):

CallContext containsInput tokens
1system prompt and tools (2,000) + question (100)2,100
2call 1's input + tool request (50) + calendar result (250)2,400
3call 2's input + tool request (50) + manual passage (1,500)3,950
4call 3's input + tool request (50) + training record (100)4,100

Two consequences follow, and both matter for your budget.

  1. Cost grows faster than the number of steps. Every call re-sends the whole context, so a result that enters early is paid for again at every later call. A 1,500-token manual passage costs 1,500 tokens at call 3 and again at call 4. The docs note that prompt caching changes what you pay for repeated tokens, not whether they occupy the window (Claude docs), so caching helps the bill but not the rot.
  2. Tool results are the big spenders. The model's own requests are tiny. A search that returns a whole manual chapter is not. Design tools to return small, useful results: the right passage, not the whole manual.
When a run gets long, a lightweight fix is clearing old tool results that are no longer needed. Anthropic calls this the "lightest form" of compaction, and the API offers it as "tool result clearing" (engineering post, docs).

What is kept between sessions 4 min

A session is one conversation: from the student's first message until they leave. Between sessions the context is gone. Next week, the same student starts a new chat, and the model sees a fresh context with your system prompt and their new question. It has no idea they asked about the laser cutter last Tuesday.

A common mix-up (M3)

"The assistant remembers me from last time." It is tempting because chat apps you use feel like they do. Some apps do add saved memory behind the scenes, but that is extra machinery someone built, not something a model does by itself. The basic API gives the model nothing from earlier conversations. For your assistant, remembering is a feature you design.

So anything that must survive a session has to be stored by your program outside the model, and put back into the context when needed. Anthropic's memory tool is one pattern: the model gets a tool for reading and writing files in a memory directory, and the application, not the model, carries out those file operations on storage it controls (Claude docs: Memory tool). That matches what you learned about the loop: the model requests, the program acts.

Deciding what to save, for the makerspace

InformationWhere it should liveWhy
"Is this student trained on the laser cutter?"A database, read by a toolIt must be exactly right and current. A note could be stale or wrong; a lookup is the source of truth.
"This student prefers morning slots"A short saved noteIt is soft, small and useful; a wrong note costs little.
The last 10 messages of this chatThe contextIt is needed right now and is short.
The full chat from last TuesdayUsually nowhereStoring and re-sending it costs tokens every session, and it holds mostly noise.

The rule of thumb: facts that must be correct go in a tool-backed source of truth; small preferences go in notes; everything else gets forgotten on purpose, because every token you keep is paid for again and competes for attention. Also treat saved student data with care: store only what the assistant needs, and ask your university what rules apply.

Retrieval: finding the right page in a long manual 6 min

The manuals are too big, and too costly, to put in every context. Retrieval means looking up only the relevant pieces when a question arrives and putting just those in the context. The usual recipe is called retrieval-augmented generation (RAG), and it is memory in the sense that the manual is a long-term store the assistant can consult.

Three pieces, in plain terms (Anthropic: Contextual Retrieval):

  • Chunking: splitting each manual into pieces, usually no more than a few hundred tokens. Where you cut matters. A chunk that starts mid-procedure, or lacks the machine's name, is hard to find and hard to use.
  • Embedding search: a model turns each chunk into a list of numbers (a vector) that captures its meaning, and does the same to the question. Chunks whose numbers are close to the question's are returned. It finds "swapping the lens" when the student writes "replace the focusing optic", because the meaning is close, not the words.
  • Keyword search (BM25): an older method that matches exact words and phrases. It shines on unique identifiers. Anthropic's example is a query for "Error code TS-999", which embeddings may miss but keyword search finds. For you: "error E-17" or "part LC-4417".

Real systems often combine both, and Anthropic reports the top-20 retrieval failure rate falling from 5.7% to 2.9% when contextual embeddings and keyword search are combined, and to 1.9% with reranking added (same post). Treat those as one team's results on their own data, not a promise for yours.

A common mix-up (M8)

"Embedding search is the modern way, so keyword search is obsolete." It is tempting because "search by meaning" sounds strictly smarter. But exact strings such as error codes and part numbers have little meaning to match, and keyword search finds them reliably. Machine manuals are full of them.

Do you need retrieval at all?

Check the size first. Anthropic's advice: if your knowledge base is smaller than about 200,000 tokens, you can often put the whole thing in the prompt, and prompt caching makes that faster and cheaper (Contextual Retrieval). For a makerspace with a dozen short manuals, that may be true, and it would be a simpler design to defend. But by context rot and per-call cost, retrieval of a few chunks may still be better value as the manuals grow. Measure your manuals in tokens before you decide.

Retrieval as a tool: "just in time"

In an agent, retrieval is usually a tool: search_manuals(query, machine). The model decides when to call it, and the program returns a few chunks. Anthropic describes this as just-in-time retrieval: the agent holds lightweight references and loads data only when needed, instead of preloading everything (engineering post). Your tool description matters here: it is how the model knows when searching is the right move.

Notes, compaction and sub-agents 3 min

Some tasks run longer than one context can comfortably hold, such as a coding agent working on your booking script for hours. Anthropic describes three techniques (engineering post):

  • Compaction: when the conversation nears the window limit, summarize it and continue in a fresh window with the summary. You trade detail for room. The risk is a summary that drops something you needed.
  • Structured note-taking: the agent writes notes to a store outside the context and reads them back later. This is memory by files: "what I have done, what is left, what I decided". The next session, or the next window, starts by reading the notes.
  • Sub-agents: a lead agent hands a focused task to a helper that works in its own clean context and returns a short summary, often 1,000 to 2,000 tokens. The lead's context stays small. Whether that is worth the extra cost is a later lesson.

For your assistant, a typical request is short, so compaction and sub-agents are probably overkill at first. Notes matter more, because they are the simplest way to carry a small amount of information across sessions.

Worked example and practice 6 min

Worked example

Decide what the assistant keeps for this request: a returning student, Dana, writes, "Book me the 3D printer for Saturday morning, same as last time. And how do I clear a nozzle jam?"

  1. List what the model must know for this call. The request, the booking and manual tools, Dana's training status for the 3D printer, her usual slot ("same as last time"), and the jam procedure.
  2. Sort each fact by how it must be stored. Training status must be correct: a tool-backed lookup. "Same as last time" is a soft preference: a short saved note (for example "Dana usually books Saturday 9 to 11"). The jam procedure is in the manual: retrieval.
  3. Decide what enters the context. System prompt and tools (always). Dana's note (a few tokens), loaded at the start of the session. The training result (small), only because the assistant called the tool. The best two or three chunks about nozzle jams, not the manual.
  4. Decide what is left out. The rest of the manual, last week's chat, and the other machines' pages. They would cost tokens at every call and dilute attention.
  5. Decide what is saved at the end. If Dana's booking changed her usual slot, update her note. Nothing else is stored. The new booking is saved by the booking tool in the booking system, which is the source of truth for it.

Summary 2 min

  • The model keeps nothing between calls. The context, rebuilt by the program, is all it sees, and it must fit the context window.
  • Between steps, the context grows and is re-sent at every call, so large tool results cost more than they first appear and bigger windows suffer context rot.
  • Between sessions, nothing survives unless you store it: facts that must be right in a tool-backed source of truth, small preferences in notes.
  • Retrieval finds the right chunks of a long manual; keyword search finds exact codes, embeddings find meaning, and a small enough manual may not need retrieval at all.
