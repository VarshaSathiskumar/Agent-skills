Context and memory in an agent

By the end of this lesson you can take any piece of information in the makerspace assistant and say where it lives: in the context on every step, fetched when needed, or saved between sessions.

Objective O3: context window, what is kept between steps and sessions, retrieval and notes as memory About 30 minutes
Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small model budget. Both problems are context and memory problems, and you will have to defend your choices at the design review.

Warm-up 3 min

Two questions from your earlier work on the agent loop. Answer each in your head or on paper before you open the answer.

Recall

Check your answer

The program runs it. The model only writes a request that names the tool and its arguments. The program then sends the result back as new input and calls the model again. That last part is today's topic: what exactly does the program send each time?

Recall

A student asks, "Is the laser cutter free tomorrow, and do I need training?" The model calls two tools and then answers. How many times is the model called?

Check your answer

Three: one call per tool request, plus one for the final answer. Every step is a separate model call. Today we find out what each of those three calls contains.

The context window 5 min

Start with one concrete moment. A student types: "How do I change the blade on the band saw?" Before the model writes a word, the program must hand it something to read. What goes in?

Everything the model can read when it writes is called its context. The context window is the limit on how much text that can be: the model's working memory. Anthropic's documentation defines it as all the text a model can reference when generating a response, including the response itself, and says it is different from the data the model was trained on (Claude docs: Context windows).

Size is counted in tokens, the small pieces of text a model reads and writes. A token is often a short word or a part of a longer one, so a page of a manual is a few hundred tokens. Everything in the request counts toward the window: the system prompt, every message including tool results, and the tool definitions, plus the output the model writes (Claude docs).

That last point is the one to hold on to. The model does not look anything up by itself and does not "know" your makerspace. Whatever is not in the context on this call, it cannot use.

Context windows have grown large: the docs list up to 1 million tokens for current Claude models. That is room, not a reason to fill it, as the section after next explains.

What is kept between steps 6 min

Now the agent loop from your last session. The assistant makes several model calls for one student request. Does the model remember step 1 when it reaches step 2?

No, not by itself. Each call is separate. What carries a step into the next is the program: it keeps a growing list of messages and sends the whole list again each time. The docs describe it this way: each turn's input contains all previous conversation history plus the new message, and what the model generates becomes part of the input for the next turn (Claude docs). Tool results are messages too, so they stay in that list.

Here is one request, with invented but plausible token counts so you can see the effect. The student asks: "Is the laser cutter free Friday at 3 pm, and what do I need to know about the lens?"

Model callWhat is newTokens sent in
1System prompt and tool definitions (2,500), question (50)2,550
2Call 1's tool request (60), calendar result (400)3,010
3Call 2's tool request (60), three manual pages (3,000)6,070
4Call 3's final answer (160) — if one more tool were called, its request and result would be added instead6,230 or more

Look at what happened. The new information across the whole request is about 3,500 tokens, but the model read about 17,800 tokens in total (2,550 + 3,010 + 6,070 + 6,230), because every call re-reads everything before it. The manual pages fetched in call 3 are paid for again in call 4, and in every later call.

That is the first thing that matters for your budget: cost grows with the length of the context, and each step re-sends it. A tool that returns a whole manual instead of three pages makes every later step in that request more expensive. (Prompt caching can lower the price of re-sent text, but cached text still takes up room in the window; Claude docs.)

A common mix-up

"The model remembers what happened earlier in the request." It feels true because the conversation reads smoothly. But the model has no memory of its own between calls. It looks as if it remembers because the program re-sends the earlier messages every time. If the program forgot to include a tool result, the next call would behave as if the tool had never been run. Memory in an agent is something the program builds, not something the model holds.

When the context gets too big 5 min

A long request, or a long chat with one student, makes the context grow. Two problems follow.

Cost. You saw it in the table: every step pays for everything before it.

Quality. More context is not automatically better. Anthropic's engineers describe context rot: as the number of tokens grows, the model's ability to recall information from the context decreases, gradually rather than at a sharp cutoff. They recommend aiming for "the smallest set of high-signal tokens that maximize the likelihood of your desired outcome" (Anthropic: Effective context engineering for AI agents). The Claude docs say the same: curating what is in context is as important as how much space is available.

Think of a desk. A big desk lets you spread out more paper, but the more paper you have, the harder it is to find the one sheet you need.

A common mix-up

"With a big enough context window, I can paste in all the manuals and be done." It is tempting because it is simple, and a window of a million tokens could hold many manuals. But every step re-sends them, so you pay for them again and again, and the model finds the right page less reliably as the context fills. A big window is room to use carefully, not a plan.

When the context does grow too large, there are three standard moves. All three are described in the same Anthropic article:

MoveWhat it doesMakerspace example
Clearing old tool resultsDrops results the model has already used. The lightest touch.The three manual pages from call 3 are removed once the answer is written.
CompactionSummarizes the conversation so far and continues with the summary in a fresh window.A 40-message chat with one student becomes a short paragraph: who they are, what they are booking.
Sub-agentsA helper works in its own clean context and returns a short summary.A helper reads a 200-page manual and returns the five relevant lines. (Lesson on multi-agent systems comes later.)

Compaction has a cost: whatever the summary leaves out is gone from the context. Anthropic describes tuning it by first making sure the summary keeps everything important, and only then trimming (Anthropic). For a makerspace chat, "the student has not done the laser safety course" is exactly the kind of line a bad summary might drop.

What is kept between sessions: notes 5 min

A student finishes chatting on Monday. On Thursday they come back. What does the assistant know?

By default, nothing. The message list lives in the program's memory for one session. When the session ends and a new one starts, the new context holds the system prompt, the tools and the new question, and nothing else. The model does not carry anything over, and no model weights change, because chatting with a model does not train it.

A common mix-up

"The assistant automatically remembers every student it has talked to." Chat products can feel this way, because they may store things for you. A model itself keeps nothing. If the makerspace assistant should know on Thursday that a student passed the laser safety course on Monday, your program must save that fact somewhere and load it into the context of the new session.

The idea has a simple form: notes, or structured note-taking, where the agent writes information to storage outside the context window and reads it back later. Anthropic gives examples such as a to-do list or a NOTES.md file, and describes a game-playing agent that kept maps and strategy notes so it could keep going after its context was reset (Anthropic).

Anthropic's memory tool is one version: a set of file operations (the model asks to create, read or edit a file, and your program does it), with the files kept on your side, so you choose where they are stored (Anthropic: Context management). The mechanism is the one you already know. Saving a note is a tool call, and reading it back is a tool call.

Lilian Weng's well-known overview of agents uses the same split in older terms: the context is the agent's short-term memory, and an external store the agent can read and write is its long-term memory (Weng: LLM Powered Autonomous Agents).

Notes have two weak points worth knowing before the design review. First, they can go stale: a note that says "laser course passed" is right until the makerspace changes its rules. Second, notes you load take context space, so keep them short. A useful rule: save what the assistant cannot look up, and look up what can change. The booking calendar and an official training database are better asked through a tool each time than copied into notes. Your own experience with a chatbot stating an outdated fact is exactly this failure.

Retrieval: finding the right page 5 min

Back to the manuals. The laser cutter manual has 120 pages. A student asks about replacing the lens. You cannot put 120 pages in every call, and you saw why. So how does the assistant find the right two pages?

Retrieval means fetching only the pieces of a large collection that look relevant to the current question and putting those into the context. In the agent loop, retrieval is just another tool. The model writes search_manuals(machine="laser cutter", query="replace lens"), the program searches, and the best few chunks (passages cut from the manual, for example one section each) come back as the tool result.

How does the search choose? Two common ways. Keyword search matches the words in the question to words in the chunks, so "lens" finds chunks that contain "lens". Embedding search turns each chunk and the question into a list of numbers that stand for meaning, so "swap the focusing optic" can find a chunk about "replacing the lens" even with no shared words. You do not need the math (it is out of scope for you); it is enough to know the two options and that they can be combined. Weng's overview names this idea for long-term memory too: an external store searched quickly for what is relevant (Weng).

There is a second way to retrieve that Anthropic describes: just-in-time retrieval. Instead of preparing a search index ahead of time, the agent keeps lightweight pointers, such as file names and links, and loads content at runtime using tools. Names and folders also carry hints, for example laser_cutter/maintenance.pdf already suggests what is inside. The trade-offs are that exploring at runtime is slower, and it needs good guidance so the agent does not waste context wandering. Anthropic notes that a hybrid works well: some material loaded up front, the rest fetched on demand (Anthropic).

A common mix-up

"Retrieval means the model searches its own memory." The model does not hold the manuals. Retrieval is a program-side search, started by a tool call, that places text in the context. If the search returns the wrong chunk, the model answers from the wrong chunk, confidently. So test your search on real student questions before you blame the model.

Check yourself

A student asks how to "swap the focusing optic" on the laser cutter. The manual only ever says "replace the lens". Which search is most likely to find the page?

Show the answer

The third option. Embedding search matches meaning, so it can bridge different words. In practice, many systems combine both kinds, and you can test which works for your manuals.

Worked example and practice 7 min

Now put it together. The skill is a sorting question you can ask of any piece of information: does the model need it on every step, only sometimes, or after the session ends?

Worked example

A student returns on Thursday and asks, "Can I book the laser cutter Friday at 3 pm? I did the course on Monday." Place each piece of information.

  1. The rule "never book without training." The model needs it on every call, and it rarely changes: put it in the system prompt. It costs a few tokens per step, and that is worth it.
  2. The booking tool's description. Also needed on every call, because the model can only choose tools it can see: it goes in the tool definitions.
  3. The laser cutter manual. Large, and needed only for some questions: retrieval. Fetch two chunks when asked about operating the machine, and not here, since this question is about a booking.
  4. Friday's availability. It changes constantly, so never store it. Ask the calendar tool each time.
  5. "Did the course on Monday." The student says so, but the claim can be wrong, and your notes could be stale. The reliable move is to check the official training record through a tool, and keep the student's statement only as a hint.
  6. "Prefers afternoons." The assistant cannot look this up and it is useful on a return visit: save it as a note at the end of the session, and load it at the start of the next.

Check the cost: by sorting this way, only the rule and the tool definitions are paid for on every step. Everything else enters the context only on the step where it is needed.

Summary 2 min

  • The model sees only its context, limited by the context window. What is not in it, the model cannot use.
  • Between steps, the program re-sends the whole message list each call. So cost grows with every step, and big tool results are paid for again and again.
  • More context is not better: context rot makes recall worse. Keep tool results small, then clear or compact when needed.
  • Between sessions, nothing is kept unless your program saves it: notes in storage outside the context, read back later. Save what cannot be looked up; look up what can change.
  • Retrieval is a program-side search, started by a tool call, that brings only the relevant chunks into the context.
