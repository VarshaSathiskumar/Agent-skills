Choosing HTTP methods and status codes for REST operations

By the end of this lesson you can take a plain-English API operation, such as "replace a user's profile" or "the email is already taken", pick the right HTTP method and status code, and explain your choice in a sentence.

Objective O2: choose HTTP methods and status codes, and explain how each method behaves About 30 minutes Builds on your earlier work on resources and URIs (O1)
Why this matters for you

You want to design APIs that a frontend can rely on, and justify your choices. The URL says what you are talking about. The method and the status code say what you want done and what happened. If those are wrong, every client has to guess.

Warm-up 2 min

Recall

From your work on resources and URIs: in a bookstore API, what is the difference between /books and /books/42, and why does neither path contain a verb like /getBook?

Check your answer

/books is the collection; /books/42 is one book inside it. The path names a thing (a noun). Today's lesson supplies the verb: the HTTP method. So GET /books/42 reads that book and DELETE /books/42 removes it, with the same path both times.

Methods are verbs; two properties sort them 4 min

Start with an everyday case. You are at a library desk. You can look up a book's record, hand in a new book for the shelf, replace a damaged record with a fresh one, or remove a record. Each is a different request, and the clerk handles each differently. HTTP works the same way: the method (also called the verb) tells the server what kind of action you want on the resource named in the URL.

Two properties help you choose, and you will use both all lesson.

A method is safe if it is meant only to read and not to change anything on the server. Looking up a record is safe. A method is idempotent if sending the same request once or ten times leaves the server in the same state. A light switch labelled "turn on" is idempotent: pressing it five times leaves the light on. A "toggle" switch is not: press it twice and you are back where you started. (Definitions follow MDN's glossary entry for idempotent.)

Idempotency matters because networks fail. If you send a request and the connection drops before the reply arrives, you do not know whether the server received it. With an idempotent method, the client can simply send it again. MDN puts it this way: a client can safely retry an idempotent request when there is doubt about whether it reached the server (MDN: HTTP request methods).

MethodPlain meaningSafe?Idempotent?
GETRead a resourceYesYes
POSTSubmit data for the server to process, often creating a new resourceNoNo
PUTReplace the resource with exactly thisNoYes
PATCHApply a partial changeNoNot guaranteed
DELETERemove the resourceNoYes

This table matches MDN's categorization of methods by safety and idempotency (MDN).

The HTTP specification only describes these promises. Your server is not forced to obey them, so you must build them in. A GET handler that deletes rows is legal code and a terrible API: browsers, caches and crawlers assume GET is safe and will call it freely.
Check yourself

A mobile app loses signal right after sending a request, and does not know if it arrived. For which method can the app resend it automatically with no risk of a duplicate effect?

Show the answer

PUT. It is idempotent: the second copy leaves the server in the same state as the first. POST and PATCH offer no such guarantee.

GET and POST 4 min

GET: read, and change nothing

Use GET to retrieve a resource or a collection. It carries no body, it must not change data, and it is safe to repeat. Because it is safe, caches and browsers may store its responses.

GET /books/42        -> one book
GET /books?author=Le+Guin   -> a filtered collection

Filtering, sorting and searching still use GET, with query parameters, because they only read.

POST: create, or run a process

Use POST when the client sends data and the server decides what to do with it. The classic case is creating a resource in a collection: the client does not choose the new book's ID, the server does. So you POST to the collection, not to the item.

POST /books
{"title": "The Dispossessed", "author": "Ursula K. Le Guin"}

-> 201 Created
   Location: /books/43

Here the server picked ID 43 and told the client where the new book lives in a Location header. Every POST like this creates a new book. Send it twice and you get two books, 43 and 44. That is exactly why POST is not idempotent.

Notice the path /books is the collection you already know from O1. The path stays a noun; the method carries the action.

Check yourself

A customer places an order. The server assigns the order number. Which request fits best?

Show the answer

POST to /orders. The server assigns the ID, so the client addresses the collection.

PUT versus POST, and idempotency 6 min

This is the pair people mix up, because both send a body. The difference is in what the request means.

PUT means: "make the resource at this exact URL look like this body." It replaces the whole current representation of the target resource (MDN). The client already knows the address. POST means: "here is some data, server, handle it", and the server decides the outcome.

A worked contrast

Suppose user 7 has this profile: name "Ana", city "Lyon". The client sends:

PUT /users/7
{"name": "Ana", "city": "Paris"}

After the first request, user 7 is Ana in Paris. After a second identical request, user 7 is still Ana in Paris. Ten requests: the same. That is idempotency. Now compare:

POST /users
{"name": "Ana", "city": "Paris"}

The first request creates user 8. The second creates user 9, a duplicate Ana. Same body, different result each time.

A common mix-up (M1)

"POST and PUT are interchangeable, since both send data." This is tempting because from the client's code the two calls look alike: a URL and a JSON body. But they promise different things. PUT targets a known URL and is idempotent. POST targets a collection or a processing endpoint and is not. Pick wrongly and a network retry can silently create duplicate orders or charge a card twice.

One more point. Because PUT replaces, fields you leave out are gone. If you PUT /users/7 with only {"city": "Rome"}, a strict server treats the new profile as having a city and no name. That is why partial updates need a different method.

Check yourself

The client sends PUT /users/7 with the same body twice. What is the state of user 7 after the second request compared with after the first?

Show the answer

The state is identical. That is what idempotent means for PUT.

PATCH and DELETE 4 min

PATCH: change part of a resource

PATCH applies a partial modification (MDN). To move user 7 to Rome without resending everything:

PATCH /users/7
{"city": "Rome"}

The name stays. Whether a PATCH is idempotent depends on what the patch says. "Set city to Rome" gives the same result every time. "Add 1 to the login count" does not. Because you cannot know in general, the specification does not guarantee it, so treat PATCH as not idempotent unless you design it to be.

Rule of thumb: sending the whole resource, use PUT. Sending only the fields that change, use PATCH.

DELETE: remove it

DELETE /books/42 removes the book. It is idempotent, and here is the subtle part. The first call removes the book. The second call finds nothing and may answer 404. The response differs, but the server state is the same: book 42 is gone. Idempotency is about state, not about getting identical replies.

Check yourself

A client wants to change only a book's price and leave every other field alone. Which request fits?

Show the answer

PATCH to the book's URL with just the price.

Success codes: 200, 201, 204 4 min

The method is the request. The status code is the server's three-digit answer about what happened. The first digit gives the class: 2xx success, 3xx redirection, 4xx the client made a mistake, 5xx the server failed. The full list lives in the IANA registry, and MDN explains each one.

Within success, choose the code that says which success.

  • 200 OK: it worked, and here is the result in the body. The usual answer to GET, and to an update that returns the updated resource.
  • 201 Created: a new resource was created. MDN notes this is typically the response to POST, or to some PUT requests (MDN). Pair it with a Location header.
  • 204 No Content: it worked, and there is deliberately no body. A natural fit for DELETE, or an update where you return nothing.
OperationMethod and pathSuccess code
List booksGET /books200
Add a bookPOST /books201 + Location
Replace a bookPUT /books/42200 or 204
Change the pricePATCH /books/42200 or 204
Remove a bookDELETE /books/42204 (or 200)
A common mix-up (M2)

"If the request reached the server and I handled it, return 200." It is tempting because the HTTP exchange itself worked. But the status code describes the outcome of the operation, not whether the network delivered it. A request that reached your server and found no such book is a 404. One that created a book is 201. If you answer 200 with {"error": "not found"} in the body, every client must open the body to learn it failed, and tools like retry logic, monitoring and caches cannot tell success from failure.

Check yourself

A client deletes a draft post and your server removes it. You have nothing useful to send back. Which response fits best?

Show the answer

204 No Content: success, no body.

Error codes: who made the mistake? 4 min

For errors, ask one question first: whose fault is it? If the client sent something wrong, use 4xx. If your server broke on a good request, use 5xx. That alone tells a frontend whether retrying the same request could ever help.

SituationCode
Malformed request: broken JSON, missing required header400 Bad Request
Not logged in, or bad credentials401 Unauthorized
Logged in, but not allowed to do this403 Forbidden
No resource at that URL404 Not Found
Clashes with current state: email already registered409 Conflict
Well-formed, but fails validation rules: age is -3422 Unprocessable Content
Your server crashed or a dependency failed500 Internal Server Error

MDN describes 409 as a request that conflicts with the current state of the server, and 422 as a well-formed request that cannot be followed because of semantic errors (MDN). The IANA registry lists 422 as defined in RFC 9110 (IANA).

Teams disagree on 400 versus 422 for validation failures. Both are defensible. What matters is that your API picks one and uses it consistently. Consistent error bodies are the next objective (O3).
Check yourself

A signed-in user tries to delete another user's private photo. The photo exists. Which code fits?

Show the answer

403 Forbidden: authenticated but not authorized.

Worked example and practice 6 min

Worked example

A library API. Operation: "A member returns a loan. The loan record 305 should be marked returned: true. Other fields stay." Choose the method and the success code, then name one error case.

  1. Which resource? One specific loan, so the path is /loans/305. (From O1: a noun, an item inside a collection.)
  2. Is it a read? No, it changes data, so not GET.
  3. Does the server pick an address? No, the loan already exists, so not POST.
  4. Whole resource or part? Only one field changes, so PATCH, not PUT. Since it sets returned to true, repeating it gives the same state.
  5. Success code? Nothing was created. Return 200 OK with the updated loan, or 204 if the client does not need it.
  6. An error case: loan 999 does not exist, so 404 Not Found. The client named something absent, which is the client's mistake: 4xx.

Final answer: PATCH /loans/305 with {"returned": true} returns 200; a missing loan returns 404.

Your turn

A shop API. Operation: "A customer replaces their saved delivery address with a completely new one. The address already exists as address 12 for that customer." Step 1 is given: the path is /addresses/12. Now decide:

  1. Which method, and why not the two nearest alternatives?
  2. Which success code?
  3. What code if address 12 does not exist? What if the signed-in customer does not own address 12 and the system refuses?
Show a solution

1. PUT /addresses/12. The whole address is being replaced and the client knows the URL, so PUT. Not POST: the server is not creating anything or choosing an address. Not PATCH: the whole resource is sent, not selected fields.

2. 200 OK with the new address, or 204 No Content. Not 201, because nothing new was created.

3. Missing address: 404 Not Found. Signed in but not the owner and the system refuses: 403 Forbidden.

Summary 2 min

  • The path names the thing; the method names the action. GET reads, POST creates or processes, PUT replaces whole, PATCH changes part, DELETE removes.
  • GET is safe. GET, PUT and DELETE are idempotent: repeating them leaves the same state. POST is not, which is the real difference from PUT.
  • Status codes report the outcome, not delivery: 201 for created, 204 for success with no body, 404 for missing, 409 for a state clash.
  • For errors ask whose fault it is: 4xx is the client's, 5xx is yours.
