Why per-server counters fail 3 min

Suppose your API allows each client 10 requests per second, and you run 3 API servers behind a load balancer. If each server counts in its own memory, one client can send 10 requests to each server and get 30 through. The count must live in one shared place. Redis is a fast in-memory database that every server can reach, so it is the usual choice (Redis rate limiter guide).

A shared counter creates a second problem, a race condition: two actors read and write the same data, and the result depends on who goes first. Say a client has exactly 1 token left. Two servers each do read the tokens, decide, write the tokens back in separate commands:

A common mix-up (M3)

"Every Redis command is atomic, so my GET then SET is safe." Each command is, but another client's command can run between your two. Atomicity has to cover the whole read-decide-write sequence.

Check yourself

Each of 3 servers keeps its own in-memory counter, limit 10 per second. What is the most one client can get through in a second?

Show the answer

Thirty. Each server enforces its own limit of 10, so three servers allow 3 x 10.

The token bucket 3 min

Picture a bucket that holds at most capacity tokens. Tokens drip in at a steady refill rate. Each request takes one token; with none left, the request is refused. An idle client's bucket fills up, so a short burst is allowed, but the long-run average cannot beat the refill rate.

Real code does not drip. It stores two numbers per client, tokens and the time of the last update ts, and on each request works out what dripped in meanwhile:

tokens = min(capacity, tokens + elapsed × rate)

Example. Capacity 10, rate 5 tokens per second. A client has 2 tokens and sends a request 600 ms after the last update. Refill: 2 + 0.6 × 5 = 5 tokens. Spend one: 4 left.

Redis's own guide stores these as a hash with two fields, one key per client such as user:123 (Redis token bucket with redis-py). We will do the same.

Atomic updates with Lua 4 min

Redis can run a small Lua script (Lua is a tiny scripting language built into Redis) on the server. Redis guarantees that a script runs atomically: all other server activity is blocked while it runs, so no other client's command can slip in the middle (Redis programmability). That fixes Figure 1: put read, refill, decide and write in one script.

local key         = KEYS[1]
local capacity    = tonumber(ARGV[1])
local rate        = tonumber(ARGV[2])   -- tokens per second
local cost        = tonumber(ARGV[3])

local t   = redis.call('TIME')          -- Redis's own clock
local now = tonumber(t[1]) * 1000 + math.floor(tonumber(t[2]) / 1000)

local b      = redis.call('HMGET', key, 'tokens', 'ts')
local tokens = tonumber(b[1])
local ts     = tonumber(b[2])
if tokens == nil then tokens = capacity; ts = now end

tokens = math.min(capacity, tokens + math.max(0, now - ts) * rate / 1000)

local allowed, retry_ms = 0, 0
if tokens >= cost then
  tokens = tokens - cost
  allowed = 1
else
  retry_ms = math.ceil((cost - tokens) * 1000 / rate)
end

redis.call('HSET', key, 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', key, math.ceil(capacity * 1000 / rate) + 1000)
return {allowed, math.floor(tokens), retry_ms}

Four design choices to notice:

  • The key comes in through KEYS, the numbers through ARGV. Redis requires every key a script touches to be passed as a key argument, so it works on a cluster too (Scripting with Lua).
  • Time comes from redis.call('TIME'). If each API server sent its own clock, a server whose clock is 2 seconds fast would hand out extra tokens. Redis's guide uses the server clock in its other algorithms for this reason; its token bucket takes the time from the caller, which leaves it exposed to skew.
  • PEXPIRE cleans up. After the time a bucket needs to refill completely, a missing key and a full bucket mean the same thing. Without expiry, every client you ever saw stays in memory. The guide's token bucket sets none.
  • The script returns whole numbers, because Redis turns Lua numbers into integers in replies.
A script blocks everything else while it runs, and Redis does not kill an over-long one on its own. Ours does a handful of fast commands, so it is safe. Never loop over big data in a limiter script.
A common mix-up (M5)

"Each server can pass time.time() into the script." Servers' clocks differ by small, unpredictable amounts. Read the time inside the script so every server shares one clock.

Show the answer

Calling it from Python and answering with 429 2 min

With redis-py, register_script wraps the Lua text in a callable. Redis's guide describes the underlying pattern: load the script once, send later calls by its SHA1 digest with EVALSHA, and fall back to EVAL if Redis has evicted it. Here is a Flask example; any framework works the same way, because every server runs this same code against the same Redis.

import redis
from flask import Flask, jsonify, request

app = Flask(__name__)
r = redis.Redis(host="redis.internal", decode_responses=True)
bucket = r.register_script(LUA_SOURCE)   # the script above

@app.before_request
def limit():
    client = request.headers.get("X-API-Key", request.remote_addr)
    allowed, remaining, retry_ms = bucket(
        keys=[f"rl:{client}"], args=[10, 5, 1])   # capacity, rate, cost
    if not allowed:
        resp = jsonify(error={"code": "rate_limited",
                              "message": "Too many requests."})
        resp.status_code = 429
        resp.headers["Retry-After"] = str(-(-retry_ms // 1000))
        return resp

Status 429 Too Many Requests says the client sent too many requests in a given time, and the response may carry a Retry-After header saying how long to wait (RFC 6585; MDN). Retry-After counts whole seconds, so the code rounds up. The JSON error body keeps the same shape as your other errors, which is what lets a frontend handle it generically.

One decision is yours: if Redis is down, do you let requests through (fail open) or reject them (fail closed)? Most public APIs fail open so a limiter outage is not an API outage. The docs do not decide this for you.

Worked example and practice 2 min

Worked example

Capacity 10, rate 5 per second, cost 1. The bucket holds 0.5 tokens. A request arrives 300 ms later. Allowed? How many tokens remain?

  1. Refill: 0.3 s × 5 = 1.5 tokens, so 0.5 + 1.5 = 2.0. This is under the capacity of 10, so no cap applies.
  2. Check: 2.0 ≥ 1, so the request is allowed.
  3. Spend: 2.0 − 1 = 1.0 token stored. The script returns {1, 1, 0}.
Your turn

Capacity 4, rate 2 per second, cost 1. The bucket holds 0.2 tokens and a request arrives immediately (no time has passed). Is it allowed? If not, what retry_ms does the script return? Step 1 is given: no time passed, so refill adds nothing.

Show a solution

Step 2: 0.2 < 1, so the request is refused. Step 3: tokens missing = 1 − 0.2 = 0.8. Step 4: at 2 per second that takes 0.8 × 1000 / 2 = 400 ms, so retry_ms = 400 and the header says Retry-After: 1 after rounding up.

Summary 1 min

  • The limiter's state must live in shared storage (Redis), not in each server's memory.
  • Separate read and write commands race; one Lua script runs atomically, so read, refill, decide and write happen as one step.
  • Token bucket: store tokens and ts, refill by elapsed time on each request, spend the cost, refuse if short.
  • Take time from Redis, pass keys via KEYS, set an expiry.
  • Refuse with 429, a Retry-After header and your standard error body.
