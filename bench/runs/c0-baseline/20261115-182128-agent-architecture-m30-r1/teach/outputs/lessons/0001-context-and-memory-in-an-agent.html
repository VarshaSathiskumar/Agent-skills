Context and memory in an agent

By the end of this lesson you can say, for any piece of information in the makerspace assistant, whether it belongs in the context window, in a saved note, or in a searchable library, and why.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small model budget. Those are three different memory problems, and each has a different right answer. At your design review you will be asked "what does it keep, and what does that cost?" This lesson gives you the answer.

The context window: everything the model sees 5 min

Start with an example. You hand a friend a sheet of paper and ask a question. They can only use what is written on that sheet. If you want them to remember your last question, you must write it on the new sheet too. They walk away with nothing, and the next time, you hand them a fresh sheet.

A language model works like that friend. The context window is all the text the model can use when it writes a response, including the response itself. The Claude documentation calls it the model's "working memory", and it is different from the huge body of text the model was trained on (Anthropic, Context windows).

Text is measured in tokens: small pieces of text, often a short word or part of a word. The window has a fixed size in tokens. Some current Claude models have a window of up to 1 million tokens (the exact size depends on the model), and the same documentation page lists the sizes.

What is on the sheet of paper

Everything in a request counts toward the window. The documentation lists it: the system prompt, every message including tool results, images and documents, your tool definitions, and the output the model generates.

That includes your tool descriptions. The descriptions you will write for the makerspace tools are not free: they are sent on every single call.

The model does not remember; the program re-sends

Here is the idea most people get wrong first. Between calls, the model keeps nothing. The program around it keeps a list of messages and sends the whole list again on every call. The documentation describes it as progressive accumulation: each user message and each response is added, and earlier turns are preserved completely. Each turn's input is "all previous conversation history plus the current user message".

A common mix-up

"The model remembers the conversation." It feels true because chat apps seem to remember. But the model is called fresh each time, and the app re-sends the earlier text. If the program stopped re-sending a message, the model would have no trace of it. This matters for design: you decide what is on the sheet of paper, and that is where you control quality and cost.

Why it fills up, and why that costs money 5 min

Two problems follow from a window that only grows. One is cost. The other is quality.

Cost: you pay for the sheet every time

Model usage is billed by tokens, and the input tokens of every call count. Since the whole history is re-sent each step, a long run costs more than the sum of what was added. Let us work through the example in Figure 1.

Worked example: counting input tokens

A student asks, "Is the laser cutter free tomorrow at 3 pm, and do I need training?" Assume the instructions and tool descriptions take 2,000 tokens and the question takes 50. The assistant makes three tool calls, so the model is called four times.

  1. Call 1 sees the 2,000 fixed tokens plus the 50-token question: 2,050 tokens.
  2. Call 2 sees call 1's input, plus the model's request for the calendar (60 tokens) and the calendar result (300 tokens): 2,050 + 360 = 2,410.
  3. Call 3 adds the manual-search request (60) and a 3,000-token excerpt from the manual: 2,410 + 3,060 = 5,470.
  4. Call 4 adds the training-record request (60) and a short result (100): 5,470 + 160 = 5,630.
  5. Total input over the request: 2,050 + 2,410 + 5,470 + 5,630 = 15,560 tokens, even though the new information was only about 3,600 tokens.

Now suppose the manual search returned a whole 12,000-token section instead of a 3,000-token excerpt. Call 3 becomes 14,470, and call 4 is 14,630, so the total is 2,050 + 2,410 + 14,470 + 14,630 = 33,560 tokens. One bulky tool result was re-sent on every later call. That is more than double the cost, for one request.

Providers can charge less for a part of the prompt that is identical from call to call (called prompt caching). It changes what you pay for those tokens, not whether they occupy the window (Anthropic docs). Prices differ by model, so check the current pricing page when you do your budget.

Quality: more is not better

You might think a bigger window solves everything: paste in all the manuals. The documentation says otherwise: "more context isn't automatically better". As the token count grows, accuracy and recall degrade, a phenomenon called context rot (Anthropic, Context windows). Anthropic's engineering team explains it with an attention budget: the model has finite capacity to attend to everything in context, and every new token draws it down (Anthropic, Effective context engineering for AI agents).

The same post gives the goal: the smallest set of high-signal tokens that makes the result you want likely. Think of the desk of a student who brings only the pages they need, not the whole shelf.

A common mix-up

"A big enough window means we do not need to choose what to include." It is tempting because a window of a million tokens sounds like it holds every manual you have. But you would pay for those tokens on every call, and the model's recall of any one fact gets worse as the window fills. Choosing what goes in is the design work.

What is kept between steps and between sessions 4 min

"Memory" in an agent is really three different things, with different lifetimes. Keep them apart and most design questions become easy.

Context (short-term)Within one run, across stepsThe program's message list, re-sent each callThe student's question and the calendar result
Notes (saved memory)Across sessionsWritten to a file or database outside the window, read back later"Sam completed laser training on 3 Oct"
A library (retrieval)Permanent, sharedAn indexed store searched on demandThe machine manuals

Between steps

Within a run, what is kept is the message list, as in Figure 1. Nothing special is needed; it is the default, and the cost is the one you counted above.

Between sessions

When the student closes the chat, the message list is gone, unless your program saved it. The next session begins with an empty window. So if Sam finished training last week, the assistant will not know unless something was written down and is loaded again. The model does not do this by itself; you design it.

Keeping the window small 4 min

Within a long run you have a few levers. Anthropic's guide lists them, from lightest to heaviest (Effective context engineering; Context windows).

  1. Make tool results small. The cheapest fix is to not let a big result in. Return an excerpt or the top three passages, not a full manual section. In our worked example this alone halved the bill.
  2. Clear old tool results. Once the model has used the calendar data, the raw result can be dropped from the message list. The post describes clearing old tool results as the lightest form of trimming, and the platform offers it as "tool result clearing".
  3. Compaction. When the conversation nears the limit, the program asks the model to summarize it and starts a fresh window from that summary. Anthropic describes keeping decisions, open problems and key details, and discarding redundant tool output.

Compaction has a price: a summary can leave out something that turns out to matter. The post advises tuning it to keep everything important first, and only then to trim what is superfluous.

For a makerspace chat, most conversations are short: a few questions and a booking. You probably need lever 1 on day one and may never need compaction. Do not build what your usage does not require; a small budget is a reason to keep the design simple.

Retrieval: finding the right page 5 min

The manuals are too long to paste in and too useful to leave out. Retrieval means the assistant searches a library and brings only the relevant pieces into the window when they are needed. The idea was named in a research paper: a model's own knowledge is stored in its training ("parametric memory"), and it can be paired with a searchable index of documents ("non-parametric memory") that a retriever queries (Lewis et al., Retrieval-Augmented Generation). Using a search to bring in text before the model writes is called retrieval-augmented generation, or RAG.

This also answers something you noticed as a chatbot user: a model can state an outdated fact with confidence. A retrieved page is current text placed right in front of the model, so it can answer from the page instead of from old training.

How to prepare a library

Think of a book index. Before any question is asked, you do the preparation once:

  1. Chunk each manual: cut it into pieces, for example by section heading, so each piece is a few hundred words. Small chunks are precise but can lose their surroundings; large chunks keep context but are less focused.
  2. Index the chunks so they can be searched. Two common ways: keyword search (like Ctrl+F, good for exact words such as "kerf" or a part number) and embedding search, where each chunk is turned into a list of numbers that places similar meanings close together, so "how thick can I cut?" finds a chunk that says "maximum material thickness".
  3. Search at question time: the tool takes the question, returns the best three or so chunks with their source (manual and page).

You do not need the math of embeddings, and it is outside your mission. You need the tradeoffs: chunk size, how many results to return, and whether exact words matter.

Load up front, or fetch when needed

The engineering post names a useful choice. Some information is needed in nearly every conversation, so you load it up front: your rules for the assistant, the opening hours. Other information is needed only sometimes, so you keep a lightweight reference and let the agent fetch it with a tool at the moment it is needed, which the post calls "just-in-time" retrieval. Claude Code itself mixes the two: it loads a CLAUDE.md file up front and fetches other files on demand (Effective context engineering).

A common mix-up

"Retrieval means the model has read the whole manual." It has read only the chunks that came back. If the search returns the wrong chunk, the model answers from the wrong page, and may do so confidently. The quality of the answer is capped by the quality of the search, so test the search on real student questions, not only the model's answers.

Notes: memory that outlives the window 4 min

Retrieval is for a library everyone shares. Notes are for what the agent learns during its own work, and must carry forward: something written to storage outside the window, and read back later. Anthropic's post calls this structured note-taking, or agentic memory, and describes it as the agent regularly writing notes to memory outside the context window, to be pulled back in at later turns (Effective context engineering).

The post's example is an agent playing a video game over thousands of steps. It kept notes such as how many levels a character had gained toward a target, what areas it had mapped, and which attacks worked on which opponents. After its context was reset, it read the notes and carried on. For your assistant the same idea is much plainer: a short record per student.

{
  "student": "sam-4821",
  "training": {"laser-cutter": "2025-10-03", "3d-printer": null},
  "preferences": "prefers morning slots",
  "updated": "2025-11-10"
}

This is a file or small database row. At the start of a session the program reads Sam's record and puts it in the window (a few dozen tokens, not Sam's whole history). When a training session is completed, a tool writes the new date. The notes are only as good as what you wrote and how you read it back.

Rules of thumb for notes

  • Save facts you will need again, not transcripts. "Laser training done on 3 Oct" is worth saving; the 20-message chat about it is not.
  • Prefer facts the program can check. Training status should come from the real training record, not from what the model wrote down, so it cannot drift. Let the system of record be the truth and the note a cache.
  • Keep notes short and readable. They go back into the window each session, so they spend your budget as the manuals do.
  • Think about privacy. A note about a student is personal data. Save the minimum, and ask your faculty advisor what the university requires.
A common mix-up

"A bigger window is the same as memory." A window only lasts for one run. Even a huge window is empty at the start of the next session. Memory across sessions needs storage that your program writes and reads.

Worked example and practice 5 min

Now put the three kinds of memory together. For each piece of information, ask three questions: Who needs it (one student, or everyone)? How long must it live (this run, or across sessions)? How big is it (a line, or a document)?

Worked example

Where should each of these live in the makerspace assistant? Fact A: "The laser cutter's maximum material thickness is 9 mm." Fact B: "Sam has a booking on Friday at 3 pm."

  1. Fact A. Who? Everyone; it is in the manual. How long? Permanent. How big? One line inside a long manual. So: the library. The assistant should search for it, and quote the source.
  2. Fact B. Who? One student. How long? Until the booking is over, and the assistant must not guess it. How big? Tiny. It is already kept in the booking system, so the assistant should read it with the calendar tool when asked, not copy it into a note that could go stale.
  3. Check the cost. Neither is put in the instructions, so neither is re-sent on every call. Only what a question needs enters the window.
Your turn

Place each of these three. Use the same three questions: who, how long, how big. The first is done for you.

  1. "The assistant is friendly and always names the manual page it used." Done: instructions, loaded up front, because it is needed on every call and is short.
  2. "Alex told the assistant earlier in today's chat that the project is made of acrylic."
  3. "Alex has passed the 3D printer safety training."
  4. "A 60-page troubleshooting guide for the vinyl cutter."
Show a solution

2. Context only. It matters for this run, it is one line, and the message list already keeps it. Saving it is optional; it would only be worth a note if Alex's project continues next week.

3. Notes, or better, the real training record. It is personal, small and needed across sessions. The best design reads it from the system of record with a tool, so there is one source of truth; a note is a fallback.

4. The library. It is shared, large and permanent. Chunk it by problem heading, index it, and return the top chunks when a student describes a problem.

Stretch: your design review

A teammate says: "Let's just put all the manuals and every student's history in the prompt and use the biggest model." In two or three sentences, write your reply using what you have learned: cost per call, context rot, and what happens at the next session.

Show a sample reply

The prompt is re-sent on every model call, so a big prompt multiplies our cost by the number of steps in each request, and recall gets worse as the window fills. It would also be empty again next session, so student history still needs real storage. Better: keep instructions short, search the manuals and return a few chunks, and load only the current student's small record.

Summary 2 min

  • The context window is everything the model sees on one call: instructions, tool descriptions, messages and tool results. The model keeps nothing between calls; the program re-sends the history.
  • Because the history is re-sent each step, big tool results and long instructions are paid for again on every call, and a fuller window recalls worse (context rot).
  • Three kinds of memory: context (this run), notes (across sessions, written by your program), and a library (shared, searched by retrieval).
  • Keep the window small: return small results, clear old ones, compact only when needed.
  • For each fact ask who needs it, how long, and how big.

Say it in your own words: without looking back, explain to a teammate why the assistant "forgets" Sam between visits, and name the two things you would build so that it does not forget what matters.
