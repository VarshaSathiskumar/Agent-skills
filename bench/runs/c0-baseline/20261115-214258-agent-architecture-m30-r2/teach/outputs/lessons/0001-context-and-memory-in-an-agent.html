Context and memory in an agent

By the end of this lesson you can decide, for each piece of information in the makerspace assistant, whether it belongs in the model's context, in a saved note, or in a searchable manual, and say what each choice costs.

Why this matters for you

Your assistant must answer from long machine manuals and remember each student's training status between visits, all on a small budget. Every one of those needs is a context-and-memory decision, and you will have to defend those decisions at your design review.

The context window 5 min

Start with an everyday case. You ask a friend to help plan a project, but your friend has no memory at all. Each time you want their help, you must hand over a single sheet of paper containing everything they need to know. They read it, write a reply, and forget it all. The sheet has a fixed size.

A language model works like that friend. The text it is given for one call is its context: the set of tokens included when the model writes its reply (Anthropic, Effective context engineering for AI agents). A token is a small piece of text, roughly a short word or part of a longer one. The context window is the maximum number of tokens the model can take in at once, and it is the size of the sheet of paper.

For the makerspace assistant, one call's context holds four kinds of text:

  • the system prompt: your standing instructions ("You are the makerspace assistant. Never book a machine for an untrained student.");
  • the tool descriptions: the names and explanations of check_calendar, search_manuals and the rest, which is how the model knows they exist;
  • the conversation so far: the student's messages and the model's earlier replies;
  • the tool results that came back, such as calendar entries or a manual page.

Two facts follow, and both matter for your budget. First, the model can only use what is in the box. Second, you are billed by tokens, both the ones you send in and the ones the model writes. A bigger box does not just cost more; it also works less well, as section 4 shows.

Tokens are not words. English averages somewhat under one word per token, so 3,000 tokens is roughly 2,000 to 2,500 words. Your model provider's documentation will give a token counter; use it on a real manual page before you plan a budget.

What is kept between steps 6 min

Now put the context window inside the agent loop. In the loop, the model is called once per step. Each call is separate, and the model keeps nothing from the last one. So how does step 3 know what happened at step 1?

The program keeps a running list of everything so far, the transcript: the question, each tool request, each result. On every step, the program sends the whole transcript back in as the context. The model's apparent memory within one request is really the program re-reading the list aloud each time.

Here is one request traced with real counts. The student asks, "Is the laser cutter free tomorrow at 3 pm, and do I need training?" The fixed part of the context (system prompt 800 tokens, tool descriptions 600, the question 50) is 1,450 tokens. Each tool request the model writes is about 40 tokens.

CallWhat is added before itInput tokens
1Fixed part only1,450
2Request (40) and calendar result (200)1,690
3Request (40) and a manual section (3,000)4,730
4Request (40) and training record (100)4,870
Total input across the request12,740

Notice two things. The context grows with every step, because the transcript only ever gets longer. And because each call re-sends the transcript, a big tool result is paid for again on every later call. The 3,000-token manual section cost 3,000 tokens at call 3 and again at call 4. That is why the size of what your tools return is a cost decision, not a detail.

A common mix-up

"The model remembers what it did earlier in the request." It is tempting because the assistant behaves as if it does. In fact the model remembers nothing; the program re-sends the transcript. The proof: if your program forgot to include the calendar result in call 2's context, the model would have no idea a calendar had been checked.

When the window fills up 5 min

Because the transcript only grows, a long enough request or a long enough chat will hit the window's limit. Before that, there is a quieter problem. Research on long contexts finds that as the number of tokens in the window grows, the model's ability to recall information from it declines; Anthropic calls this context rot, and describes the model as having a finite attention budget that every new token draws down. The decline is a gradient, not a cliff (Anthropic). The guiding principle in that article is to find the smallest set of high-signal tokens that gets the job done.

So "put everything in context" is the wrong default, for quality and for cost. When the transcript gets long, a program has three common moves:

MoveWhat it doesRisk
Clear old tool resultsDrops bulky results the model has already used, such as the 3,000-token manual sectionThe model cannot re-read it without calling the tool again
CompactionAsks the model to summarize the conversation, then starts a fresh window holding the summaryThe summary may leave out a detail that matters later
Save notesWrites key facts to storage outside the window (next section)The agent must decide what to write and later read it back

Anthropic describes clearing old tool results as one of the lightest forms of compaction, and advises tuning a compaction prompt first for recall (keep everything that might matter) and then for precision (cut what does not) (Anthropic).

A common mix-up

"A bigger context window means we can stop worrying." It is tempting because a bigger box holds more. But a fuller box costs more on every call and, given context rot, can make answers worse. A window is a budget to spend carefully, not a bin to fill.

What is kept between sessions: notes 6 min

A session is one visit: from the student's first message until the chat ends. When it ends, the transcript is gone, and the context window starts empty next time. The model has learned nothing from the visit, since its training is fixed. So if Sam passed the laser cutter training on Monday and returns on Thursday, a bare assistant would ask Sam again.

The fix is a note: facts the program saves outside the context window, then reads back when they are needed. Anthropic calls this structured note-taking, or agentic memory, with examples like a to-do list or a NOTES.md file the agent keeps, and says it lets an agent keep track of progress across thousands of steps and after context resets (Anthropic). Lilian Weng's survey of agents draws the same line: short-term memory is what fits in the finite context window, and long-term memory is an external store the agent can query (Weng, LLM Powered Autonomous Agents).

For your assistant, a note can be as plain as one record per student:

{
  "student": "sam",
  "trained": ["laser_cutter"],
  "pending": ["3d_printer_safety"],
  "last_visit": "2026-11-12"
}

It works in two moves, both done by your program or by tools the model calls:

  1. Read: when Sam starts a session, load Sam's record and put it in the context (a few dozen tokens).
  2. Write: when something durable happens, such as Sam passing a training, call a tool such as save_note that updates the record.

Two design points for your review. First, write sparingly: notes you save are notes you pay to load later, so keep the facts that will change a future answer (training status) and skip chit-chat. Second, the note is only as good as its read: a saved note that nothing loads is the same as no note.

A student's training status is also a fact that should come from the authoritative record, not from the model's memory of a chat. Treat notes about people as data your program owns and checks, not as something the model is trusted to recall.

Retrieval: finding the right page 5 min

The notes store is small. The manuals are not: a machine manual may run to hundreds of pages, and a student's question needs one or two of them. Retrieval means finding the few relevant pieces in a large store and putting only those into the context.

Think of looking something up in a printed manual. You do not read the whole book to learn the blade speed. You use the index, find page 142, and read that page. An agent can do the same with a search_manuals tool. A common way to search is to turn each chunk of text into a list of numbers called an embedding, so that chunks with similar meaning get similar numbers. The question is turned into numbers too, and the store returns the closest chunks. Weng's survey describes this as a vector store with fast search, usually approximate, giving up a little accuracy for a large speedup (Weng).

There is a second style. Anthropic describes just-in-time retrieval: the agent keeps lightweight pointers, such as file paths, stored queries or links, and loads the actual data at runtime with tools, reading step by step. The trade-off it names is that this is slower than having everything pre-computed, and needs good tools; many tasks suit a hybrid, loading a little up front and exploring the rest (Anthropic).

For the makerspace assistant, the budget argument settles most of it. Compare three designs for "What speed should I set for 3 mm acrylic?"

DesignIn the contextVerdict
Paste the whole manualHundreds of pages on every callCostly, and rot makes the answer worse
Search, return top chunksAbout three chunks, a few hundred tokensCheap; depends on the search finding the right chunk
Search, then read a whole page on demandSmall, then one page if neededCheapest on average; takes an extra step
A common mix-up

"Retrieval makes the model know the manual." It does not. The model learns nothing; retrieval only places a few passages in the box for this one call. If search returns the wrong chunk, the model will answer from the wrong chunk, confidently. That is the same confident-but-outdated behaviour you noticed in chatbots, now caused by a weak search instead of old training.

Worked example and practice 6 min

Worked example

Using the numbers from section 2 (fixed part 1,450 tokens, each tool request 40 tokens), suppose search_manuals is changed to return a 600-token chunk instead of the 3,000-token section. What is the total input across the four calls, and how much is saved?

  1. Call 1 has only the fixed part: 1,450.
  2. Call 2 adds the request (40) and the calendar result (200): 1,450 + 40 + 200 = 1,690.
  3. Call 3 adds a request (40) and the smaller chunk (600): 1,690 + 40 + 600 = 2,330.
  4. Call 4 adds a request (40) and the training record (100): 2,330 + 40 + 100 = 2,470.
  5. Total: 1,450 + 1,690 + 2,330 + 2,470 = 7,940. Before it was 12,740, so the saving is 4,800 input tokens, nearly 40%. The chunk saved 2,400 tokens once at call 3 and again at call 4.
Your turn

A different request: fixed part 1,000 tokens; each tool request 50 tokens. There are four calls. The tool results, in order, are 100 tokens (calendar), 2,000 tokens (manual section) and 100 tokens (training record). Call 1 has only the fixed part, so its input is 1,000. Work out the input of calls 2, 3 and 4, and the total. Then find the new total if the manual result were only 400 tokens.

Show a solution

Call 2: 1,000 + 50 + 100 = 1,150. Call 3: 1,150 + 50 + 2,000 = 3,200. Call 4: 3,200 + 50 + 100 = 3,350. Total: 1,000 + 1,150 + 3,200 + 3,350 = 8,700. With a 400-token manual result: call 3 = 1,150 + 50 + 400 = 1,600; call 4 = 1,600 + 50 + 100 = 1,750; total = 1,000 + 1,150 + 1,600 + 1,750 = 5,500. The large result is carried through call 3 and call 4, which is why shrinking it saves so much.

Summary 2 min

  • The model sees only the context window for one call. Nothing carries over unless the program puts it in.
  • Between steps, the program re-sends the growing transcript. Each big tool result is paid for again on every later call.
  • A fuller window costs more and can recall worse (context rot), so keep the smallest set of useful tokens. Clear old results or compact when it grows.
  • Between sessions, nothing is remembered unless saved: notes outside the window, loaded when needed.
  • Retrieval finds the few relevant chunks of a large store and puts only those in the window. It does not teach the model the manual.
