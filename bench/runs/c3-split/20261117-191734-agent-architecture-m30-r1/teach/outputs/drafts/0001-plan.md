# Plan: What the assistant sees and what it remembers

- Objective: O3, Explain context and memory in an agent: the context window, what is kept between steps and between sessions, and retrieval and notes as memory.
- Minutes: 30; total budget: 4500 words
- Win: By the end of this lesson you can decide, for the makerspace assistant, what stays in its context during a request, what gets saved between a student's visits, and how it finds the right manual page, and defend each choice with a cost or accuracy reason.
- Builds on: learning record 0001 (a model takes text in, writes text out), learning record 0002 (the agent loop: model asks, program runs the tool, result returns, repeat). Quiz 0001 is ungraded, so the lesson re-explains "every step is a separate model call run by the program" as the foundation of S2, without quoting any quiz item.
- Primary source: Effective context engineering for AI agents (Anthropic Engineering) - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents

## Key facts
K1. The context window is all the text the model can reference when generating a response, including the response itself; it is a "working memory", not the training data. Everything in the request counts: system prompt, every message, tool results, documents, and tool definitions. - https://platform.claude.com/docs/en/build-with-claude/context-windows - S1
K2. Failure case: if the input alone exceeds the window, the API returns a 400 `invalid_request_error` ("prompt is too long"). Newer models can instead stop generation with `stop_reason: "model_context_window_exceeded"` when input plus `max_tokens` hits the limit. Window size depends on the model (up to 1M tokens on current models; 200k on some others). The token counting API estimates a request before sending. - https://platform.claude.com/docs/en/build-with-claude/context-windows - S1
K3. Between steps, the program keeps the history: each turn's input is all previous history plus the new message, and each response becomes part of the next input. Previous turns are preserved completely, so every step re-sends everything, and the context grows with each tool result. (Lesson-level inference: the model call itself keeps nothing; the program resends. Reported by third-party guides as "stateless", so word it from the official "input phase contains all previous conversation history" statement.) - https://platform.claude.com/docs/en/build-with-claude/context-windows - S2
K4. More context is not automatically better: as token count grows, accuracy and recall degrade ("context rot"). The model has a finite "attention budget", so aim for the smallest set of high-signal tokens. - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents - S3
K5. When a long run nears the limit, compaction summarizes earlier contents and starts a new context with the summary; the lightest form is clearing old tool results (context editing). Failure case: a summary can drop a detail that mattered later. - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents and https://platform.claude.com/docs/en/build-with-claude/context-windows - S3
K6. Between sessions, nothing survives unless something outside the context window stores it. Structured note-taking: the agent writes notes (a to-do list, a NOTES.md file) outside the window and pulls them back in later. The memory tool does this with files in a directory on the developer's own infrastructure, so the developer controls storage and persistence. - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents and https://claude.com/blog/context-management - S4
K7. Retrieval: instead of loading everything up front, the agent keeps lightweight identifiers (file paths, stored queries, links) and loads data with tools at runtime ("just-in-time retrieval"). The alternative, embedding-based retrieval before the model runs, and hybrids exist; a hybrid loads some context up front and lets the agent explore the rest. - https://anthropic.com/engineering/effective-context-engineering-for-ai-agents - S5

## Sections
### S1 The window
- Concept and term: the context window: everything the model sees in one call, and a hard limit on it.
- Example to trace: a student asks "How do I change the blade on the bandsaw?" Show the actual request the program builds as a Python dict: system prompt (about 400 tokens, made-up), 3 tool definitions (about 600), the student's question (20). Then the model asks to call `search_manual`; the result is a 3,000-token manual excerpt. Tally the running total in a small table, ending near 4,000. Then show the model's answer also counts. Note that input tokens are what the sponsor's bill is made of, so each line of the tally is a cost line.
- Why this works: the model has no access to anything but the text in the call, so whatever is not in that text (a booking, a manual page) does not exist for it, and whatever is in it costs tokens.
- Check: a teammate proposes pasting all 12 machine manuals (about 900,000 tokens, made-up) into the system prompt "so it knows everything". Which is the problem: it may not fit on some models (400 error), it is billed on every call, and it is likely to degrade recall. Options: (a) only that it might not fit, (b) that it costs tokens on every call and may exceed the limit, (c) that models cannot read manuals, (d) nothing, bigger windows solve it. Right is (b); (a) ignores cost, (c) is false, (d) ignores K4 (previewed, taught in S3). Equalize option lengths and vary position.
- Key facts: K1, K2
- Where the length comes from: the line-by-line token tally table and the Python request dict traced field by field; one extra mini-trace of the overflow error (what the program sees, 400 "prompt is too long", and what the code should do: count tokens first, or trim).

### S2 Between steps
- Concept and term: accumulating history: the program, not the model, carries the conversation forward by resending everything each step.
- Example to trace: "Is the laser cutter free Friday, and can I book 2 pm?" (a request the learner already met in the loop record). Step 1: call 1 input = system + question (about 1,000). Model asks `check_calendar`. Step 2: program runs it, appends the tool call and the result (800 tokens of calendar JSON), calls the model again: input about 1,850. Step 3: model asks `book_slot`; step 4 call input about 2,000 after appending the booking confirmation. Show a Python `messages` list with `append` at each step and a table of input tokens per call (1,000, 1,850, 2,000, then final). Add up total billed input across calls (made-up numbers) to show it is the sum, not the last size.
- Why this works: each model call starts from nothing but the text it is given, so the only way step 2 knows what step 1 found is that the program pasted it in again, and each paste is paid for again.
- Check: an agent makes 5 calls and each tool result adds 2,000 tokens to a 1,000-token start. How many input tokens are billed in total across the 5 calls? Right: 1,000 + 3,000 + 5,000 + 7,000 + 9,000 = 25,000. Wrong answers: 11,000 (final size only, forgets resend), 10,000 (adds results once), 15,000 (miscounts growth). Show the work.
- Key facts: K3
- Where the length comes from: the four-step trace with the appended list and per-call table, plus the faded sum in the check; address the misconception "the model remembers the earlier step on its own" with the trace (if the program forgot to append, the model would book without knowing the calendar result).

### S3 When it fills
- Concept and term: context rot (accuracy falls as context grows) and compaction (summarize old context and continue with the summary).
- Example to trace: a long session in which a student asks about 6 machines; by step 14 the context holds 11 old manual excerpts (about 33,000 tokens, made-up), and the answer about the first machine gets vaguer. Show two fixes in order: clear the old tool results (keep only the questions and answers), then if still big, replace the first 10 turns with a 300-token summary: "Student is Sam, wants 3D printer Friday; laser cutter requires safety quiz". Trace the before and after token counts. Then show the failure: the summary left out the Friday 2 pm slot the student had said, so the model re-asks or double-books.
- Why this works: the model spreads a finite attention over every token it is given, so old irrelevant text steals attention from the relevant text, and a summary trades detail for space, which is why the summary must keep what later steps need.
- Check: the assistant's context is at 90 percent after a long manual lookup. Which should it clear first? Options: the old tool results already answered, the system prompt, the student's current question, the tool definitions. Right: old tool results (they are bulk, already used and re-fetchable). Each wrong option removes something needed on every step.
- Key facts: K4, K5
- Where the length comes from: the before-and-after token table and the summary text shown in full, the failure trace, and a second check on what a good summary must keep (a new case: a booking in progress).

### S4 Between sessions
- Concept and term: notes as memory: writing facts to storage outside the context and reading them back next session.
- Example to trace: Sam visits Monday, passes the laser cutter safety training, and the session ends; the context is discarded. Wednesday a new session starts empty. Trace both versions: without notes, the assistant asks Sam's training status again; with a notes file, step by step: at session start the program reads `memory/sam.md` (a small file, about 60 tokens), puts it in the context, and the assistant can say "last time you asked about the laser cutter". Show a small Python sketch with `open(...).read()` at start and `append` at the end, and the memory-tool idea (the model asks to read or write files, the program carries it out in a directory the team controls).
- Why this works: the context lives only for one session, but a file lives on until it is changed, so the program can load a small, chosen slice of it into the next context.
- Check: which of these should the assistant save between visits: the student's preferred machine, a 3,000-token manual excerpt it fetched, the ongoing calendar JSON, or "Sam is cleared for the laser cutter"? Discuss: save short durable facts (preference); re-fetch bulky or changing things. The clearance claim is the safety case below.
- Safety in this section (must appear in the lesson): a note saying "Sam is cleared for the laser cutter" is a note the model wrote, not a verified record. The assistant must not grant or book restricted-machine access from that note. The training record in the makerspace's own system, checked by a tool the program runs, is the source of truth; the note may only say what to check ("ask the training-records tool"). Say who verifies: the training-records system and the staff who maintain it, not the model and not the notes file. Also note that stored student data is a privacy matter the team decides with staff, not the model.
- Key facts: K6
- Where the length comes from: both versions traced side by side as two short timelines, the Python sketch, the notes file shown in full, and the safety paragraph with a worked wrong case (stale note: Sam's training expired; the note still says cleared).

### S5 Finding the page
- Concept and term: retrieval (just-in-time): the assistant keeps a light index and loads only the needed page with a tool.
- Example to trace: the manuals are 12 PDFs, about 900 pages. The question: "What speed should I set for cutting 3 mm acrylic on the laser cutter?" Trace: the system prompt holds only a table of contents (12 entries, about 200 tokens); the model calls `search_manual(machine="laser", query="acrylic speed")`, which returns 3 page ids and short snippets (about 300 tokens); the model calls `read_page(id)` for one (about 800 tokens), and answers citing it. Compare the token count with loading everything (900 pages at about 1,000 tokens, made-up, is about 900,000). Trace what happens when search returns nothing useful: the model refines the query once, then tells the student it could not find it rather than guessing.
- Why this works: the model only needs the one page that answers the question, so a tool that finds and returns just that page keeps the context small and the bill low, at the price of an extra step or two.
- Check: a student asks a question that needs two manuals (a laser cutter and a ventilation unit). What should the assistant do: search each, read the relevant pages, and answer from both; loading both entire manuals; answering from training memory; asking the student which manual. Right: search each and read a page from each. Wrong options show cost, hallucination risk, and needless friction.
- Key facts: K7
- Where the length comes from: the step-by-step trace with the JSON for search results and the no-result branch; a second trace for the two-manual case; the token comparison table.
