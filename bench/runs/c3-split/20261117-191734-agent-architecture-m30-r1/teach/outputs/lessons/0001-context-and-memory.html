What the assistant sees and what it remembers

By the end of this lesson you can answer five design-review questions for the makerspace assistant, each with a cost or accuracy reason: what is in its context, what is resent each step, what happens when it fills, what is saved between visits, and how the right page is found.

Warm-up 2 min

Recall

In the agent loop, a student asks "Is the laser cutter free Friday?" The model decides it needs the calendar. Who actually runs the calendar lookup, and what happens to the result?

Check your answer

The program runs it, not the model. The model only writes a request for the tool; the program carries it out and sends the result back to the model, and the loop repeats until the model has an answer. Today's question is hiding inside that sentence: when the result "goes back to the model", what exactly is sent, and what happens to it afterwards?

1. The window 4.5 min

A student types: "How do I change the blade on the bandsaw?" Before the model sees a single word, your program builds a request. Models read and write text in small chunks called tokens, roughly a word or part of a word; the bill and the size limit are both counted in tokens. Here is the request as a simplified Python dict (a real call also sets model and max_tokens, and tools holds schema dicts), with a made-up token count beside each part:

request = {
    # standing instructions, ~400 tokens
    "system": "You are the makerspace assistant...",
    # 3 tool definitions, ~600 tokens
    "tools": [search_manual, check_calendar, book_slot],
    "messages": [
        # the student's question, ~20 tokens
        {"role": "user", "content": "How do I change the blade?"},
    ],
}

Three tools for now; later sections add read_page and a training-records check. Trace it field by field. system is your standing instructions. tools holds the description of each tool, because the model can only ask for a tool it has been told about. messages holds the conversation so far, which is one question. The model reads all of this, and nothing else, to produce its reply.

The model replies with a request, not an answer: call search_manual with the query "bandsaw blade change" (about 30 tokens). Your program runs the search and gets back a manual excerpt of about 3,000 tokens. It adds that to the messages and calls the model again. Now the model reads the question, the tool request and the whole excerpt, and writes a 150-token answer.

Two things to notice. First, the model's own answer counts too: the window holds the input and the response. Second, you pay for tokens: input is billed on every call, and output too, usually at a higher rate. The table shows the size of the context at each step, not the bill; section 2 shows how the bill adds up. The 3,000-token excerpt is most of the size here.

What the example just showed has a name. The context window is all the text the model can reference when it generates a response, including the response itself; it works like the model's working memory, and it is not the training data. Everything in the request counts: system prompt, every message, tool results, documents and tool definitions. Its size depends on the model, up to 1 million tokens on current models and 200,000 on some others (Anthropic, Context windows).

Why this works

Beyond what it learned in training, the model sees only the text in the call. A booking, a manual page, the student's name: if it is not in that text, it does not exist for the model. And whatever is in the text is billed as tokens, which is why "what goes in the context" is a design decision and a budget decision at once.

2. Between steps 4.5 min

Take a request like the ones in the loop: "Is the 3D printer free Friday, and can I book 2 pm?" (a machine with no training requirement, so a calendar check is enough to book; restricted machines come in section 4). Here is the program's code, with the size of each model call beside it (made-up numbers for tracing):

messages = [{"role": "user",
             "content": "Is the 3D printer free Fri 2 pm? Book it."}]

reply = call_model(system, tools, messages)
# call 1: input ~1,000 tokens
messages.append(reply)    # model asks: check_calendar
result = run_tool(reply)  # calendar JSON, ~800 tokens
messages.append(result)

reply = call_model(system, tools, messages)
# call 2: input ~1,850 tokens
messages.append(reply)    # model asks: book_slot
result = run_tool(reply)  # confirmation, ~100 tokens
messages.append(result)

reply = call_model(system, tools, messages)
# call 3: input ~2,000 tokens
# reply is the final answer: "Booked, Friday 2 pm."

Trace the steps. In call 1 the input is the system prompt, the tools and the question, about 1,000 tokens. The model asks for check_calendar. The program runs it and appends two things: the model's request and the 800-token result. Call 2 therefore sends the original 1,000 plus those 850 or so: about 1,850. The model, now seeing the calendar, asks for book_slot. The program appends that request and the short confirmation, and call 3 sends about 2,000 tokens. The model writes its final answer.

Input tokens per call (made-up numbers for tracing)
CallInput tokensWhat was appended before it
11,000Nothing: system, tools, question
21,850Tool request and 800-token calendar JSON
32,000Booking request and 100-token confirmation
Billed input: 4,850The sum of the calls, not the last size

The name for this: accumulating history. Each turn's input is all the previous history plus the new message, and each response becomes part of the next input; earlier turns are kept completely, so every step re-sends everything and the context grows with each tool result (Anthropic, Context windows). The one doing the carrying is your program, through the append calls. In a long run the resent history is most of the bill. Prompt caching can lower the price of the repeated start of a request, but those tokens still count toward the window (Context windows).

A common mix-up

"The model remembers the earlier step on its own." It feels true because a chat seems continuous. Delete the two append lines and call 2 contains only the question: the model has never seen the calendar, so it either asks for the calendar again or books 2 pm without knowing whether it is free. Nothing carried step 1 over except the program pasting it back in.

Why this works

Each model call starts from nothing but the text it is given. The only way step 2 knows what step 1 found is that the program pasted it in again, and every paste is paid for again as input.

3. When it fills 4.5 min

A student spends a long session asking about six machines. By step 14 the context holds 11 old manual excerpts, about 3,000 tokens each, so about 33,000 tokens, plus roughly 3,000 of system prompt, tools, questions and answers. Then the student asks a follow-up about the first machine, and the answer comes back vaguer than it was at step 2, even though nothing is near the limit. The old excerpts are in the way.

Fix 1 is to clear the old tool results. The questions and answers stay; each used excerpt is replaced by a one-line stub like "[manual excerpt on bandsaw, cleared; search again if needed]".

Before and after, in order (made-up numbers for tracing)
MomentWhat the context holdsTokens
Step 14, beforeSystem, tools, Q and A (3,000) and 11 excerpts (33,000)36,000
After fix 1Same, with each excerpt replaced by a 50-token stub3,550
Much later, before fix 2Ten early turns (20,000) and recent turns (8,000)28,000
After fix 2A 300-token summary and the recent turns (8,000)8,300

Fix 2 is for when clearing is not enough because the conversation itself is long. The program replaces the first 10 turns with a short summary and continues from it:

Summary of earlier conversation: Student is Sam, wants the 3D printer
on Friday. Laser cutter requires the safety quiz. Bandsaw blade
change answered (manual p. 14).

Now the failure. The student had also said, in turn 6, "I need the Friday 2 pm slot". The summary above left it out. Fifty turns later the student says "book it", and the model, which has never seen 2 pm in its current text, asks which time again or picks a slot that clashes with a booking. The summary saved space and lost a detail that mattered.

Two terms go together here. Context rot is the drop in accuracy and recall as the number of tokens in the context grows; the aim is to keep only the few tokens that carry the most useful information. Compaction is the answer to it: when a long run nears the limit, summarize the earlier contents and start a new context with the summary, with clearing old tool results as the lightest form (Anthropic, Effective context engineering; Context windows).

Why this works

The model has a limited attention budget to spread over every token it is given, so old, irrelevant text takes attention away from the text that matters. A summary trades detail for space, so it only works if it keeps what later steps will need.

If you do nothing, the history keeps growing until a call's input exceeds the window. The API then returns a 400 error, "prompt is too long", and the run ends. So measure first: the token counting API estimates a request before you send it, and your code clears or summarizes before the estimate reaches the limit (Context windows).

4. Between sessions 5 min

On Monday, Sam talks to the assistant about the laser cutter and says they passed the safety training. The session ends and the context is discarded. On Wednesday Sam opens a new session. Here are the two timelines.

The same Wednesday, without and with a notes file
StepWithout notesWith notes
1New session starts with an empty context.Program reads memory/sam.md (about 60 tokens).
2Sam: "Can I book the laser cutter?"Program puts the notes in the context, then Sam's question.
3Assistant has no idea who Sam is and asks about training and preferences again.Assistant: "Last time you asked about the laser cutter. I'll check your training record before booking."
4The same questions repeat every visit.At session end the program appends what is new to the file.

The notes file, shown in full, is small on purpose:

# Sam
- Prefers the laser cutter, afternoons.
- Mon: asked about acrylic settings.
- To check: ask the training-records tool before any laser booking.

The code that does it is a few lines of ordinary Python:

import os

def start_session(student_id):
    try:
        with open(f"memory/{student_id}.md") as f:
            notes = f.read()
    except FileNotFoundError:
        return ""
    # goes in the first message, with a visible label
    return "Unverified notes, for context only:\n" + notes

def end_session(student_id, new_facts):
    os.makedirs("memory", exist_ok=True)
    with open(f"memory/{student_id}.md", "a") as f:
        f.write(new_facts + "\n")

student_id must be an id your program issued, never text the student typed. new_facts comes from the model or the student, so your program should accept only allowed kinds of fact, such as preferences and pointers, never clearance or permissions.

The name: external memory, or notes. The agent writes facts to storage outside the context window and pulls them back in later, as with a to-do list or a NOTES.md file. Without something outside the window, nothing survives between sessions, and a bigger window does not change that: the context is gone when the session ends (Anthropic, Effective context engineering). The model can also be given tools to read and write such files itself; the memory tool does this with files on the developer's own infrastructure (Anthropic, Context management).

Why this works

The context lives for one session only, but a file lives until someone changes it. The program can therefore load a small, chosen slice of the file into each new context, which gives the assistant memory without paying for a whole history.

A common mix-up

"A note is a fact." Suppose a note said "Sam passed laser training". That is what the model wrote down from what Sam said, not a verified record. If Sam's training expired last week and the assistant books the laser cutter because of the note, an untrained person is on a dangerous machine. So the assistant must not grant restricted-machine access from a note. The note may only say what to check, such as "ask the training-records tool".

The source of truth is the training record in the makerspace's own system, kept by staff. Enforce it in code: book_slot itself should look up the record and refuse a restricted-machine booking without a current one, whatever the model or the notes say.
Stored student data is also a privacy matter: what is saved, for how long and who can read it is for your team to decide with the makerspace staff.

5. Finding the page 5 min

The manuals are 12 PDFs, about 900 pages. A student asks: "What speed should I set for cutting 3 mm acrylic on the laser cutter?" Trace how the assistant answers without loading any manual up front.

  1. The system prompt holds only a table of contents: 12 entries, about 200 tokens.
  2. The model calls search_manual(machine="laser", query="acrylic speed").
  3. The program returns three page ids with short snippets, about 300 tokens:
[{"id": "laser-p31", "snippet": "Cutting speeds by material: acrylic 3 mm ..."},
 {"id": "laser-p07", "snippet": "Supported materials and thicknesses ..."},
 {"id": "laser-p44", "snippet": "Speed and power presets ..."}]
  1. The model picks laser-p31 and calls read_page("laser-p31"). The program returns that page, about 800 tokens.
  2. The model answers from the page and cites it: "Per the laser manual, p. 31: ..."
Tokens entering the context for this one question (made-up numbers for tracing)
ApproachManual text in contextExtra steps
Load everything (900 pages at about 1,000 tokens)about 900,000, on every call0
Search, then read one pageabout 1,100 (300 of snippets + 800 for the page), plus the 200-token table of contents in the system prompt2

Now the branch where search finds nothing useful. Say the student asks about a setting the manual does not cover and the search returns three unrelated pages. The model refines the query once, for example "acrylic" in place of "acrylic speed". If that also returns nothing useful, it tells the student it could not find the answer in the manuals, and suggests asking staff. It does not guess a number, because a made-up speed setting on a laser cutter is worse than no answer.

The name: retrieval, here just-in-time retrieval. The assistant keeps lightweight identifiers such as file paths, stored queries and links, and loads data with tools at runtime instead of loading everything up front (Anthropic, Effective context engineering).

This is memory too, of a different kind from the notes. The notes file is small, so the program loads it whole at the start of a session. The manuals are far too big to load whole, so they stay in storage and the assistant pulls in one page when it needs it. If the notes ever grew large, they would be searched the same way.

Embedding search is the other main way to find pages; a later lesson covers it.
Why this works

The model only needs the one page that answers the question. A tool that finds and returns just that page keeps the context small and the bill low, at the price of an extra step or two.

Worked example and practice 4 min

Worked example

Design the assistant's memory for "Sam asks, on Monday, about the laser cutter, then returns on Wednesday to book it". One decision and one reason for each of the five concepts (made-up numbers for tracing).

  1. What is in the context (section 1). At the first call on Wednesday: system prompt with the table of contents (600), five tool definitions (search, read page, calendar, booking, training check; 1,000), Sam's notes (60) and the question (30), about 1,690 tokens. Reason: only what every step needs is always present, and everything is billed.
  2. What is resent (section 2). The program appends the calendar check and the booking, so history grows and each call resends it. Reason: the model keeps nothing between calls, so it must be given the calendar result again.
  3. What happens when it fills (section 3). If a long manual lookup fills the context, clear the old tool results first and keep the pending booking in any summary. Reason: results are bulk and re-fetchable, and the pending slot exists nowhere else.
  4. What is saved (section 4). memory/sam.md holds the preference and "check the training-records tool before any laser booking". Whether Sam is trained comes from the training-records tool at booking time. Reason: a note is not a verified record, and the training-records system and its staff are the source of truth.
  5. How the page is found (section 5). Search, then read one page, adding about 1,100 tokens of manual text. Reason: one page answers the question.

Budget line for Wednesday's laser-cutter manual question: call 1 about 1,690 tokens, call 2 about 2,020 (adds the search request and 300 of snippets), call 3 about 2,850 (adds the page request and the 800-token page). Billed input: about 6,560 tokens, against millions for pasting all manuals into every call.

Summary 1 min

Memory inside a session is the context, kept by the program between steps. Memory across sessions is notes stored outside the context. Retrieval pulls big stored knowledge in on demand. The five answers for your design review:

  1. In the context: only what every step needs, because every token is billed and the window is limited.
  2. Resent each step: the whole history, because each call starts from nothing but the text it is given.
  3. When it fills: clear old tool results first, then summarize, keeping pending state.
  4. Saved between visits: short durable notes, never a claim to act on; verify from the source of truth.
  5. Finding the page: search, then read one page, instead of loading every manual.
