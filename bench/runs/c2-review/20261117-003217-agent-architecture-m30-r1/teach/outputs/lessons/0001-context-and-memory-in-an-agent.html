Context and memory in an agent

By the end of this lesson you can explain what your makerspace assistant keeps in its context, what it saves between sessions, and how it finds the right page in a long manual, and sketch where each piece of one request lives.

Objective O3: context and memory in an agent About 30 minutes Builds on: the agent loop
Why this matters for you

Your assistant has to answer from long machine manuals and remember each student's training status between visits, on a small model budget. Each of these is a decision about what goes into the model's context and what stays outside it, and you will defend those decisions at your design review.

The context window: all the model sees 4 min

A student writes to your assistant: "Is the laser cutter free tomorrow at 3 pm, and do I need training to use it?" Before the first model call, your program assembles one block of text:

  1. The system prompt: the assistant's role and rules (say 300 tokens).
  2. The tool definitions: names and descriptions of check_calendar, search_manuals, check_training_record and book_slot (say 500 tokens).
  3. The student's message (30 tokens).

That block, 830 tokens, is the model call's entire input. The model has no other source: it cannot look at the calendar, your code, or last week's chat. If a rule such as "bookings are limited to 2 hours" is not in that block, the model does not know it, however many times you told it before.

A token is a small piece of text, often part of a word. Providers measure input and output in tokens and charge for them, which is why this lesson counts in tokens.

What you just traced has a name: the context window is all the text the model can reference when it writes a response, including the response itself; the docs call it the model's "working memory", as opposed to the large body of data it was trained on (Claude docs: context windows). Everything in a request counts toward it: system prompt, every message including tool results, and the tool definitions.

The window has a maximum size: up to 1 million tokens on current Claude models, 200 thousand on some others. If the input alone is larger, the API rejects the request with a "prompt is too long" error (Claude docs).
Why this works

The model writes its answer from the text in front of it plus what it learned in training, and talking to it does not change that training (the model itself stays the same between calls). So anything it should use right now must be put into that text. "Context" is simply the name for what you chose to put there.

Check yourself

A teammate says: "We'll explain the booking rules to the assistant once, in Monday's chat, and it will know them all semester." What is wrong with this plan?

Show the answer

The second option. The model has no memory of Monday; it only reads what your program sends with each call, so durable rules belong in the system prompt.

What is kept between steps 5 min

Continue the same request. The loop from your first session now runs, and the program keeps a Python list called messages. Here is what each model call receives (illustrative token counts, and a simplified list: the real API wraps tool results inside messages):

# call 1 input: 830 tokens
messages = [question]

# model asks for check_calendar (+40); result (+200)
messages += [request, calendar_result]
# call 2 input: 830 + 40 + 200 = 1,070

# model asks for search_manuals (+40); result (+1,500)
messages += [request, manual_pages]
# call 3 input: 1,070 + 40 + 1,500 = 2,610

# model asks for check_training_record (+40); result (+60)
messages += [request, training_result]
# call 4 input: 2,610 + 40 + 60 = 2,710
# the model now writes the final answer

Each call carries everything from the earlier calls, because the program appends each request and result and sends the whole list again. The total the model reads across the four calls is 830 + 1,070 + 2,610 + 2,710 = 7,220 input tokens, not 2,710. (How search_manuals finds those manual pages is section 5.)

This has a name: the message history (or conversation history) is the list of everything exchanged so far, and it is what the agent "keeps" between steps. With the API, previous turns are preserved completely and each turn's input is all previous history plus the new message (Claude docs: context windows). The program holds the list; the model re-reads it every time.

Why this works

Every model call is separate, so the only way a step can build on an earlier step is for the program to put the earlier step's text back in. Input is paid for on every call, so a long history is paid for again at each step. What you choose to re-send is the cost lever you control.

Providers also offer prompt caching, which lowers the price of an unchanged, repeated beginning of the input. The cached tokens still occupy the window; caching changes what you pay, not whether they count (Claude docs).
A common mix-up

"The model remembers step 1 by itself." A chat app makes it feel that way. But in call 2 the model knows the student's question only because your program re-sent it. Leave it out of the list and the model sees a calendar result for a question it was never shown.

Check yourself

Your system prompt plus tool definitions is 1,000 tokens and the student's question is 50. The model makes three tool requests of 50 tokens each; each tool result is 500 tokens. It then writes a final answer. The history is never trimmed. How many input tokens do the four calls read in total? (Do not count the final answer.)

Show the answer

7,500. Call inputs are 1,050, 1,600, 2,150 and 2,700, since each step adds 550 tokens (a 50-token request and a 500-token result) to the history.

When the context fills up: clearing 4 min

In section 2 the manual pages were re-sent in call 4, where nobody needed them. Now picture a longer session: a student spends 20 minutes asking about three machines, and the assistant runs search_manuals eight times. Each result is 1,500 tokens, so about 12,000 tokens of manual pages sit in the history. Then the student says: "OK, book me the bandsaw on Friday at 2." To do that, the model needs the booking tool and the current request. It does not need the laser cutter's lens-cleaning page from minute 3.

Before the next call, the program can keep the request lines but replace old results with a stub (using the same simplified list as before).

def clear_old_results(messages, keep_last=1):
    results = [m for m in messages
               if m["role"] == "tool_result"]
    for m in results[:-keep_last]:
        m["content"] = "[cleared: search again if needed]"
    return messages

Trace it: with eight results and keep_last=1, results 1 to 7 become a stub of about 12 tokens each, and result 8 stays whole. The history drops from about 12,000 tokens of manual text to about 1,600. With keep_last=2 it is about 3,100. Either way the model can still see that it searched, and can search again.

This is tool result clearing: dropping old tool outputs from the context once they have served their purpose. Anthropic describes it as one of the lightest forms of compaction, the general idea of shrinking a context that is nearing its limit (Anthropic: effective context engineering).

Why this works

More context is not automatically better: as the token count grows, accuracy and recall degrade, which the docs call context rot (Claude docs). A bigger window raises the ceiling but not that effect, nor the per-call cost. Old results are the cheapest thing to drop, because the model has already used them and the tool can be called again.

Clearing is the light touch; heavier compaction summarizes the whole conversation and restarts from the summary, which a later lesson covers. Two cautions: clearing changes the start of the input, so it breaks any cached prefix, and the docs advise clearing enough tokens each time to be worth that loss, not a little at every step (Claude docs: context editing). And a session that overflows the window fails or stops early, so clear before you hit the limit.
Check yourself

At step 12 of a session, the context holds the system prompt, the tool definitions, the student's latest request, and eight old manual search results. Which should you clear first?

Show the answer

The old search results: large, already used, and re-obtainable. The other three are what the model needs for its next call.

Between sessions: notes 5 min

On October 3 an instructor signs Priya off on the laser cutter, and your program records it. On Thursday she opens a new chat and asks, "Can I book the laser cutter?" The new session starts with a fresh list: messages = []. Nothing from earlier chats is in it, so the model has no idea who Priya is or what she completed. (Section 1 again: no text in the call, no knowledge in the call.)

The fix lives outside the model. Your program keeps a small file of records and loads one into the system prompt when a session starts:

records = {
  "priya": {"trained": ["laser (Oct 3)"],
            "notes": ["prefers mornings"]},
}

def start_session(student_id):
    r = records.get(student_id, {})
    return f"Student record: {r}"

def save_note(student_id, text):  # a tool
    rec = records.setdefault(
        student_id, {"trained": [], "notes": []})
    rec["notes"].append(text)

Trace Thursday: start_session("priya") adds a line to the system prompt that reads, in effect, "trained: laser (Oct 3); notes: prefers mornings", about 40 tokens. The model reads it and answers: you are trained on the laser cutter, so let me check the calendar for mornings. At the end it calls save_note("priya", "asked about laser booking"), so Friday's session can load that too.

This is notes as memory: information written to storage outside the context window and loaded back into a later context (Anthropic calls this structured note-taking, or agentic memory, in effective context engineering). The assistant's "memory" between sessions is only the notes your program loads.

Why this works

Since a model call sees only its input, any memory that survives a session must live somewhere else, such as a file or database, and be put back into the input later. A short record carries the facts without the whole old chat. It has to stay short: a record loaded in full counts against the window every call, so cap it or summarize old notes.

A common mix-up

"The assistant learns from every chat, so it will remember students." Chatbot apps make it seem so, but as in section 1 the model itself does not change; any remembering is a program saving and re-loading text.

A risky habit

"If a student says they are trained, save it." Look at who writes what in the code: trained is written only by your program, from the instructor's sign-off, because training status gates machine access. notes is where the model may write, and it holds soft facts such as preferences, never access. Loaded notes are unverified text, and the booking tool should re-check check_training_record before it confirms.

Check yourself

Marcus tells the assistant he likes the 3D printer's left bed because it is flatter. Which of these should be saved as a note for his next session, rather than fetched or fixed in the system prompt?

Show the answer

The bed preference. It is per student and lasting. Job status changes constantly (use a tool), and rules belong in the system prompt.

Long manuals: retrieval 5 min

The laser cutter manual is 120 pages, roughly 60,000 tokens. Pasting it in the system prompt means every model call re-sends 60,000 tokens (section 2). Instead, split the manual in advance into small pieces and search them when a question comes in. Here are three pieces (real ones are 300 to 500 tokens; these are tiny) and a deliberately simple search:

chunks = [
  {"id": "laser-3",
   "text": "Clean the focus lens with alcohol "
           "before each session"},
  {"id": "laser-7",
   "text": "Never cut PVC it releases chlorine gas"},
  {"id": "printer-2",
   "text": "Level the print bed before the first layer"},
]

def search_manuals(query, k=1):
    q = set(query.lower().split())
    def score(c):
        return len(q & set(c["text"].lower().split()))
    return sorted(chunks, key=score, reverse=True)[:k]

A student asks how to clean the focus lens. The model calls search_manuals("clean the laser focus lens"). The query's words are {clean, the, laser, focus, lens}. The scores: laser-3 shares clean, the, focus, lens = 4; printer-2 shares only "the" = 1; laser-7 shares nothing = 0. With k=1 the tool returns laser-3, and the model writes its answer from it. With real chunks and k=3 the result is about 1,500 tokens, the size used in section 2, and still 40 times smaller than the manual.

This is retrieval: finding the few pieces of a large source that match the question and putting only those into the context, as the tool result. The pieces are called chunks (Anthropic's context engineering article describes agents loading data like this at run time, with tools).

Why this works

The model needs a few relevant paragraphs, not the whole manual, so the search does the finding and the context holds only the result. That costs a small result per step instead of a huge one, and the model reads a short, focused context. The cost: the answer is only as good as the search, so a bad match gives the model the wrong page.

printer-2 scored 1 only because of the word "the", which shows how crude word overlap is. Real search compares meaning rather than words; a later lesson covers it.

Notes and retrieval are both memory kept outside the window and pulled in when needed. They differ in who writes them, and so in how they are used:

MemoryWritten byPulled in
Student records (notes)Your program, and the model for soft notesLoaded whole at session start
Manual chunks (retrieval)People, once, in advanceSearched when a question needs them
A common mix-up

"The window holds 1 million tokens, so just paste the whole manual." It fits, so no error, but fitting is not free. At 4 calls per request, a pasted 60,000-token manual is about 4 x 60,000 = 240,000 input tokens per request; retrieving 1,500 tokens each call is 4 x 1,500 = 6,000. Recall can also degrade in a long context.

Check yourself

The blade-change steps. They are one small part of a large manual and needed only occasionally. The training list is a short record, and the booking rule is a system prompt rule.

Worked example and practice 4 min

Worked example

Priya (trained on the laser cutter only) writes: "Can I book the CNC router Thursday at 2 pm? And which bit do I use for acrylic?" Decide what goes where.

  1. Session start, context. The program loads Priya's record (about 40 tokens) into the system prompt along with the rules and tool definitions. Reason: these are needed on every call, and the record is small.
  2. Call 1, from context alone. The model sees "trained: laser only", so it tells her the CNC router needs training first, with no tool call. Reason: a fact already in context is cheaper than a tool result. (If she had asked to book, the booking tool would still re-check her record before confirming.)
  3. Call 2, retrieval. For the bit question the model calls search_manuals("CNC router bit acrylic"). One or two chunks (a few hundred tokens) come back. Reason: the manual stays outside; only the match enters.
  4. Call 3, final answer. The model tells her about the training requirement and the bit, from context and one chunk.
  5. Session end, notes. The model calls save_note("priya", "asked about CNC router and acrylic bit"). Reason: the next session can start there. It is a soft note, not a training claim.
  6. Clearing. Not needed here; with three calls the history is small. It matters in longer sessions.
Your turn

Marcus is trained on the 3D printer. He returns after two weeks and writes: "Is the 3D printer free Saturday morning, and what was I printing last time?" Steps 1 and 2 are given: (1) the program loads Marcus's record into the system prompt at session start; (2) the model calls check_calendar for Saturday, because slots change daily. You do the rest: (3) where does "what I was printing last time" come from, and what if it was never saved? (4) What should be saved at the end? (5) Sketch three boxes (context, saved records, manual chunks) and place these six items in them: the booking rules, the tool definitions, Marcus's training, Saturday's free slots, his last print, and the 3D printer's bed-leveling procedure.

Show a solution
  1. "What I was printing last time": a saved note, loaded at session start, provided the previous session saved one with save_note. If none was saved, nothing can supply it, and the assistant should say so instead of guessing.
  2. Save a soft note such as "asked about Saturday morning slot". No manual search is needed, and clearing is not needed in a short session.
  3. Context: the booking rules (system prompt), the tool definitions, the loaded record and Saturday's slots (calendar result). Saved records: Marcus's training and his last print. Manual chunks: the bed-leveling procedure, fetched only if he asks.

Summary 1 min

  • The context window is everything the model sees in one call: system prompt, tool definitions, history and tool results.
  • Between steps, your program keeps the message history and re-sends all of it each call, so cost grows with history length.
  • Clear old tool results to keep the context small and focused.
  • Between sessions, nothing survives unless your program saves notes and loads them back; safety facts such as training come from the sign-off record, not from chat.
  • Retrieval puts only the matching chunks of a long manual into the context. Notes and retrieval are both memory outside the window.
